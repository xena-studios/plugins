## One minimum version: Paper 1.21.11, Java 21 (2026-10-21)

Every plugin supports the same oldest Paper, so the core is written once against one API. 1.21.11 is the last 1.21 release and still widely run; 26.x needs Java 25, so building for 1.21.11 with Java 21 bytecode covers both. xLimbo drops 1.18.2. Raising the minimum is a breaking change and needs a new major version.

## The rewrite ships as new majors, one plugin at a time (2026-10-21)

xUtilities 2, then zChat 3, then xLimbo 2, each released before the next starts, so the docs always describe released versions. Each carries old configs forward automatically, backing up the old file first. The old source is gone; the docs are the spec.

## The core is shaded into each plugin, never installed on its own (2026-10-21)

Server owners install one jar per plugin and nothing else. Each plugin relocates its copy of the core (`co.xenastudios.<plugin>.core`), so plugins built on different core versions never clash, and `minimize()` drops the core classes a plugin doesn't use.

## Commands are registered at runtime, so command changes apply on reload (2026-10-21)

Spike (`sandbox/`, checked in CI): a command registered through the Bukkit command map after startup runs by name, alias and `namespace:name`, tab-completes, and appears in the command tree the server sends clients. Removing it from `getKnownCommands()` takes it out of that tree, and re-registering with new aliases drops the old ones. Each takes well under 10 ms. This passes on Paper and Folia, 1.21.11 and 26.3.

So turning a command on or off, its aliases and permission, and adding or removing link commands can all apply on `/<plugin> reload` (followed by `Player#updateCommands`), instead of needing a restart. A disabled command isn't registered at all, so another plugin can take its name. Paper's Brigadier lifecycle API can't do this: it only registers at startup and on a datapack reload.

Still to confirm with a real client: that `updateCommands` refreshes tab completion for players already online. (It's the call LuckPerms and others make for the same reason.)

Gotcha: a command dispatched while another command is running is queued until that one finishes, so code that dispatches commands must run outside a command's execution.

## Configs are generated from a schema in code (2026-10-21)

A spike showed that Paper's `YamlConfiguration` writes a commented config and reads it back with no server running. (That test is gone; the core's `ConfigLoaderTest` now covers writing and reading configs.) Each plugin declares its settings once (default, validation, comment); the same declaration writes the default `config.yml`, reads and checks the live one, and generates the docs' "full default config" in each plugin's `DefaultConfigTest`, so the docs can't drift from the code.

## Boot tests on real servers (2026-10-21)

`scripts/boot-test.sh` boots a real Paper or Folia server with the plugin jars, runs console commands, stops it, and fails on any error in the log or any warning from our plugins. CI runs it at the minimum version and the newest, on both. Unit tests can't catch a plugin that fails to enable, or a Folia threading mistake; this does.

## The core: what every plugin gets (2026-10-21)

Built with xUtilities 2. A plugin extends `XenaPlugin`, declares its config as records (`ConfigSpec`), and says in `setup(config)` which commands, permissions and modules that config wants. The core applies the difference on startup and on every reload, so a plugin never handles reload itself. It also gives every plugin `/<plugin> reload|info` and the update checker, and isolates failures: a command that throws sends "something went wrong" and logs the trace; a module that won't start stays off; neither takes the rest down.

- **Permissions are declared from the config**, with the command's default, so a renamed permission keeps it (a renamed `/ping` permission is still everyone's).
- **Server commands are replaced and given back.** Paper wraps vanilla commands in a new object on every lookup, so they're recognised as "not a plugin's" rather than by identity. Another plugin's command is never replaced: that clash is a console warning, and ours stays reachable namespaced.
- **The default config is written by the core's own emitter**, not Bukkit's: quoted strings, inline lists, comments, blank lines between sections. Carrying an old file forward still goes through Bukkit, which keeps the owner's values and comments.
- **A file that isn't valid YAML is never overwritten.** On reload the running config stays; at startup the defaults run until it's fixed.
- **Tests never reach the network**: they run with `-Dxena.offline=true`, which keeps the update checker and bStats off.

## Jar budgets are per plugin, and honest (2026-10-21)

xUtilities 2 is about 146 KiB against 1.x's 100.5: roughly 60 KiB of core (reload for everything, config migration, the theme, the update checker), 15 KiB of bStats, 50 KiB of commands, and 4 KiB of 1.x's default messages (so an upgrader who never changed one gets 2.0's look), plus zip overhead. Compiling without local variable tables (keeping line numbers, for stack traces) saved 13 KiB. Its budget is 150 KiB, so anything that grows it is a decision, not drift. (Budgets were raised the next day: see [Jar budgets are a tripwire, not a target](#jar-budgets-are-a-tripwire-not-a-target-2026-10-22).)

bStats lives in the core, relocated into each plugin's package; a plugin opts in by overriding `bStatsId()`. The IDs: xUtilities 34866, zChat 21533 (from zChat 1.0, which still reports to it, so zChat 3 carries its history on), xLimbo 34867, xRewind 35410, xPlots 35419, xTeleport 35423, xVote 35422, xBans 35418, xMoney 35421, xStats 35436, xBackup 35420. bStats' Bukkit class submits from its own thread on Folia, so it needs no scheduler of ours. Tests never start it (`xena.offline`). Runtime cost is what "lightweight" is really about: no repeating tasks, listeners only while their feature is on, and every message parsed once, not per send.

## Messages share a theme (2026-10-21)

Every plugin's config starts with a `theme`: a prefix, a base colour, and `<highlight>`, `<success>` and `<error>` styles that messages use as MiniMessage tags. Default messages are written only in those, so an owner restyles a whole plugin in five lines, and every plugin in the family looks alike out of the box. The base colour wraps each chat message rather than being a tag, so messages don't need to open and close it. A message is parsed the first time it's sent and again only if the theme changes (on reload); messages with placeholders parse per send, as before.

When a default message changes, its old text goes in the spec with `formerDefault`. Carrying an old file forward gives any setting still on an old default the new one, in place, so owners who never touched their messages get the new look and owners who did keep theirs.

## MockBukkit for command logic, real servers for the rest (2026-10-21)

MockBukkit runs the commands' logic in milliseconds, but it can't `teleportAsync`, cancel Folia-style tasks, or tell harmful potion effects apart, and plugin classes it loads can't be `final`. Those paths are covered by `boot-checks.txt` on real servers, or by reading the code. CI also compiles against the newest Paper with removal warnings as errors (`-Pxena.newestPaper`), which is how `PotionEffectType#getCategory` (marked for removal in 26.3) was caught before release.

## Jar budgets are a tripwire, not a target (2026-10-22)

"Lightweight" means what a plugin costs while it runs: no repeating tasks, listeners only while their feature is on, messages parsed once. Jar size barely affects that, since a 160 KiB jar loads as fast as a 100 KiB one. Budgets that sat within 5 KiB of each jar failed on every reasonable feature, so each is now about 50 KiB above its jar (xUtilities 200, zChat 210, xLimbo 220) and a new plugin starts at 150 (the core and bStats alone are about 75). They still catch what they're for: a library shaded in by mistake, or code copied instead of shared, which add hundreds of KiB. A plugin within 10 KiB of its budget should get it raised on purpose, with the reason beside it.

## Renovate for dependencies, a workflow for Minecraft (2026-10-22)

Renovate, not Dependabot: it groups every minor and patch update into one weekly PR, merges it once CI passes, and shares one config across the org's repos (`xena-studios/.github`'s `renovate-config.json`). Automerge is per repo: here and in NeoSkript, where CI covers what a merge changes and nothing goes live; not in Raptor, the website (a merge deploys it) or brand (no CI). The minimum Paper is excluded, because raising it is a breaking change for owners.

New Minecraft versions aren't a dependency bump. They append to `xena.gameVersions` (Modrinth's list) and move two CI pins together, which Renovate can't express, and "released" means Paper has a stable build, not just a Maven artifact. `scripts/new-minecraft.sh` reads that from Paper's download API; `minecraft.yml` runs it on Mondays, with Renovate's batch, and opens the PR; it can also be run by hand when a version comes out. A PR opened with the workflow's token doesn't trigger other workflows, so it starts `plugins.yml` itself.

## zChat's chat path (2026-10-22)

Every chat message runs through one `AsyncChatEvent` handler, cheapest check first: mute, cooldown, filter, anti-repeat, then mentions and the format. The format is set as a viewer-unaware renderer, so Paper draws the line once and sends it to every viewer. Measured on MockBukkit, a whole message costs about 40 µs off the main thread; the filter is about 2.5 µs and drawing the format about 10 µs.

- **State is safe from any thread.** Chat runs on many threads at once (Folia especially), so the mute, cooldowns, hidden chat, spies and reply targets live in concurrent maps. Mentions look names up in zChat's own concurrent index, kept on join and quit, not the server's player map, which isn't meant for that.
- **The smart filter folds, then matches whole tokens.** Each character is lowercased, stripped of accents, and has number-for-letter swaps undone; everything else is a gap. Runs of single letters ("b a d") are joined. A word becomes a regex where each run of a letter matches that many or more ("baad" → `b+a{2,}d+`), so stretched letters are caught but "as" never matches "ass". Matching whole tokens is what keeps *class* clean. The original index of every folded character is kept, so censoring hits exactly what was typed.
- **PlaceholderAPI values are inserted, not pasted.** `%name%` in a format is rewritten to `<papi:'name'>` at load; the tag inserts the value as legacy-coloured text after parsing. Pasting it into the template first, as zChat 2 did, let any placeholder that shows player-chosen text inject clicks and hovers.
- **Group permissions default to false.** An operator getting the admin format because they're an operator surprised owners.
- **A zChat 1.x config is set aside, not migrated.** It was a different plugin with no `config-version`; `ConfigSpec.foreign` recognises it, moves it to `config.yml.old` and writes the defaults.

## xLimbo is Paper only (2026-10-22)

Folia can't create worlds at runtime, and creating its void world is xLimbo's core job. A limbo also has nothing for Folia to parallelise: no mobs, no redstone, players standing still. Its real load is a mass arrival (logins and chunk sending), which Folia barely helps. So `folia = false`, and xLimbo is free to use Paper-only API.

- **Players are placed before they're in the world.** `AsyncPlayerSpawnLocationEvent` sets the spawn while the player is still configuring, so there's no teleport after joining and each arrival loads one spot once.
- **The spawn area is kept loaded** with plugin chunk tickets (at most 17×17 chunks), and the default spread is 64 blocks, not 1.x's 4000: a mass arrival is a few dozen ready chunks, not a fresh chunk per player.
- **The return queue is main-thread state** fed by an async status ping (a raw Server List Ping, about 60 lines, no library). A server only answers status once it's ticking, so an answer means it's ready for players. Players are tried at most three times in five minutes, so a ban on the main server can't bounce someone forever.
- **No game rules.** Minecraft 1.21.11 renamed them and Paper marked the old constants for removal; every rule xLimbo wanted already had a better route (event cancels, the void biome's empty spawn list, a long clear-weather spell).
- **xLimbo only deletes what it made.** A world folder xLimbo creates gets an `xlimbo.dat` marker with the floor it was made with; only marked folders are ever deleted, rebuilt or unloaded. A world it didn't make (the main world, a Multiverse world) is configured and nothing more, and an unloaded folder it didn't make is refused rather than adopted or deleted. Folders are found through the server, since 26.1 keeps extra worlds under `<main world>/dimensions/minecraft/`.
- **Players can't see each other by default** (`player.hide-others`). Hundreds of players arriving in one spot each tracking every other one is a limbo's biggest load by far, much more than anything xLimbo itself does.
- **The 2.0 jar was about 165 KiB**: the shared core and bStats are about 75 KiB, and the world safety, return queue, status ping and protections the rest.
- **Rebuilding on reload** moves players to the server's main world, unloads the limbo, deletes it if it's temporary, makes it again and puts them back. The main world itself can't be rebuilt, so in single-world mode floor changes say "restart".

## Main is protected, and checked by CodeQL (2026-10-23)

`main` takes changes only through pull requests, never force-pushed or deleted, and requires two checks: `plugins-ok` and `docs-ok`. A required check has to report on every PR, but each workflow only has work for some of them, so each runs on every PR, skips what the change doesn't touch (its `changes` job), and ends in one job that passes when everything else passed or was skipped. A PR that the New Minecraft workflow opens has to start both workflows itself.

Code scanning is CodeQL, GitHub's own: the deepest free dataflow analysis for Java (a player's chat line followed into a command, for example), with results on the PR. Java is traced through a real Gradle build rather than CodeQL's build-less mode, for accuracy; the workflows and the docs' scripts are scanned too. `security-extended` queries, weekly as well as on every change. Dependencies are left to Renovate, which opens a fix PR as soon as one has a known vulnerability (`osvVulnerabilityAlerts`, in the org's shared settings): Dependabot alerts and its fix PRs would duplicate it.

## A config that can't be saved is still used (2026-11-17)

Loading writes the file back whenever it changes it (carrying it forward, adding new settings). Some hosts mount plugin folders read-only, and some volumes can't replace a file in one step. Before, either case dropped the owner's whole config for the defaults. Now a failed write is a warning and the settings are used as read; a mount without atomic moves falls back to a plain replace; and a migration whose backup can't be made is carried forward in memory only and never written, so a backup can't pile up on every start. `ConfigLoader.read` peeks at the settings without writing anything, for code that runs before the plugin's own load (xLimbo's world generator).

## In-game edits write config.yml (2026-11-17)

`/filter` changes `filter.words` in `config.yml` rather than keeping its own file, so there's one list whether staff edit it in game or by hand, and the docs' config page stays the whole story. The edit goes through `XenaPlugin.editConfig`: on the global thread outside the command, Bukkit reads the file (keeping the owner's comments), the change is checked against the file itself (so a hand edit made without a reload counts), the file is swapped in whole, and the normal reload applies it. A file that isn't valid YAML is never touched, and a change that changes nothing writes nothing. Bukkit writes lists in block style, as the config migration already does. Any plugin can use it for in-game settings later.

## Releases: the job that runs Gradle can't write to the repo (2026-11-17)

`release.yml` is three jobs. **publish** checks the tag, builds, and publishes the plugin's API (if it has one) to Maven Central and the plugin to Modrinth, Hangar and voxel.shop with the `release` environment's secrets, but its `GITHUB_TOKEN` can only read. **github** has `contents: write` and runs no project code (no checkout, no Gradle): it uploads the jar and notes the first job built. **docs** runs no project code either: its one permission, `actions: write`, starts the Docs workflow, so the site shows the new version. So a build script, a Gradle plugin or a dependency can never push to the repo or rewrite a release. Workflows default to `permissions: {}` and each job asks for what it needs.

## Audit follow-ups: split words, vanish, reloads (2026-11-17)

- **The smart filter joins short pieces only into whole words.** Runs of one- and two-letter pieces ("ba dw or d") are joined and must make a whole filter word, never contain one, so "is it to an" can't censor anything. Words with a `*` are left out, because "as so" makes `*ass*`. Pieces longer than two letters aren't joined: "pen is" would make a word.
- **`Player#canSee` from the chat thread is accepted as racy.** Paper keeps who a player has hidden in a plain `HashMap` written on the main thread. Read from the chat thread it can give the wrong answer around the moment someone vanishes, but not crash, so mentions still use it for the highlight. The ping asks again on the target's own thread (the main thread on Paper), so a vanished player is never pinged. A concurrent snapshot would need events Paper doesn't fire for hide and show.
- **xLimbo's return history lives on the plugin.** The return queue restarts when server-check's settings change on reload; the tries and arrival times it reads are kept by the plugin, so a reload can't hand a refused player three more tries. Tries outlive a quit: being sent back is quitting.
- **Plugins can let go of things on disable.** `XenaPlugin.shutdown()` runs after the modules stop. xLimbo uses it to unload a world it made when it's disabled while the server keeps running (`/reload confirm`), so the world doesn't keep the old instance's generator; the new instance makes it again and brings players in. A world the server loaded itself can't be remade, so its floor is read from a generator of the same class name.

## A shared database layer, with no drivers shaded in (2026-11-17)

xRewind keeps its history in a database, and the voting and economy plugins now do too, so `core/db` opens one from a shared `storage` config section: SQLite in the plugin's folder by default, MySQL or MariaDB for networks.

- **No driver in the jar.** Paper and Folia ship sqlite-jdbc and mysql-connector-j (checked on 1.21.11 and 26.3), and a paper-plugin's class loader sees them. Shading them would add about 14 MiB. If Paper ever drops them, a `PluginLoader` can fetch them at startup.
- **SQLite is set up for one writer and many readers:** WAL, so lookups never wait for the writer; `synchronous=NORMAL`, safe with WAL (a power cut can lose the last moments, never corrupt the file); `auto_vacuum=INCREMENTAL`, so purges give space back a little at a time instead of locking the file for a full `VACUUM`.
- **Numbered schema steps**, recorded in a `meta` table, each in its own transaction. A database made by a newer version is refused, never changed.
- **Connections on demand, no pool.** A plugin that writes a lot keeps one connection for its writer; reads are staff commands, rare enough to open their own.

xRewind opens its database off the server's threads, so a slow or unreachable MySQL never holds up startup or a reload, and a reload that can't open a new database keeps the old one. Its rows are only numbers: names, worlds, block states and items are stored once in dictionary tables, and times are seconds since 2026 in four bytes, which last until 2094.

## xRewind's write path: references in, numbers out (2026-11-17)

A listener does as little as it can: it builds one record from what the event already has (the player's uuid and name, the world's name, the block's `BlockData` before and after) and adds it to a lock-free queue. It looks nothing up and takes no lock, so it's as cheap on Folia's region threads as on Paper's main thread: about 40 ns in the benchmark (`WriterTest`), against a budget of 2 µs.

One writer thread does the rest. It owns the dictionaries that turn names, worlds and block states into ids, as plain maps, since nothing else touches them, and writes batches of up to 10,000 rows, each one transaction, every half second or as soon as 2,000 are waiting. New dictionary rows go in the same transaction as the first rows that use them, so no row ever points at a name that isn't there. A batch that fails is kept and retried on a fresh connection, after a pause that grows to 30 seconds; the console hears about it once, not on every retry. Until the database is ready, or while it's down, entries wait in the queue: the console is warned at 100,000, and past a million new ones are counted and dropped rather than run the server out of memory. Stopping writes what's left, for up to 10 seconds.

A batch that keeps failing on a live connection (three times in a row) is a row the database won't take, not the database being down, so its rows are then written one at a time and only that one is dropped, with a warning; `/xrewind status` counts it as missed. MySQL tables are made utf8mb4 whatever the database's default, so a heart on a sign or an emoji in chat is never that row.

`BlockData` is safe to read from the writer: the server's block states are immutable, and `getBlockData` hands back a copy.

Plugins can now add subcommands to their own command (`Setup.subcommand`): `/xrewind status` sits beside `reload` and `info`, each with its own permission, so staff who aren't admins can use the ones they're given.

## xPlots: plots in memory, found by arithmetic (2026-11-17)

xPlots replaces a Skript that rented one WorldGuard region per plot and rewrote every nearby sign each second. It's Paper only for 1.0, like xLimbo: putting plots back and editing signs across Folia's regions adds risk with little gain for box servers.

- **No region per plot.** A field is one selection split into a grid, and the plot for a block is worked out from the grid: `(x - origin) / (size + path)`, the remainder saying "path". Each world keeps the box around all its fields, so a block outside every field costs one check. A field's whole footprint is protected at every height; plots are buildable only between the selection's lowest and highest blocks. With WorldGuard installed, xPlots makes one region per field that allows building, so a world-wide `build deny` doesn't block plots, and decides who may build itself.
- **Everything in memory, loaded before anyone joins.** Plots are read once, synchronously, while the server starts, so there's never a moment when plots exist but aren't protected. So `storage` applies on restart, unlike xRewind's. Changes are copied on the main thread and written by one thread in order, retried while the database is down, so the database never has a later change without an earlier one.
- **One timer.** It's set for whatever is due next (a lease running out, or its owner's warning a day or an hour before) and never waits more than 20 minutes, so lag or a changed clock can't put it far off. A warning due while the owner is offline is sent when they join. Signs are checked once a minute, only in loaded chunks, and rewritten only when what they show changes.
- **Snapshots, not schematics.** Each plot's blocks are saved when it's made, as a palette of block states and an index per block, deflated: a few hundred bytes for a small plot. Saving and putting back run a few milliseconds per tick, after loading chunks in the background. A plot being put back can't be built in or rented until it's done, and one still going at shutdown is finished rather than left half done.
- **Vault without a hard dependency.** The economy is looked up when it's used, since economy plugins often register after xPlots starts. Item currency matches material, and name and custom model data when set.
- **WorldGuard is compiled against 7.0.14**, the newest built for Java 21, with only its API jars: their own dependencies pin a Guava that clashes with newer Paper's.

## Developer APIs ship inside the plugin, and shared code lives in the core (2026-11-17)

Every plugin gets a public API (issue #42; xPlots doesn't have one yet), in `<plugin>/api` on the `xena.api` convention: interfaces, records, enums and events, depending on nothing but paper-api. The plugin shades it into its own jar unrelocated and never minimized, so other plugins find the API classes in the plugin they depend on, and server owners still install one jar. It's published to Maven Central as `co.xenastudios.<plugin>:<plugin>-api`, set up the way NeoSkript publishes `co.xenastudios.neoskript:neoskript-api` (the same Gradle plugin, POM and signing key), by the release tag that releases the plugin. Because an API module can't see the core, an API can't leak core types, which are relocated per plugin and would differ between plugins anyway.

Checked on real servers (`sandbox/api`, used by `sandbox/consumer` and `sandbox/paper-consumer` in CI): on Paper and Folia, 1.21.11 and 26.3, an ordinary `plugin.yml` plugin with `depend` and a Paper plugin with `join-classpath: true` both load the API classes from a paper-plugin and reach it through Bukkit's services manager.

The plan was binary-compatibility checks (japicmp) from the first released API. Instead, as NeoSkript does, each API's public signatures are committed in `<plugin>/api/<plugin>-api.api`, and `check` fails when they change until `apiDump` is run, so a change to an API is always deliberate.

Code two plugins need moves to the core instead of being copied (issue #48). The root build runs PMD's copy-paste detector over every module but the sandbox and fails when a block of about five lines or more is in two modules; repeats inside one module are only reported, and so are repeats only across plugins' APIs, which can't use the core, so the boilerplate every Bukkit event needs repeats there. The first move: the `Toggle` settings every switchable command has, which xUtilities and zChat each defined and xLimbo wrote out by hand, is now `co.xenastudios.core.command.Toggle`, with `CommandSpec.named(name, settings)`.

## Network mode: one change feed in the database (2026-11-17)

xBans, xVote, xMoney and xStats keep what's hot (active bans, balances) in memory, which is only right on one server. On a network sharing one MySQL or MariaDB database, a ban made on one server has to reach the others' memory. `core/db`'s `ChangeFeed` does that for every plugin, instead of each writing its own.

- **A table, not a message broker.** The servers already share the database, so a change is a row in the plugin's `changes` table (topic, a small payload such as a uuid, the server it came from, when). Redis or a proxy channel would be one more thing to run, or would need a player online to carry the message. A plugin publishes in the same transaction as the change itself, so the others never hear of a change that rolled back.
- **Off unless asked for.** A plugin with network support adds `NetworkSettings` as its `network` section, off by default. Off, or on SQLite (one server by definition, and the console is told), publishing does nothing, no table is made and nothing repeats. On, one task off the server's threads checks every `check-every` seconds (3 by default), so a change reaches the others in about that.
- **One index range per check.** Each check reads rows above the newest id it has seen, by the table's key, at most 500 at a time; its own server's rows (a random id per start) are skipped, and subscribers get the rest in order on the feed's thread, hopping to the right thread themselves.
- **Late commits aren't lost.** Ids are handed out on insert, not on commit, so a slow transaction can commit after a newer row was already read. An id skipped over is asked for again on each check for 15 seconds (a rolled-back insert leaves a gap forever, so it isn't waited on longer), and a jump of over 1,000 ids isn't waited on at all.
- **Changes from before a start aren't replayed.** A starting server reads its tables anyway; it starts from the newest row.
- **Pruned to ten minutes, never empty.** Once a minute each server deletes rows older than ten minutes below the newest it has seen, by key range. The newest row always stays, so an old MySQL that forgets its counter on restart can't hand out an id again.
- **A server that may have missed changes reads again.** A feed is only as good as the server's memory of what it read, so `onResync` tells a plugin to reload what it keeps in memory from its tables whenever that can't be trusted: when checks start working after failing, when none worked for five minutes (rows it never saw may be pruned), and after a jump in ids too big to wait for. Found reviewing xBans (#63): without it, a server cut off from MySQL for more than ten minutes kept enforcing lifted bans and missed new ones until a restart.

It's tested on SQLite with two feeds sharing a file (`ChangeFeedTest`, including late and never-committed rows and pruning), and against a real MariaDB when `XR_MYSQL` is set (`ChangeFeedMySqlTest`, as xRewind's), which CI runs.

## Chat pages, offline players, warmups and Vault move to the core (2026-11-17)

Each of these has at least two users among the plugins being built (#48's table), so each is in the core before the second one is written.

- **`text/ChatPages`**: a list a page at a time, from memory or a page already read from a database with its total, and a footer players click. The footer's `<next>` and `<previous>` are filled in as pre-processed tags, because inside a `<click>` an ordinary placeholder isn't filled in at all: xRewind's "Next page" ran `<next>` until it moved onto this. `<has_next>` and `<has_previous>` hide a link when there's no such page. `Tasks.sender` sends a reply on the player's thread, or the global one for the console, for lists read off the server's threads.
- **`player/Profiles`**: a name to a uuid and back for players who may be offline, never blocking. What's in memory (online players, its own 2,000 answers, the server's user cache) answers at once with a completed future; the player's saved data and Paper's profile lookup run off the server's threads. Two lookups of one player share one, and a name Mojang doesn't know isn't asked about for ten minutes, so typos can't use up its rate limit.
- **`player/Warmups`**: from xPlots. A short task on the entity's own scheduler checks four times a second for moving half a block, so it's Folia-safe though xPlots isn't, and costs nothing for anyone not waiting. Damage cancelling needs a listener, so one is registered only while a warmup that damage cancels is running. The countdown can show on the action bar. It works on any entity, which is how the sandbox checks it on real Paper and Folia servers with a pig.
- **`hook/VaultEconomy`**: from xPlots. The class plugins use never names a Vault type, and the one that does is only loaded once Vault is enabled, so a server without Vault never sees a `NoClassDefFoundError` (the sandbox checks this on servers without Vault). The economy is looked up each time, as before.

xPlots keeps its own `Wallet` (an economy or an item) and its teleport messages and bypass permission; only the general parts moved. Its jar grew about 8 KiB, mostly the warmup's damage and countdown options that xTeleport uses.

## xTeleport: one path for every teleport, and RTP that can't lag (2026-11-18)

xTeleport (#35) is homes, TPA, warps, spawn and `/rtp`, on Paper and Folia.

- **Every teleport takes one path** (`teleport/Teleporter`), its own commands' and the API's alike: cooldown and cost checked, the core's warmup, the destination worked out (another player's spot is read on their thread only now), its chunk loaded with `getChunkAtAsync` and the spot checked on the thread that owns it, `PreTeleportEvent`, the cost taken, then `teleportAsync` with the `COMMAND` cause, which xUtilities' `/back` already records. A teleport that fails or throws after paying is refunded. The event fires after the warmup and the check, so a plugin sees the real destination; a combat-tag plugin's refusal comes three seconds late, which is the price.
- **Safe arrival is about what's there now.** Inside the world border, nothing harmful at the feet or head, neither inside a full block, and ground that isn't harmful at most `teleports.max-fall` (3) blocks down, or water at any depth. A ladder, vine or scaffolding counts as ground. Homes, warps, spawn and TPA are all checked: a `/tpahere` from the End's void or a lava pool would otherwise trap the player who accepts. RTP spots are checked when found. Checks use `Material` (solid, a liquid set) rather than `Block#isPassable`, which is cheaper and works in MockBukkit.
- **Whoever asks pays.** For `/tpahere` the player who accepts moves (and has the warmup), but the cost and the cooldown are the asker's, as with `/tpa`.
- **Asking twice doesn't notify twice.** A request already waiting from the same sender is kept, and the sender is told they already asked, so nobody can be spammed with `/tpa`.
- **Requests run out when read.** Each player's inbox is a list replaced whole on each change; anything older than `tpa.expire-after` is dropped whenever it's read or added to. No timer. Requests from a player who left are skipped when answered.
- **One database thread, in order.** The store opens the database on its own thread and runs every read and write there after it, so a home read after it was set is always there and a slow MySQL never holds up startup. Commands say "not available" until it's open (milliseconds on SQLite). Online players' homes are read on join and kept until they quit; staff reading an offline player's homes go to the database. Every place has a `server` column, empty for now, so cross-server homes can come without a migration. `storage` applies on restart, as in xPlots.
- **A change is only reported once it's saved.** Setting or deleting a home, warp or the spawn, and `/tptoggle`, change memory at once (so a second `/sethome` sees the first against the limit), then reply when the write completes. A write that fails is undone in memory, unless something changed it since, and the player is told to try again; API futures complete exceptionally. Once a write succeeds, memory is changed again: a read of that player already running when the change was made (as they join) was queued ahead of the write and stores older data, and the store's one thread guarantees that read is stored before the write completes. Retrying failed writes is left for later, in the core.
- **RTP: one chunk at a time.** A candidate is a point spread evenly over the ring's area, inside the world border (and off the End's main island, within 1,000 blocks of 0,0, unless allowed). Its chunk loads with `getChunkAtAsync`; for `only-generated` that's `getChunkAtAsync(x, z, false)`, which completes with null for a chunk never generated, rather than `isChunkGenerated`, which can read the disk on the calling thread. The column is read on the chunk's own thread. At most `attempts` candidates, one search per player, and `max-searches` at once server-wide (over it, players are told to try again; a queue would make them wait without knowing). Blocked biomes are looked up in the registry once per config.
- **Two RTP cooldowns.** Each search starts `rtp.search-cooldown` (30 seconds), found or not, so an unlucky search, or a warmup cancelled by moving, can't be repeated straight away to keep the server generating chunks and fill the global cap. The command's own cooldown (5 minutes) starts on arrival, like every other command's.
- **Other worlds' borders and spawns, on Folia.** `/rtp world_nether` typed in the overworld reads the Nether's spawn point and border from the player's region. Folia ties neither to a region: on 1.21.11 and 26.3, `CraftWorld#getSpawnLocation` and `CraftWorldBorder`'s getters read a few plain values with no thread check, so this is safe without hopping to the global region.
- **`/xteleport rtpcheck`** runs real searches without a player, so the boot checks exercise the search on Paper and Folia, 1.21.11 and 26.3, and owners can see how often a world's settings find a spot.
- **The bed home uses `getPotentialRespawnLocation`.** It's deprecated (since 1.21.5, not for removal) for a method that loads the chunk on the calling thread to validate the bed, which is what must not happen. The block is read after the warmup, once its chunk has loaded in the background, to stand on top of it.
- **Spawn without a teleport.** New (or every) joining players are placed with `AsyncPlayerSpawnLocationEvent`, reading the spawn from memory, so there's no teleport after joining. Respawning at spawn is for deaths only: leaving the End goes where the game sends it.
- **Tests drive real teleports.** MockBukkit can't `getChunkAtAsync` or `teleportAsync`, so both go through two plugin methods (`loadChunk`, `move`) that the tests' subclass does synchronously, and its store's writes can be made to fail. MockBukkit can't cancel an entity's scheduled task yet, so players who wait out a warmup in the tests have a small scheduler of their own. Everything else is the real code.
- **Imports: EssentialsX only in 1.0.** Its userdata, warps and spawn files are plain YAML in a known layout. HuskHomes and CMI keep their data in databases whose layout couldn't be checked against a real install here, and a wrong guess would lose homes quietly, so they wait for a version that can be tested against one. An import keeps what's already in xTeleport (insert-or-ignore), so running it twice is safe.

## xVote: a receiver of our own, and votes taken before they're paid (2026-11-18)

xVote receives votes itself instead of depending on NuVotifier, which hasn't had a release since 2021 and which nearly every voting plugin needs beside it.

- **NuVotifier's protocols, byte for byte, without Netty.** The greeting, v1's 256-byte RSA block (PKCS#1 v1.5, a 2048-bit key) and v2's signed JSON (HMAC-SHA256 of the payload with the list's token, the greeting's challenge inside, 0x733A and a length in front), and the same error replies. Keys stay in `rsa/` as NuVotifier writes them and tokens in a `tokens.yml` with its `tokens:` section, so a NuVotifier folder is taken over on the first start and lists never change. Tokens are kept out of `config.yml`, which owners paste when asking for help. They're read with a path separator no name has, because Bukkit splits keys on dots and `MinecraftServers.org` would become two sections (NuVotifier itself trips on this). The tests use a key, a v1 block and an HMAC made with openssl, plus votes built exactly as NuVotifier's own client builds them, so the same mistake can't sit on both sides.
- **One platform thread accepts, each connection gets a virtual thread,** under a hard cap (more are closed at once, 256 by default since virtual threads are cheap) and a cap per address (4), with 3 seconds for the first bytes and a deadline for the whole conversation rather than per read, so a byte at a time can't hold a slot, and a limit per address per minute checked before anything is read or decrypted. IPv6 counts by its /64. Behind a tunnel every list shares one address, so both limits per address can be raised or set to 0. A failed accept is retried after a pause growing to a second; only closing ends the loop. Logging has two budgets: a list's mistakes once per list, up to 100 (a bad signature counts per service only for a service with a token of its own; a v1 block that won't decrypt, an unknown service and a bad signature on the default token share one warning each, since a scanner or a made-up name can send them); everything else once per kind, without the address or names it carried, so scanners can't fill the log or use up the first budget. Network text loses its control characters as the vote is made, so it can't fake log lines, and a site that isn't listed reaches console commands with only `[A-Za-z0-9._-]`. JSON is Paper's Gson; nothing is shaded in.
- **A vote is taken before it's paid.** Every vote is a row; paying one starts with `UPDATE ... SET claim = ? WHERE claim IS NULL` in the database, so two servers sharing it can't both pay a vote, however they race (tested with two servers on one SQLite file, and on MariaDB with the real change feed). A crash between taking and paying loses that reward rather than paying it twice; a player who leaves before the reward reaches their thread gives the vote back, and so does a normal stop for every vote taken but not yet paid (each is either paid or given back, by one atomic remove from this run's list). The vote's place in the player's count, streak and first-of-the-day are stored when it's matched to a player, so whichever server pays it pays the same.
- **Names wait.** Lists send names, not uuids. A name is matched from memory only (online, voted before, or the server's user cache), never by asking Mojang, because a name that never joined may be a typo or a Bedrock player; it waits, and the first player with that name to join gets it. On a network, the change feed's news of a vote lets the server where that name is online match it.
- **Totals keep their period's key** (the day, week and month they were counted in), so nothing resets them at midnight and no task runs. Leaderboards are sorted again only on the first question after a vote; a voter read again unchanged (a join) doesn't count as one.
- **First of the day comes from the locked `voters` row** (`last_day`), not a count of the day's votes: on MySQL a plain read sees the transaction's snapshot, taken before the row lock, and could miss a vote another server just counted. Only a vote counted late, for a day before `last_day`, counts that day's votes. (MariaDB 11.6+ refuses such a stale locking read anyway, and the job runs again.)
- **The receiver starts off the server's threads,** since it reads key files and may make a key, one change at a time, and never binds after the plugin is disabled.
- **The jar is about 317 KiB:** the receiver, the ledger and its network claims, rewards, commands and the API. Its budget is 350.

## xBans: what's in force in memory, history append-only (2026-11-18)

xBans (#41) is LiteBans' commands on the family's core. Staff trust a ban plugin only if nothing gets round it, so most choices are about that.

- **Every ban and mute in force is in memory**, read off the server's threads when the database opens: a small set even on a big server. The join check is a couple of map lookups, with no database query, and keeps working if MySQL drops for a moment. Mutes are checked the same way on every chat message and command. Expiry is checked when read, so nothing runs on a timer.
- **Fail closed.** A login just after a start waits up to 10 seconds for the bans to load, off the server's threads, then is turned away with a "still starting" screen. A database that can't be opened at startup is tried again every 15 seconds until it opens (the only other repeating task, and only while it's broken); until then nobody joins. Letting everyone in while the database is down would let banned players in too.
- **Three checks.** At pre-login (the main one), when the connection finishes configuring (`PlayerConnectionValidateLoginEvent`), and at join. A ban is put in memory before anyone is kicked for it, and a player is in the online list before their join event, so a ban made at any moment of someone's connection is caught by one of the checks or by the kick.
- **Mutes block commands by what they are, not what was typed.** A muted player's command is looked up in the command map, so an alias (`/emsg`) or a namespace (`/essentials:msg`) of a blocked command is blocked too. Only a muted player's commands are looked up. The older chat events (`AsyncPlayerChatEvent`, `PlayerChatEvent`) fire in full before Paper's `AsyncChatEvent`, so a chat formatter or Discord bridge on them would relay a muted player; xBans cancels them too, first and again last. Paper fires them only while something listens. xBans always listens to the asynchronous one, which costs one event per message off the server's threads. A listener on the synchronous one moves every chat message onto the main thread, so xBans guards that one only while another plugin listens to it, and each message's asynchronous event checks whether one does. Checking only as plugins enabled missed listeners added later (Skript's scripts, a Discord bridge once it connects). Paper fires the synchronous event after the asynchronous one and reads its listeners when it does, so the guard is in place for that same message.
- **Append-only.** `punishments` rows are never changed. An unban is a row in `removals`, keyed by the punishment, so two servers can't revoke one twice. A replaced ban is revoked with a fixed reason, and still counts toward its template's ladder. The only delete is `/prunehistory`, which staff ask for and confirm. Two replacements at once can't leave two in force: the revocation is an `INSERT IGNORE`, and if it finds the old one already revoked, the new one isn't stored, the old one is dropped from memory (another server may have revoked it before its change arrived), and the command decides again.
- **Replacing follows who may lift.** A new ban or mute replaces an old one on the same scope only if it reaches everyone the old one did, ends no sooner, and its sender could `/unban` the old one (gave it, has at least its giver's weight, or has `xbans.unban.override`; anyone, with weights off). Otherwise it's refused if the old one already reaches everyone for at least as long, and both stay if not. Without the third rule, a helper who can't lift the console's one-day ban could replace it with a two-day one of their own and lift that. The replacement check comes first, so an equal permanent ban replaces (a reason can be changed) instead of being refused as covered. The cases, each with a test (`ReplacingTest`, and on a server in `XBansTest`):

  | Case | What happens |
  | --- | --- |
  | Same length (permanent twice, or ending together) | Replaced: the new reason stands. |
  | Longer | Replaced. |
  | Shorter | Refused: "already banned until …, unban them first to shorten it". |
  | IP ban over the same account's ban | Replaced if it lasts as long: it reaches the account too. Shorter: both stay. |
  | Account ban over an IP ban | Never replaced (the IP's other accounts would get back in). Refused if the IP ban lasts as long; otherwise both stay. |
  | A senior's (or the console's), by a junior | Never replaced. As long or shorter: refused with "given by someone who outranks you", not advice to unban that they can't follow. Longer: both stay, and the junior's unban lifts only their own. |
  | Mute and ban | Kept apart: a mute never replaces or blocks a ban, nor a ban a mute. |
- **History pages by key range.** Each viewer's list remembers where each page it showed ended, so the next page is one index range below the last id shown: as quick on page 300 as on page 1, and steady while new punishments arrive. A page jumped to directly finds its start from the index.
- **IP keys.** An address is stored as written, or with `ips.hash` as an HMAC-SHA256 with a salt kept in `ip-salt.txt` beside the config, never in the database, so a stolen database can't be brute-forced back to addresses (all of IPv4 would take seconds against a known salt). The database records a check of the salt, so a network server with a different one says so. Turning hashing on hashes what's stored; it can't be undone. Loopback addresses are never stored or banned: behind a proxy without forwarding, every player seems to come from one, and an IP ban on it would ban everyone. A hashed database opens only with the salt it was hashed with: if `ip-salt.txt` is missing or its check doesn't match, xBans doesn't make a new one and the database doesn't open (retried every 15 seconds, so nobody joins), since with the wrong salt no IP ban would match anyone. For a salt lost for good there's a way out, named in that console message: an empty `reset-ip-salt.txt` in xBans' folder makes the next start adopt the salt that's there (or a new one) and delete the file. A file rather than a config option, so it can't be left on and quietly reset a network that later gets one wrong salt. An IP punishment with no account is named after half its address (`203.0.x.x`) or the start of its hash, because that name is what the broadcast everyone sees shows; turning hashing on renames those too, and rewrites where an imported vanilla IP ban came from (`vanilla:ip:<key>:<date>`, by the key, never the address).
- **Turning hashing on is one transaction.** The addresses, the names, the import records, the `ip-mode` row and the salt check commit together, so a crash midway leaves the database as it was. Otherwise the next start would hash the hashes, and every IP ban and alt would be lost. The switch is claimed first, with an insert-if-absent of the salt check: of several servers starting at once on a database that isn't hashed yet, one hashes, and the others find its check, see their salt differs, and wait for it to be copied across. On MySQL the second insert waits for the first transaction's lock, so it can't slip in between.
- **Weights from permissions, remembered.** `xbans.weight.<n>` is read from a player's effective permissions (so operators get none unless given), and recorded at each join, so an offline player is held to the weight they had. Limit-group permissions default to false, so an operator isn't held to a helper's cap.
- **Templates are held to staff limits.** A template's ladder ends in a permanent ban, so letting templates past a helper's cap would let a helper reach permanent by repeating `/ban Steve hacking`. Each template has its own permission (`xbans.template.<name>`, operators by default), and `xbans.limit.bypass-templates` is there for servers that want helpers to use a template's own durations.
- **An IP punishment is held to everyone on the IP.** It reaches every account that joins from it, so the accounts seen on it (the `ips` and `players` tables) and those online on it now are each checked for `xbans.exempt` and weight, as the target is. Otherwise `/ipban <the owner's address>` would lock the owner out.
- **Unbans follow weights.** The weight of whoever gave a punishment is stored with it (the console's, plugins' and imports' as the highest), and lifting it needs at least that weight, or to have given it, or `xbans.unban.override`. It's LiteBans' `unban.own` idea, by weight instead of a yes or no. Only while `staff-limits.weights` is on. Imports count as the console's because their staff's weights aren't known: whoever gave one can still lift it, and so can `xbans.unban.override`.
- **Network mode on the core's change feed.** A punishment publishes its id in the same transaction; other servers read the row and apply it as if made there (memory, kicks, broadcast). Imports publish "quietly", so a thousand imported bans aren't a thousand broadcasts. The feed starts before the bans load, so a change made meanwhile is in both (memory ignores the second copy). A change whose punishment can't be read is tried twice more, then everything in force is read again and memory brought in line with it, leaving alone whatever changed while it was read; any ban found that way kicks its players. One reload runs at a time: those asked for while it runs become one more after it. A reload that fails is tried again every 15 seconds until one works (a one-shot delay each time, only while failing). While one is due, changes aren't retried one by one, and while one is waiting to retry they aren't read at all, since it reads them anyway. Otherwise 500 changes during an outage would hold the feed's thread for ten minutes of sleeps and start 500 full reloads. Changes to memory (adding, removing, a reload finishing) take one lock, so a reload can't drop a ban added as it finishes, or bring back one revoked as it finishes. Reads take no lock. The same reload runs whenever the core feed says it may have missed changes (`ChangeFeed.onResync`: after its checks failed for a while, or rows were deleted before it saw them). `/unban` and the rest read what's in force from the database, not memory, so a server that missed a ban can still lift it.
- **LiteBans from MySQL, not H2.** Paper ships no H2 driver, and H2's file format changed between 1.4 and 2.x, so reading LiteBans' default H2 file would mean fetching the right driver at runtime. LiteBans' own import moves H2 to MySQL, so the docs send owners that way first.

## xBackup: a content-addressed store, read twice, restored on start (2026-11-18)

xBackup (#23) keeps backups in a small restic-like repository it writes itself: every blob named by its SHA-256, grouped into immutable packs (data and structure in separate packs), index files saying which pack holds which blob, and one text file per snapshot, written last. Nothing is changed in place: a backup writes packs, then their index, then its snapshot, each flushed before the next, so a crash leaves at worst unreferenced packs for garbage collection. Every pack ends with a footer listing its blobs, so the index can always be rebuilt from the packs. Proven by `CrashTest` (operations killed at random writes with no clean-up allowed, 160 rounds) and `KillTest` (a second JVM SIGKILLed mid-backup).

- **Region files chunk by chunk.** Each chunk's record (length, compression byte, payload) is its own blob, and a region's layout (where each chunk sits, its timestamp, its blob) is another. A chunk whose location and timestamp are unchanged is reused from 8 bytes of header. That's safe because the server writes a moved chunk to new sectors before pointing the header at them and never writes into sectors the header points at, so a chunk read between two identical header reads is consistent. A header that doesn't add up is kept as a whole file. Restores put every record back at its offset with zeroed padding: Minecraft reads the same file, and a real 26.3 round trip matched 1,611 of 1,612 chunks byte for byte (the other was written after the backup).
- **Read twice.** M0 settled the pause: `setAutoSave(false)` stops all world writes, `World#save(true)` flushes (per region on its own thread on Folia; from the global thread it throws or silently saves nothing). The worlds are read first with the server saving as usual, then, during the pause, only what changed since. Autosave is off for under a second even on a first backup. Worlds whose owner turned autosave off are neither flushed nor turned on. The worlds actually turned off are remembered under one lock with a "still wanted" flag, and every end (finally, the watchdog, disable) turns exactly those back on, so a late main-thread step can never leave autosave off. On Paper, xBackup's main-thread steps go through the core's `Tasks.nextTick`, which uses the Bukkit scheduler there, not the global region scheduler: with nobody online Paper pauses after `pause-when-empty-seconds`, and its paused tick runs `CraftScheduler#mainThreadHeartbeat` but skips `tickChildren`, where the global region scheduler ticks (read from 1.21.11's and 26.3's `MinecraftServer#tickServer`, and seen on a real server: global-region tasks waited until someone joined). Folia doesn't pause when empty.
- **SQLite by SQLite.** The plan had family plugins pause their writers for a "quiet moment" through the core. Instead, any SQLite file is copied with `VACUUM INTO` through Paper's driver: one consistent read transaction, no cooperation needed, and nothing added to the core. A database that can't be copied that way keeps its last good copy; its raw bytes are never copied. The API's `QuietMoment` remains for plugins with multi-step flat files.
- **The index is a table of parallel arrays**, about 65 bytes a blob, held only while a job runs. Garbage collection marks with a map of 8-byte prefixes (a clash keeps garbage, never deletes data), runs at most daily, and repacks mostly-dead packs: new packs and a fresh index are written before any old file is deleted.
- **Restores swap from the bootstrap, all or nothing.** Staged files are checked against their hashes, then a journal drives the swap on the next start (or straight away from the command line), each step repeatable, so a crash part way is finished next time. Every staged copy is checked before anything moves. A step that fails moves everything back, including what an earlier run cut off by a crash had put in place (every entry journaled as set aside or done), and keeps the journal as `restore/failed`, so a later start never swaps it in by surprise; if moving back fails too, the bootstrap halts the server rather than let it load or generate a half-swapped world. Restores write only inside their folder, through no links, and refuse links leading outside the server folder. The command line refuses while xBackup's `running.lock` (OS-locked from bootstrap until the process exits, since Paper saves worlds after plugins disable) or any world's `session.lock` is held, looking in the restored folders, a few folders deep, and `bukkit.yml`'s `world-container`. An in-place restore takes `running.lock` itself for its whole run and checks the `session.lock`s again just before it swaps; a bootstrap that finds `running.lock` taken halts the server, since staging can take hours. Paths are resolved from the working directory, which is the server folder.
- **One job at a time** on one low-priority worker thread, with an OS file lock on the repository so the command line and the server never write at once. The only timer is the schedule, set again after each backup; checks and clean-ups ride along.
- **Remotes are mirrors.** Packs are immutable, so a backend only needs put, get, list and delete; copies send what's missing (packs, then indexes, then snapshots) and refuse a remote holding a different repository. A copy deletes from the remote only snapshots the repository removed on purpose (noted in a local `forgotten` file, never copied) and older than its newest, and only packs garbage collection deleted on purpose (noted in `collected` before they go), when every snapshot left on the remote is also local. "Not in the local index" never means "unused": a pack that went missing here is noted in `lost`, which a copy never deletes, and the remote keeps its own index files while it keeps such a pack. GC drops missing packs before marking and takes back unindexed packs holding needed blobs. `/backup copy <remote> tidy` is the owner's way to remove what only the remote has, after a confirmation. Local damage, a rolled-back disk, or an empty repository deletes nothing. S3 is SigV4 by hand on `java.net.http` (checked against AWS's published example); WebDAV and the drives are plain REST with a small JSON reader, because the command-line restore has no Gson.
- **Remote secrets live in `secrets.yml`, not `config.yml`.** Owners share their config for help, and xBackup backs it up and copies it to every remote. Passwords and client secrets go in an owner-only `secrets.yml`, which is never backed up, nor are SFTP keys, tokens and the command line's settings file. The command line reads `secrets.yml` itself (a small two-level YAML reader, since it has no SnakeYAML) rather than keeping a copy of the passwords, and drive tokens live in an owner-only `tokens.yml`. S3 uploads still send `Content-MD5`: buckets with Object Lock require it, and it's only a check against damage in transit. Any found in `config.yml` are moved there each time the config loads, before its first load at startup.
- **SFTP and FTP libraries are fetched by xBackup, not Paper's library loader.** The issue planned Paper's loader. It resolves only at startup, so a remote added on reload would need a restart, and the command-line restore has no Paper at all. xBackup downloads JSch or Commons Net (one dependency-free jar each, Google's mirror of Maven Central first, then Maven Central) only when a remote of that type is used, checks a pinned SHA-256 (`LibrariesTest` fails if the catalog version moves without it), and loads the code that uses it through its own class loader: xBackup's `remote.lib` classes only from xBackup's jar, the library's only from its jar.

## Global work survives an empty server's pause (2026-11-18)

Paper pauses a server that has been empty for `pause-when-empty-seconds` (a vanilla setting, 60 by default). While paused it still runs console commands and Bukkit's scheduler, but not the global region scheduler, which Paper ticks with the worlds. So anything a plugin queued there waited for the next player: the core's own `/<plugin> reload` queued the reload itself there (to run after the command), so a reload typed in an empty server's console did nothing until someone joined. Found by xBackup (#61), whose scheduled backups timed out on empty servers, and reproduced with xUtilities 2.0.2 on Paper 1.21.11 and 26.3 with `pause-when-empty-seconds=1`.

`Tasks.global` and the new `Tasks.nextTick` use Bukkit's scheduler on Paper and the global region scheduler on Folia, which never pauses. The core's reload and `editConfig` use `nextTick`. With the fix, the same test logs the reload six seconds after the pause. Where plugins called `Bukkit.getGlobalRegionScheduler()` directly, xRewind's rollback applier (on Paper) and xLimbo's world sync and API moved to Bukkit's scheduler in their next releases, xRewind 1.1.0 and xLimbo 2.1.0 (#69). xLimbo's three repeating ticks stay: they only act on online players, and a paused server has none.

## xMoney: the economy stands in for Vault, and memory is the truth (2026-11-18)

xMoney (#22) is an economy plugin that is also Vault, on Paper and Folia.

- **It provides Vault rather than running beside it.** Spike M0 (63 boots, six approaches) found one jar can't both stand in for Vault and coexist with it. xMoney is a paper-plugin with `provides: [Vault]` and ships VaultUnlockedAPI 2.20 (Vault 1's `net.milkbowl.vault` and VaultUnlocked 2's `net.milkbowl.vault2`) unrelocated, unmodified and unminimized. Paper always loads it first and refuses a real Vault or VaultUnlocked jar as a duplicate, with an ERROR it can't be stopped from logging; xMoney adds one warning naming the jar, and never refuses to start (Paper has already refused Vault, so refusing too would leave no economy at all). Both APIs are LGPL-3.0; the jar carries the LGPL and GPL texts and a notice in `META-INF/licenses/`.
- **What real Vault did that xMoney now does.** LuckPerms (`loadbefore: [Vault]`) registers its Vault permission and chat hooks through xMoney, checked on Paper. Real Vault also registered a SuperPerms Permission provider when no permissions plugin did; xMoney registers its own (online players' Bukkit permissions, no groups) at the lowest priority. Lost: Vault's `/vault-info` and `/vault-convert`; `/xmoney import vault` does the converting.
- **The core's `VaultEconomy` needs no change.** `isPluginEnabled("Vault")` finds xMoney through the provided name, and a Paper plugin's optional `Vault` dependency with `join-classpath` sees xMoney's API classes: `hook-consumer` charges through it in every CI boot. So xPlots and xTeleport work with xMoney as they are.
- **Amounts are longs of ten-thousandths**, whatever the configured decimals (0 to 4), so changing decimals never rescales what's stored. The decimals are only for showing amounts and for typed command input (rounded half up). Vault and API amounts keep all four places, so 0.995 then 0.005 takes exactly 1.00 and, with 0 decimals, 0.4 takes 0.4 (rounding each to the decimals took 1.01, and nothing). Past four places, deposits and sets round down and withdrawals, transfers and `has` round up, so rounding never makes money and a positive withdrawal never succeeds for nothing. A Vault 1 double is first read to 15 significant digits, which a double always holds, so 0.1 + 0.2 isn't charged as 0.3001; that's only done below ten billion, where the 15th digit is finer than a unit, so it clears noise of under a twentieth of a unit. Above, 15 digits are coarser than units (half even, 123456789012.34567 paid in as ...012.3460), so the double's own digits are rounded the safe way instead. Rounding at 15 digits down for deposits and up for withdrawals, as the review suggested, would charge 0.1 + 0.2 as 0.3001 and pay 4.35 × 100 in as 434.9999. Balances go back to plugins with every place they have (`12.50`, `0.995`). NaN, infinities, negatives and anything over 100 trillion are refused.
- **On one server, memory is the truth.** Every account is loaded while the server starts, before any plugin can ask, so no Vault call ever touches the database. A change is checked and applied under the account's own lock (a transfer takes both, in uuid order) and queued for one writer thread before the lock is let go, so the ledger's order is the order of changes. (The issue says compare-and-set; a lock held for nanoseconds gives the same guarantee and keeps the queue in order.) The writer puts whatever is waiting in one transaction: each balance as a `+ delta` update and its ledger row together, so a crash never leaves them disagreeing. It commits as soon as there's work, with no timer. The first ledger row of each transaction carries a random `commit_id`, so a retry after a commit whose answer was lost finds it and isn't applied twice.
- **On a network, the database decides what takes money, and network mode is experimental in 1.0.** Withdrawals, transfers and sets are `UPDATE ... WHERE balance >= ?` on the writer, and the caller's future completes once that's committed (a millisecond or two on a LAN). Each is queued, then either started by the writer or abandoned by its caller, by compare-and-set, never both: an abandoned one never runs, so refusing it is true. A Vault call on a server thread waits at most `network-wait-ms` (50 by default, never above 250) for the writer to start it; elsewhere it's 5 seconds, which the writer also checks before starting one. While the writer is failing they're refused at once. Once started, the caller waits for the real outcome: a transaction that fails before its commit was sent is reported as failed (it rolled back), and so is one that hasn't reached its commit within a second of starting (rolled back, checked before each statement), so before the commit a caller waits about 4 seconds at most. Only a commit whose answer was lost is looked up by `commit_id` before answering, with a locking read (`LOCK IN SHARE MODE`): a commit MySQL is still making (an fsync stall, semi-sync replication) holds the row it inserted, so the check waits for it instead of reporting "failed" just before the money is taken. The API's and commands' futures have a timer, so an unstarted change is answered within 5 seconds even if nobody waits with a timeout. The writer's MySQL connections in network mode come from their own `Database` with `connectTimeout` and `socketTimeout` of 3 seconds in its properties (appended after the owner's, so they win), so the handshake of a reconnect is bounded too, not #62's five minutes; retries are at most 2 seconds apart. The core has no way to open a connection with extra properties, so xMoney opens a second `Database` (a core candidate). **If the database dies at the moment a withdrawal commits, the calling thread waits until the database answers again; on the main thread that can freeze the server, which is why network mode is experimental; leases (#66) would remove the case.** Automatic refunds were considered and rejected: a refund after "failed" is a second change that can itself fail, and "told failed, never charged" is the rule. A writer failing with nothing left to save (a withdrawal that failed is answered and gone) checks the database once a second, or it would refuse withdrawals for good; a connection idle for 30 seconds is checked before it's used, since MySQL's `wait_timeout` closes it. Prunes, re-reads and resyncs never hold up saving: a failed prune is dropped until the next day's, and a re-read that fails twice becomes one resync once saving works. Stopping answers a started change whose commit wasn't sent as refused, and one whose commit was sent with an error, never a refusal; a lock around sending the commit makes sure a refused one is never sent after. The alternative considered, per-account leases (a `leases(uuid, server, until)` row taken at async pre-login, so the server a player is on decides their withdrawals in memory), was designed in #66 but isn't planned for a release. Deadlocks (two servers' transactions on the same rows) are retried at once; rows are changed in uuid order (in a batch of saved changes: account rows, then one balance change per account, then the ledger rows in the order the changes happened, each with its balance after worked back from the database's), and new account and balance rows are single upserts, since an update that finds no row takes a gap lock on InnoDB and two servers' first deposits deadlocked. A burst of thousands of deposits is one long transaction that a withdrawal waits behind; that's documented rather than split, since the queue is in order either way. Deposits can't overspend, so they're applied in memory at once and kept as "pending" until saved. Every write reads the balance back and sets memory to it plus this server's pending changes, and publishes the account on the core's change feed, so the other servers do the same within `check-every`. `max-balance` is checked against memory there, so it's a soft limit. The first server to make a player's account gives the starting balance (`INSERT IGNORE`).
- **Events never hold up saving.** `PreTransactionEvent` fires on the caller's thread before the lock; `BalanceChangedEvent` fires after the commit, on a thread of its own made the first time something listens, never the writer's (a handler that withdrew on a network would otherwise wait for itself).
- **Vault 1 calls don't say who's calling**, so the ledger reads it off the stack: the first frame from another plugin's class loader, cached per class. Payments only; balance checks don't walk the stack.
- **Name-based Vault calls** (Towny's `town-Foo`) find the account by that name, a player the server has cached by it, or make one that isn't a player's, keyed by a uuid made from the name. Accounts made for version-2 uuids (Citizens' NPCs), through Vault or the API, aren't players' either. Neither is in `/baltop`.
- **A name finds one account or none.** A player joining always takes their name, even unchanged, and any other account that had it loses it, in memory and in the database (its name is emptied, and it shows the start of its uuid), so the name can't be ambiguous again after a restart. Two stored accounts with one name (from two servers at once) leave it out of the index at load; Vault's name-based calls then ask the server's player cache (`getOfflinePlayerIfCached`, never the disk or the web) and are refused if it doesn't know, and `/pay` and `/eco` ask the core's `Profiles`. Plugins can't rename an account to a name another has, and accounts made by uuid (imports, plugins paying a player who hasn't joined) never get a name another account has. Names ignore case, so on an offline-mode server `Steve` and `steve` (two uuids) share one: whoever joined last has it.
- **Imports are dry runs until confirmed**, and set balances through the ledger as `IMPORT`, so the balance before is in the history. If any of the accounts changed in xMoney since (any ledger row but a start or an import), the dry run says how many and the import needs `confirm overwrite`. Negative balances come in as 0, not as a missing line that would leave a starting balance. On a network an import is one writer op that sets up to 100 balances per transaction, in uuid order, stopping early after 20 ms, and goes to the back of the queue after each, so payments go between chunks; it waits for a database that's away rather than dropping lines, and publishes one `accounts` change at the end, which makes the other servers read every balance again (the same as the change feed's `onResync`, #64). EssentialsX userdata is read by xMoney's own line scanner for three top-level keys, not shared with xTeleport's YAML reader yet (a core candidate once a third importer needs it). CMI's SQLite is read by column names, since its layout couldn't be checked against a real install. `import vault` asks the other economy on the main thread, a few milliseconds a tick, scheduled through the core's `Tasks` (since #67 Paper's global region scheduler stops while an empty server is paused, so an import from an empty server's console would have waited for a player); the list of players who have played is read off the server's threads.
- **One repeating task**, while `ledger.keep-days` is above 0: a minute after start and then daily, ledger rows older than that are deleted in slices of 5,000 ids between other writes. Each slice starts from the oldest row through the primary key and stops at the first row newer than the cutoff (rows are written in time order), so a slice costs the same however big the ledger is; finding the range through the time index, as at first, grew with the square of the backlog and could time out for good on a network.
- **CI boots xMoney on its own.** With it in the shared boot, every plugin would see Vault and the sandbox's check of the core's hook without Vault would fail. It boots with its two test plugins, then again beside a real VaultUnlocked jar (pinned by sha256). That run's checks file uses `boot-test.sh`'s new `allow:` step for Paper's duplicate-plugin ERROR and xMoney's warning: lines with that text don't fail the run, and the text must appear. No other run allows anything.
- **Tests:** 16 threads paying each other conserve every unit and the database matches memory and its own ledger; a JVM SIGKILLed mid-write, three times over on one file, leaves balances exactly their ledger rows and the total unchanged; two ledgers on one SQLite file in network mode, and two on MariaDB with the real change feed, never overspend. A connection wrapper makes the writer's database go away, lose a commit's answer, or fail one statement on cue: a withdrawal queued behind a failing write is refused and never taken once the database is back, a lost commit is reported as done and applied once, an import waits out an outage, an outage with only a withdrawal in it recovers, a change too slow to reach its commit is refused and rolled back, and stopping answers a started change. On MariaDB, the lost-commit check waits for a commit another connection is still making, and the writer's connections wait 3 seconds whatever the owner set.

## xStats: counters read on each player's thread, leaderboards in memory, a website on the JDK's server (2026-11-18)

xStats (issue #47) gives players their stats, everyone leaderboards, and owners a website their server hosts itself. Paper and Folia.

- **Minecraft already counts; xStats reads.** One save task, every five minutes, asks each online player's own entity scheduler for a reading, four players a tick, so a full server is never read in one tick. A reading is the server's own counters (`Player#getStatistic`, a map lookup), the camera's direction, and any placeholder stats: no listener for kills, blocks or movement. Joins and quits are the only events. The readings go to xStats' one thread, which owns every number in memory and does all database work, so nothing needs a lock and no game thread waits on the database.
- **Running totals beside the counter's last reading.** Each stat on each server is a total and the last raw reading. A rise is the difference, so a save lost to a crash is made up at the next reading; a counter that fell by more than a tenth of its last reading, or by more than 1 for one under 10 (a deleted stats file, or a world rolled back that far), restarted from 0, so the total keeps growing, while a smaller fall (another plugin's `decrementStatistic`) is a decrease. The first reading of a player or a stat is history: all time, not today. Placeholder and API stats keep their last value the same way, so the first one after a restart counts. A stat added later, by a reload or another plugin's registration, has its saved rows read before anything is counted on top.
- **Events wait in order, added up, and bounded.** Readings, joins and other plugins' changes wait for the next save in one queue. Other plugins' increments of one stat for one player wait as one number, and a run of sets as its first and last value and the rises between, so a plugin that counts every block broken adds nothing per call. A join or a reading closes the player's open sums: another plugin's join listener can increment before xStats hears of the join, and a sum ahead of the join would carry every later increment to a save that drops it, the player not existing yet. A player whose rows can't be read (a database blip after a restart) has that event and every later one of theirs held back in order for the next save, and everyone else's are saved; applying them out of order would make a reading look like a counter restart and double it. Past 100,000 waiting the console is warned; past a million new ones are dropped and counted, as xRewind does.
- **Data size.** One daily row per player, stat and day it rose, only for stats the owner gives periods; days older than 90 fold into months, each server folding only its own rows. 10,000 players with ten stats with periods are rows only for the days they played.
- **AFK-aware playtime from the save's own comparison.** Time since the last reading counts only if the camera turned. Position alone would count a water-stream AFK pool, and a movement listener would cost every tick.
- **Leaderboards are worked out during the save** for stats that changed (or every board when a day turns over, who's left out changes, or the network's numbers are read again), as sorted arrays: a rank is a binary search, ties share a place. Placeholders, `/leaderboard`, boards and the website read them from memory.
- **Private is private on the whole site, straight away.** `/stats private` (here or on another server of the network) makes the website's leaderboard pages and summaries again at once, rather than at the next save. On the site, places are counted among players it shows, so a place never gives away that someone private is above; in game, where private players still show, places count everyone.
- **One translation table.** Bukkit names 23 of Minecraft's 78 custom stats differently (`PLAY_ONE_MINUTE` is `play_time`). The table was taken from CraftBukkit's own mapping in the 1.21.11 and 26.3 server jars (they differ only by 26.x's `sleep_in_straw_bed`), and `/xstats status` checks it on every boot test through Paper's scoreboard criteria, which name each stat by its vanilla key. 26.x keeps stats files in `world/players/stats`; the import reads both folders.
- **The website runs on `com.sun.net.httpserver`,** in every JDK, so no library is shaded. Read-only; virtual threads with a cap (a request that waits over two seconds gets 503, and past eight times the cap waiting, connections are closed, which the JDK's dispatcher survives); a count per visitor per minute (an IPv6 visitor by their /64) that reads the visitor's address only from listed proxies (addresses or CIDR ranges), and only from the one header the owner names: `X-Forwarded-For` by default, whose nearest untrusted hop is used, or `CF-Connecting-IP` when chosen. Believing both let a visitor pick their address through nginx or Caddy, which pass on what they're sent. Past 10,000 addresses in a minute, new ones are let through uncounted until the next minute rather than clearing anyone's count or sharing one (a shared count let one flood from an IPv6 /48 lock out every real visitor); the cap on requests at once still bounds what that costs. Ports a proxy adds to an address are dropped. Heads have their own limit (five times the page limit) and wait up to five seconds for one of four fetches without holding a page's turn, at most 64 waiting; pages that can name players (leaderboards, summaries, search) are `no-cache` with an ETag, so a player who goes private isn't kept by a browser or CDN, while the server's page is cached a minute; pages everyone sees made after each save and sent gzipped with ETags. Site files come from the jar by exact name; the owner's logo by a strict file-name pattern. It sets `sun.net.httpserver.maxReqTime`/`maxRspTime` only if nobody has, since the JDK otherwise waits forever for a slow request; those are the JVM's, shared with any other plugin's server, and don't stop a slow trickle of bytes, so the docs say to put a reverse proxy in front of a public site. Off by default: a port opened without the owner knowing is worse than a setting to turn on.
- **The site is plain files** (about 64 KiB since its redesign in #105), copied into the jar and zipped by the build, and `/xstats web export` writes them with a `config.json` pointing at the API. It only ever sets `textContent`; a test fails the build on `innerHTML` and friends, and the page has a CSP with no inline script.
- **Networks** use the core's change feed only as a signal: a server that hears another saved reads the network's sums at its next save, so memory holds network totals and each server writes only its own rows. A gauge (a placeholder or a set value, such as a balance) isn't summed: it's the value read last, by `totals.updated`, which holds when the value was read rather than when it was saved (#106), so a balance spent on creative isn't shown as survival's older, higher one (servers' clocks are expected to agree, as NTP keeps them). A hide that couldn't be read from the feed is picked up by the next reload.
- **Later: cheaper network reloads.** Each reload reads every player's sums again, a few tens of milliseconds for ten thousand players on xStats' own thread, at most once a save. Fine for 1.0; later it can read only the players changed since a version it stored.
- **`/leaderboard`, not `/top`.** The issue asked for `/top`, but xUtilities has `/top` (to the highest block), and with both installed one would lose it with a warning. `/lb` is its alias; owners without xUtilities can add `top`.
- **Family integrations** (xBans, xVote, xMoney, xPlots, xTeleport, zChat) aren't built yet (#42), though all but xPlots now have an API on `main`; profile sections and custom stats are the API they'll use.


## More stores: Hangar and voxel.shop, published by the release (2026-11-23)

## The rewrite: every platform, in Kotlin, one plugin at a time (2026-11-23)

Every plugin is rewritten again so it runs on Spigot, CraftBukkit and Bukkit down to 1.8.8, Fabric, NeoForge, Forge 1.20.1, Sponge, Velocity and BungeeCord, Pumpkin and Vine, Minestom and Hytale, as well as Paper and Folia, translated, with the speed and jar sizes it has today. [ROADMAP.md](ROADMAP.md) is the plan; this is why it's shaped that way.

- **Kotlin, and its logic multiplatform.** Pumpkin's plugins are WebAssembly components, and its Kotlin API is Kotlin/Wasm: code that runs there can't use a Java library or `java.*`. So each plugin's logic is Kotlin Multiplatform, built for the JVM and `wasmWasi`, and only thin adapters touch a platform. Kotlin on the JVM is as fast as Java, and null-safety removes a class of crashes. The cost is the stdlib, which is fetched or installed, not shaded, so jars stay their size. Without Pumpkin, adding a platform layer to the Java core (#118's plan) would have been cheaper; with it, one codebase for every platform needs this.
- **Our own markup, not MiniMessage, in `common`.** MiniMessage is JVM-only. A small parser for the subset we use draws to Adventure on the JVM and to Pumpkin's text there, and keeps the parse-once cache in shared code.
- **Today's versions move to `maintenance`.** A rewrite on a side branch for months rots; `main` is the rewrite, and fixes to today's versions are released from `maintenance` until each new major has been out a month.
- **A major ships on four platforms.** Paper, Folia, Spigot and Fabric (plus a proxy for network features); NeoForge, Forge, Sponge, Pumpkin, Vine, Minestom and Hytale follow as minors, in waves. Fourteen plugins on twelve platforms at once wouldn't ship.
- **Stores change with the platforms.** Spigot users can now run the plugins, so SpigotMC gets listings, downloading from GitHub since it has no upload API. BuiltByBit's update API still needs its paid Ultimate plan, so it's a free listing the same way. CurseForge takes the Bukkit, Fabric, NeoForge, Forge and Hytale jars through its API.
- **The release needs an approval.** With more stores and tokens, the `release` environment now waits for a maintainer to approve each run.
- **Translations (#117) are built in from the start,** in the core, rather than moved into each plugin after.

## M0: Java 8 bytecode, each server's own text, and Pumpkin waits on upstream (2026-11-24)

## The rewrite grows inside today's repo, module by module (2026-11-24)

M1 starts the rewrite's build (#122). Where its code lives, and the first rules it sets:

- **Today's Java stays on `main` until each plugin's rewrite replaces it, in place.** The Java core stays the `:core` project; the rewrite's core modules are subprojects inside its folder: `core/core-common` (KMP, `jvm` and `wasmWasi`), `core/core-api` (KMP) and `core/core-jvm` (Kotlin/JVM), with the `platform-*` modules beside them later. So the layout in ROADMAP.md is reached without moving anything twice, and nothing today's plugins build, test, boot or document changes: no plugin depends on the new modules, and their conventions (`xena.kmp`, `xena.kmp-api`, `xena.kotlin-jvm`) are separate from `xena.java`.
- **One Kotlin version, in `gradle/libs.versions.toml`:** 2.4.21, the newest M0 booted on Spigot. Every Xena plugin moves to a new one together.
- **Warnings are errors, and every public declaration is explicit** (Kotlin's explicit API mode). The JVM targets are Java 8 class files compiled against Java 8's API (`-Xjdk-release=1.8`); a test in `core-jvm` reads the class files to make sure.
- **Kotlin's own ABI validation for APIs,** with the signatures committed in `<module>/api/` and checked by `check`, for the JVM and the `wasmWasi` klib at once (`./gradlew <module>:updateKotlinAbi` after a deliberate change). It's marked experimental, but it replaces a separate plugin and does what the Java APIs' `apiDump` does.
- **Errors are `Outcome<T, E>`,** an `Ok` or an `Err` with a typed error. Not `Result`, so it never shadows Kotlin's `Result`, whose error is always a `Throwable`.
- **Durations** read everything today's plugins read, plus spaces, `ms`, `mo` and `y`; `write` is exact, so a config read back keeps its value, where today's codec rounded to two units.
- **Markup is parsed once and rendered per send.** The theme's tags (`<highlight>`, `<prefix>`, ...) are given to the parser, since the theme changes only on reload; placeholders (`<player>`, and `<has_next>...</has_next>` shown or not) are filled in when it's rendered, inside clicks and hovers too, and text placeholders can't add styles. A tag it doesn't know, or a placeholder it isn't given, stays as text, as in MiniMessage. In a gradient, a part with its own colour keeps it.
- **CI:** a pull request that only changes the rewrite's modules builds and tests just those, on the JVM and on `wasmWasi` (with the Node Kotlin's Gradle plugin pins, from a repository in `settings.gradle.kts`), and skips today's plugins' tests and boots; one that changes today's core still checks everything.

## The rewrite's config: a schema in Kotlin, YAML read by snakeyaml-engine-kmp and written by us (2026-11-24)

The config system is in `core-common` (`co.xenastudios.core.common.config`), with the file's side in `core-jvm`. It keeps what today's does (above: generated from a schema, used when it can't be saved, edited in game); what's new:

- **A schema of typed keys, not `kotlinx.serialization` classes.** A plugin's config is an `object : ConfigSchema` whose properties are keys (`int("limit", 3, "comment", min = 0)`) and sections, in file order; `config[HomesConfig.homes.limit]` reads one. No reflection, so it's the same on Wasm and survives R8. Each bad value is reported with its path and line and falls back to its own default, where a serialization decoder stops at the first. Comments, limits and former defaults live on the key, and `describe()` gives the schema as data for the site's manifest task.
- **YAML is read through a `YamlReader`, and written by us.** The writer is in `core-common`, as today's core has its own emitter: schema order and comments, the owner's values as they wrote them (even ones that can't be used), unknown keys kept after the known ones of their section. A file is rewritten only when loading changed it (a new setting, a carry forward) or by an in-game edit, and then the schema's comments replace the owner's own; today's Bukkit path kept those. The parser's comment events could bring them back if owners miss them.
- **snakeyaml-engine-kmp on the JVM, not kaml.** kaml 0.104.0 is Java 11 class files, which the core's Java 8 floor can't load (`ConfigBytecodeTest` checks the parser and its dependencies), and its serialization layer would go unused. snakeyaml-engine-kmp is the parser kaml is built on: Kotlin Multiplatform, Java 8, and the library whose wasmWasi build is pending (krzema12/snakeyaml-engine-kmp#523). When that's published, `core-common` can depend on it and `JvmYaml` moves there; until then `core-common`'s tests read YAML with a small test-only reader. It costs about 870 KB unshrunk with okio; how it reaches servers (`libraries:`, the loader, R8) is settled with packaging.
- **Migrations edit the file's tree, and can run again.** Each `migrate(from)` step uses operations that leave an already-carried file as it is (a move whose source is gone does nothing; one whose destination the owner set just drops the source), so a carry that couldn't be saved runs again on the next start with the same result.

## The core's library loader: Java on its own, one cache, pins the build checks (2026-11-24)

The startup path M0 proved (`sandbox/m0/bukkit`) moves into the core as `core/core-loader`: the Java shim a Bukkit-family plugin's main class extends (`BukkitBootstrap`), and the loader behind it.

- **A Java module of its own, not part of `core-jvm`.** The shim runs before the stdlib can be loaded, so one Kotlin class there, or a call Kotlin inserts (`Intrinsics`), is a `NoClassDefFoundError` on an old server. `core-jvm` has the stdlib and `core-common` on its class path, so nothing would catch that until a boot test; in a Java module with no Kotlin on its class path it doesn't compile. It's Java 8 bytecode (`xena.java8`), needs nothing but Spigot's 1.8.8 API (compile-only, so the shim uses nothing newer), and each plugin shades and relocates it, as it does the core. The Bukkit shim sits in its `bukkit` package until `platform-bukkit` exists; the loader itself knows no platform, for a proxy's shim and the optional libraries later.
- **One cache for the family, `plugins/Xena/libraries/`,** laid out like a Maven repository, so the second plugin finds the first one's jar, and an owner who has to put it there by hand is told the exact path. A jar is checked against its pinned SHA-256 every time it's used, not only when downloaded (a few milliseconds for the stdlib, and only on servers without `libraries:`), so a damaged or swapped file is downloaded again, never loaded.
- **Mirrors:** Google's mirror of Maven Central, then Maven Central, as xBackup does. `mirror:` in `plugins/Xena/libraries.yml` (or `-Dxena.libraries.mirror`) replaces them: a file, because many hosts don't let owners add JVM flags, read with Bukkit's own YAML since the config system is Kotlin. Offline, a refused connection or a download with the wrong hash ends in one line naming the library, each mirror's reason, the setting and the path.
- **Per jar, and visible from anywhere counts.** The spike's groups are gone: each jar has a probe class of its own, and a jar whose probe the plugin's class loader already sees (bundled by the server, fetched through `libraries:`, or another plugin's on servers before 1.16.5) isn't downloaded. On those servers the first plugin's stdlib is everyone's, so the shim warns when `KotlinVersion.CURRENT` isn't the version it was built for.
- **How a jar is added,** as M0 found: reflection on Java 8, the trusted lookup on 9 and later, the child-first loader last. Reflection is also tried after the lookup on 9+, so `--add-opens java.base/java.net=ALL-UNNAMED` is the fix if a JDK refuses `Unsafe`, and `loader:` (or `-Dxena.libraries.loader`) forces one. M0's `global` strategy is dropped (it broke on 1.15.2). Falling back to the child-first loader logs a warning, which fails a boot test, so CI notices the day a JDK refuses the lookup.
- **The hashes are committed, and the build checks them.** `gradle/library-pins.txt` holds the SHA-256 of every library a plugin downloads; `xena.fetched-libraries` fails the build when a jar Gradle resolves isn't there with that hash, then writes the list into the jar (`META-INF/xena/libraries.txt`). Hashing at build time alone would trust whatever Gradle downloaded; a pin is a reviewed line, as in xBackup's `LibrariesTest`. A bump runs the build with `-PupdatePins`. One file for the repo, since the family shares its versions. The same coordinates go into plugin.yml's `libraries:`.
- **Boot tests through `scripts/boot-test.sh --server`,** which boots a server jar already on disk (BuildTools' Spigot can't be downloaded) on a chosen JDK, and now reads the log format of Spigot 1.13–1.16, where it missed errors before. CI doesn't run them yet: it needs BuildTools' jars and JDKs 8 and 16.
- When the Bukkit jar is shrunk with R8, the main class and the `PluginEntry` class keep their names and constructors: the server and the shim make them by name.

## The platform layer: Folia's model everywhere, events by key, CompletableFuture on the JVM (2026-11-24)

What the core and the plugins program against, so their logic never touches a server (#122). The adapters (`platform-bukkit`, `platform-fabric`) implement it in their own PRs.

- **Players are `PlayerRef`, a `kotlin.uuid.Uuid` inside.** `java.util.UUID` doesn't exist on Wasm, and `Uuid` is stable from Kotlin 2.4 and an ordinary class, not a value class, so it doesn't mangle Java signatures. A wrapper rather than a bare `Uuid` so an API says "a player", and can't be handed an entity's or a plot's UUID by mistake. Java gets there with `PlayerRefs.of(java.util.UUID)` and `PlayerRefs.javaUuid(ref)`, in `core-api`'s JVM part; a bare `Uuid` elsewhere converts with the stdlib's `UuidKt.toJavaUuid` and `toKotlinUuid`. Worlds are `WorldRef`, by the name the platform keeps across restarts (the folder on Bukkit, the dimension id on the mod loaders and Pumpkin); `Location` is immutable and knows its chunk, which is what Folia's regions are made of.
- **Async in an API is `Pending<T>`: on the JVM it *is* `CompletableFuture<T>`.** An `expect class` with an `actual typealias` to `CompletableFuture` on the JVM and a small single-threaded promise on Wasm. So an API is written once in common code, a Java plugin sees a plain `CompletableFuture` (what ROADMAP.md promises), and Pumpkin, which has no threads and answers plugin calls synchronously over IPC, gets something that works there. The common helpers (`resolve`, `onSettled`, `map`, ...) are `@JvmSynthetic`, so Java's autocomplete shows only `CompletableFuture`'s own methods. The cost is `-Xexpect-actual-classes` (expect classes are Beta) in `core-api` alone. Not chosen: a type of our own on every platform (Java would get an unfamiliar future), `suspend` (not allowed in API signatures, and it needs coroutines at runtime), plain callbacks (no way to chain or wait from Java).
- **Events are subscribed by an `EventType<E>` key, not a class.** Each event declares one (`@JvmField val TYPE = EventType.of("xmoney:balance_changed")`). Wasm has no reflection and Java has no `KClass`; a key also means delivery never depends on class hierarchies, and every event has a stable name for logs, the generated docs and Pumpkin's IPC. Priorities are Bukkit's six, so listeners move between the two unchanged. A pre-event is `Cancellable`; `ignoreCancelled` skips those already cancelled, and a later listener can uncancel. A listener that throws is logged and the rest still hear the event. Listeners are a copy-on-write snapshot, so firing takes no lock and allocates nothing, and an event no one listens to costs a map lookup (`hasListeners` lets a plugin skip building it).
- **Only the owning plugin fires.** The public `EventBus` (in `core-api`) is subscribe-only; firing is on `SimpleEventBus`, in `core-common`, which each plugin keeps for itself and hands out as its API's bus.
- **Native events are a bridge: a subscriber at `NORMAL` that also hears cancelled events.** Bukkit's adapter registers one per event type, firing a Bukkit event that wraps ours and delegates `isCancelled`, so Skript and Bukkit listeners see the event and their cancellation is what our later listeners see. No special case in the bus, and the order is the same on every platform.
- **The scheduler is Folia's model, with fewer threads elsewhere.** Work says `Where` it belongs (`Global`, `At(location)`, `On(entity)`, `Async`), with a `Duration` delay and an optional period, and gets the one `Task` type back. On Folia those are the region, entity, global and async schedulers; on Bukkit and Fabric the first three are the main thread; on Pumpkin all four are tick callbacks (`Threading.REGIONS`, `MAIN_THREAD`, `SINGLE`). A delay of zero is the next tick, never now; `now(where)` runs inline when the thread already owns it, as today's `Tasks.global` and `Tasks.entity` do. Server-thread delays round up to whole ticks. Global work keeps using Bukkit's scheduler on Paper, so it survives the empty-server pause ("Global work survives an empty server's pause"). What a platform can do is a set of `Capability`s and its `Threading`, found once at startup.
- **The clock, files and the console come from the platform.** Pumpkin's plugins can't read the clock or files themselves (M0), so shared code never calls the stdlib for them: `Clock`, `Storage` (the plugin's own folder, paths that can't leave it, all-or-nothing writes, typed errors, called from async tasks) and `Log`. `SystemClock` serves every JVM platform.
- **A failing module turns itself off; nothing else does.** A module registers everything through its `ModuleContext`: tasks, subscriptions, and `onDisable` for what an adapter registers natively. When it turns off, all of it is undone, so a module that's off registers nothing and runs nothing, even a task already queued. Anything run through the context that throws (`enable`, `reload`, a task, a listener, a `guard`ed platform callback) turns that module off at once, logs why, and keeps the reason for `/<plugin> debug`; the plugin and its other modules carry on, and the next reload tries the module again. A failure on another thread stops the module there and then, and its cleanup runs on the global thread. Errors the JVM can't recover from (`VirtualMachineError`) aren't contained. On reload a module either takes the new config in place (`reload` returns `true`) or is replaced by a new one from its factory, the default, so settings always apply on reload.
- **Development builds check threads.** `platform.checkThread(where) { "what" }` throws `WrongThreadException` when the current thread doesn't own `where`, if `Platform.development`; in a release build it's one field read. The fake platform is a development build on Folia's rules by default, so a plugin's tests catch the wrong thread before Folia does.
- **`core-testing` is the fake platform** every plugin's tests use, on the JVM and Wasm: a virtual-time scheduler that runs everything in a fixed order on the test's thread while tracking which "thread" each task is on, entities that spawn, move and despawn (retiring their work), a clock on that time, files in memory and a recorded log. A KMP module rather than test fixtures, which KMP doesn't have; `core-common`'s own tests use it too.
- **No audience or message target yet.** Sending messages to players comes with translations, in its own PR; this layer names players only by `PlayerRef`, so the two meet there.

## The rewrite's database: one writer that never repeats a commit, statements per dialect, records for Pumpkin (2026-11-24)

The database layer of the rewrite (#122): `co.xenastudios.core.common.db` and `.storage` in `core-common`, `co.xenastudios.core.jvm.db` in `core-jvm`. It keeps what today's `core/db` proved ("A shared database layer, with no drivers shaded in", "Network mode: one change feed in the database"); what's new:

- **SQL is built, not written, in common code.** A table is declared once (`object Homes : Table("homes")` with typed columns: `INT`, `LONG`, `DOUBLE`, `BOOLEAN`, `UUID` as 16 bytes, `INSTANT`, `BYTES`, `text(max)`, `nullable()`, `map`), and `Sql(dialect, prefix)` writes each statement for the database it's on: `createTable` (`IF NOT EXISTS`, utf8mb4 InnoDB on MySQL, SQLite's own row id), `insert`, `insertIgnore`, `upsert`, `update`, `delete`, `select`, and `raw` with `{p}` for what the builders don't cover. Values are bound, never spliced in, and rows are read back by column (`row[Homes.name]`). No `java.*`, so it compiles for `wasmWasi`, and its tests run on both.
- **Upserts per dialect, because old servers ship old SQLite.** Spigot 1.8.8 bundles sqlite-jdbc 3.7.2, older than SQLite's `ON CONFLICT ... DO UPDATE` (3.24). M0 didn't test SQLite, so the dialect carries the version the driver reports, and below 3.24 an upsert is an `UPDATE` then an `INSERT OR IGNORE`, which run in the same transaction on the one writer, so nothing slips between them (tested on a real SQLite). MySQL and MariaDB get `ON DUPLICATE KEY UPDATE c = VALUES(c)`: MySQL 8.0.20+ calls `VALUES()` there deprecated but runs it, and MariaDB has no row-alias form. The oldest SQLite used is 3.7.0, for WAL.
- **Each plugin's tables have its prefix, so the family can share one database**: one MySQL, or one SQLite file in `plugins/Xena/` that the adapter passes. Each prefix has its own `{prefix}meta` table and schema version. The `meta` and `changes` tables have today's columns, so a plugin can keep its tables across its rewrite.
- **Migrations are numbered steps of statements, each in its own transaction with its new version,** as today. A step can run again: MySQL commits each table change as it goes, so a statement whose table, column or index is already there (`ALREADY_EXISTS`, from MySQL's 1050, 1060 and 1061 or SQLite's message) is skipped. A database made by a newer version is refused, never changed.
- **Errors are `Outcome<T, DbError>`** with a kind code can act on (`UNAVAILABLE` and `BUSY` are worth retrying; `CONSTRAINT`; `CORRUPT` for a stored value its column can't read; `OVERLOADED`, `CLOSED`, `NO_DRIVER` and others). Every `Pending` settles with one; none fails.
- **One writer thread per database, writes acknowledged on commit.** `write(statements)` queues and returns; the writer runs everything waiting (up to 1,000 writes) as one transaction, consecutive statements with the same SQL as one JDBC batch (so `rewriteBatchedStatements` makes one multi-row insert on MySQL), and settles each write's `Pending` once it's committed. While the database is down a batch is kept and retried (at once, then from 250 ms doubling to 30 s), with one line when it goes and one when it's back. A batch the database refuses is split, and only the write at fault fails, as xRewind's writer does. Past 100,000 waiting the console is warned; past a million new writes are refused with `OVERLOADED` rather than run the server out of memory. `transaction { }` runs read-then-write work (a withdrawal) on the writer in its own transaction, rolled back on an error; `session { }` runs migrations there. Closing finishes what's queued, waiting up to 10 s for a database that's down, then fails the rest with `CLOSED`.
- **A commit whose answer is lost is looked up, not repeated.** Each transaction also sets this writer's row in `meta` to the batch's number. When the connection dies after the commit was sent, the writer reads that row on a new connection: if the number is there the batch landed and is acknowledged, otherwise it's run again. Without it, a retried insert after a lost answer (a MySQL restart at the wrong moment) wrote its rows twice. A clean close deletes the row.
- **Reads beside the writer, and no HikariCP.** Each reader thread keeps one connection: one on SQLite, whose WAL lets it read while the writer writes, two on MySQL. A reader idle for a minute closes its connection and ends, and one idle for 30 s is checked before use, since MySQL's `wait_timeout` closes idle connections. SQLite readers are `query_only`, so a write by mistake fails. That's the whole pool: the threads are few and each owns its connection, so HikariCP's checkout, validation and housekeeping (and its jar) would buy nothing. Reads see what's committed; one that must see a write waits for that write's `Pending`, or runs in `session`.
- **Drivers: the server's first, then fetched; never shaded.** `Drivers` loads the server's SQLite driver (Paper's, Spigot's), or MySQL's (Connector/J 8+, then 5.1 on old servers), and uses it directly, not through `DriverManager`, which only hands out drivers the caller's class loader sees. SQLite older than 3.7.0 is passed over. Otherwise a `DriverFetcher` downloads the jar (`DriverLibrary` has the coordinates) and it's loaded in a class loader of its own. The core's loader (#143) has the pinned, shared cache this needs but no hook for optional libraries yet, so `DriverFetcher` is the seam: each adapter passes one built on `LibraryCache` once both are in, with the driver jars' hashes in `gradle/library-pins.txt`. Until then a server without a driver is told which one to install.
- **Network mode's change feed is common code**, the same protocol and table as today's, on the `Database` interface: published in the change's own write (`feed.publishing(topic, payload)` added to the same `write`) or transaction, checked every few seconds off the server's threads, late commits waited for, pruned to ten minutes but never empty, and a resync when a server may have missed changes. The waiting and pruning logic is a pure class tested on both targets. On the JVM it's tested end to end with two databases on one SQLite file and, with `XR_MYSQL` set, on MariaDB.
- **Pumpkin gets the same records in files.** `RecordStore<K, V>` (`get`, `all`, `put`, `remove`) is what a plugin that runs on Pumpkin writes its storage against, from one `RecordType` declaration on a `Table`: `SqlRecordStore` upserts through the writer on the JVM; `FileRecordStore` keeps the records in memory and writes the whole file (all or nothing, through `Storage`) on the next async task after a change, acknowledging it once the file holds it. The file is text with named columns, so a column added later reads as `NULL`. A plugin whose data needs queries (history, leaderboards) uses the database and isn't on Pumpkin.
- **Crash-safety is tested by killing connections.** `ChaosTest` closes the writer's connection under it mid-batch and at commit, before and after the commit reaches SQLite, while four threads write, and checks every acknowledged write is in the database exactly once; it fails if the lost-commit lookup is removed. `MySqlDatabaseTest` does the same against MariaDB, with a migration that got partway and a refused write in a batch.

## Translations: English in code, other languages as files, drawn once per language (2026-11-24)

The design is #117's; this is how the core builds it (`co.xenastudios.core.common.i18n`, with the files and the server text in `core-jvm`). What wasn't obvious:

- **English is code; every other language is a file.** A plugin declares its messages in a `MessageBundle` (key, English, comment, placeholders, former English), as the config declares settings, and ships `lang/<tag>.yml` for the others. Placeholders are declared, not guessed: English may use only styles, the theme's tags and its own placeholders, so a typo like `<hilight>` fails in the plugin's tests, and the site gets each message's placeholders from the code.
- **Each language's file in the plugin folder is written in full,** with the bundle's comments, and owners edit it in place. A message it lacks is added in the shipped translation, or in English where there's none, so a partial translation shows what's left. `default-language` chooses a file for readers whose language has none; it doesn't fill other files' gaps, which would put German into the French file.
- **Untouched messages follow updates on every load, not only on a new version.** A message still on a text the plugin once shipped (a former translation, a former English text, or the English that stood in before the translation came) gets the current one. Former translations sit in the shipped file under a reserved `translation:` section, with the language's name and whether it's machine-drafted; the written file has no such section. An owner who wants an old wording back changes a character.
- **Matching is strict:** region, language, `default-language` (`pt_BR` → `pt-BR` → `pt` → default). `pt-PT` doesn't get `pt-BR`, nor `zh-TW` `zh-CN`; a plain `pt.yml` serves every Portuguese. Matches are kept per client locale, up to 256, since clients send what they like.
- **Drawn once per language, kept beside the translations.** `Translations` parses each message once per language on first use, with the theme's tags (so the theme applies to every language, and a new theme means new translations), and keeps the chat form of messages without placeholders. `MessageDrawer` keeps each one drawn to the server's text per language, so a send is two array reads; a broadcast groups viewers by language and draws once per group, the console in `default-language`. Renderers only draw. Viewers are any `V` with a `LanguageSource<V>`: the core's player type isn't settled, and the platform modules implement it on theirs.
- **Formats are our own tables.** `common` has no `java.text`, so numbers, durations (with CLDR's plural rules: three forms in Russian and Polish) and dates are a small table per launch language. Grouping uses a no-break space where CLDR has a (narrow) space, since every client's font draws U+00A0; rounding is half up, as for money. Dates take the reader's UTC offset from the platform.
- **The CI check** (`TranslationCheck.verify`, in each plugin's tests until it's a Gradle task) fails on missing and unknown keys, on tags a translation uses that its English doesn't fill (a placeholder, a typo, or a click or hover its English hasn't, so a translation can't add `<click:run_command:'/op me'>`), and on placeholders it drops. Styles and theme tags may change freely. In an owner's file, the same foreign tags are only reported.
- **Server text:** Adventure is compiled against 4.7.0, which Paper 1.16.5 bundles, so nothing newer can be called. Spigot 1.8.8's `bungeecord-chat-1.8-SNAPSHOT` is in no public repository, so `BungeeRenderer` compiles against 1.16-R0.4 and a test reads its class files to keep it to the members 1.8.8 has, apart from RGB colours and copy-to-clipboard behind switches the platform sets at startup; its other tests also passed against the 1.8.8 jar from BuildTools. On Spigot 1.21, where a `BaseComponent[]` send costs 12.7 µs against 4.6 µs for a legacy string (M0), the platform picks `LegacyRenderer`, which lives in `common`.

## Commands are data that runs, and the docs read the same data (2026-11-24)

A plugin's commands, permissions and placeholders are declared once in `core-common` (`command`, `permission`, `placeholder`), and the same objects are what runs, what the platform registers and what the site shows (#122, as M0's site spike proposed).

- **A literal tree with typed arguments, run by our own dispatcher in common code.** `commands { root(...) { literal(...) { argument(...); executes { } } } }` builds an immutable `CommandTree`; `CommandDispatcher` parses, checks permissions, runs hooks and the handler, and completes, the same on the JVM and Wasm, so a plugin's command tests run on the fake platform on both. An argument type parses, suggests and describes itself for the docs, so the three can't disagree. Results are data (`CommandResult`: usage, no permission, invalid argument and why, on cooldown, ...) shown through `CommandFeedback`, English until the translations take over; nothing a handler throws reaches the server. A node takes arguments or has subcommands, not both, which keeps every line unambiguous.
- **Cloud 2 is an adapter's business, behind `CommandRegistrar`.** Where Cloud has a platform module, the adapter registers the tree's shape with it (literals, arguments with our parsers and suggestions, permissions, sender type) so clients get Brigadier's hints, and Cloud's handler hands the line back to our dispatcher, so hooks and errors behave alike where there's no Cloud: Sponge 8+ and, if Cloud's beta falls short, Fabric 1.20.1 (M0) get small bridges, Pumpkin its own commands. The registrar is synced on startup and every reload, as today's `CommandRegistry` is.
- **Permissions are declared objects with Bukkit's defaults and children,** `<plugin>.<suffix>` in a `PermissionSet`, synced through `PermissionRegistrar`. A node's permission is needed on top of every one above it, as a Bukkit command's gates everything under it.
- **Cooldowns and confirmations are hooks around the handler.** A cooldown starts only after a run that didn't fail and has an optional bypass permission; a confirmation runs a command when the same line is typed again in time. Their state lives in the hook, so a tree rebuilt on reload starts them fresh.
- **The admin subcommands are one reusable subtree,** `AdminCommands`, mounted under each plugin's own root: `reload` and `debug` always, `import`, `migrate` and `forget` where they apply, each with `<plugin>.admin.<sub>` and `<plugin>.admin` granting them all. `reload` runs on the global thread on the next tick and syncs the plugin's `ModuleSet` (`ModuleReloader`), reporting modules that failed; the others are in "The admin subcommands" below.
- **The manifest is written by our own small JSON writer, not kotlinx.serialization.** Each object in it is built through a shape that refuses unknown, missing or mistyped fields, and the JSON Schema is made from the same shapes, so the schema can't drift from what's written; output is byte-identical on the JVM and Wasm. That keeps `core-common` free of a runtime dependency (ROADMAP.md, Light) for something only the build uses. Messages and events have a seam (`MessageInfo`, `EventInfo`) that the translations and the API's events fill later; platforms come from the build.
- **`xena.manifest` in build-logic** adds `xenaManifest` (core-common's `ManifestMain`, run on the plugin's JVM test classpath, so a `ManifestSource` can build the plugin on the fake platform), `checkXenaManifest` on `check` (naming the file and line that's stale; `-PupdateGolden` updates instead, like the config goldens) and `updateXenaManifest`. Until a plugin is rewritten, `core/core-testing/sample` (xSample, never released) proves it: its manifest is in `docs/src/generated/xsample/`, which the docs' `references` collection validates against the schema but no page shows. The reference components are in `docs/src/components/reference/`, used by no page yet.

## The admin subcommands: checks before a paste, imports page by page, migrations checked by count (2026-11-24)

What `/<plugin> debug`, `import`, `migrate` and `forget` run on (#122), in `co.xenastudios.core.common.admin` with the HTTP in `core-jvm`; "Commands are data that runs" declared them. Each is mounted only when the plugin gives what it runs on, so a plugin without a database has no `migrate`. Their replies are `CoreMessages`, drawn in the reader's language by `AdminText` (English until the adapter says which locale a source has).

- **Debug checks first, then a paste.** Health checks answer through a `Pending`, so the database's (a `SELECT 1` on a reader, timed), dependencies', config's and modules' never wait on a server thread, and one that hasn't answered in 10 s fails its line rather than hang the command. The threads check schedules a global task and an async one from it and asks each whether it owns the global thread: the mistake a wrongly picked scheduler makes on Folia shows there before it shows as a crash. The report (versions, platform, the checks, the last 50 warnings and errors kept by `RecentErrors`, the config) is built and uploaded on an async task.
- **mclo.gs, behind `PasteService`.** It's what Minecraft support channels already ask for, takes a plain form post (so `HttpURLConnection`, no client library, Java 8), keeps pastes 90 days and hides IP addresses itself. A network can pass its own service; with none, or when the upload fails, the report is written to `debug/` in the plugin's folder and the reply says why.
- **Secrets are removed by name, erring wide.** Any YAML key that names a secret as a word (`password`, `token`, `secret`, `api-key`, `webhook`, `auth`, ...) loses its value wherever it is, and credentials in a URL and `password=` in a query string go too, across the whole report, errors included (a JDBC error can carry its URL). A paste is public to anyone with the link and gets shared in Discord, so removing a harmless value is the better mistake.
- **Importers are pages with a cursor, and writes that replace.** An `Importer` detects its source, counts, reads a page after a cursor, and writes one record at a time, all through `Pending`s, so a source in a database or a file works the same, and Pumpkin isn't ruled out. The core saves the cursor in `imports/<id>.txt` after each page is written, so a run that stops carries on there; writes must replace (`upsert`, `insertIgnore`), so a page written twice, or a whole import run again, changes nothing. A record that fails is reported (the first five in chat, all in the console) and the run goes on; only a page that can't be read stops it. `--dry-run` reads everything and counts what would be imported or skipped, writing nothing. One import at a time. xSample's tests have an example importer.
- **Migrations copy, count, then switch; the source is only read.** The target is migrated to the plugin's schema first, so its tables, keys and schema version are the plugin's own; a target with rows in any of the plugin's tables is refused unless `--force`, which empties them, so a second server's data is neither mixed in nor lost by accident. Rows go a page at a time in key order (`Sql.select` gained `offset`), each page one write through the target's single writer. Then every table is counted on both sides, and only if they match is the target closed and the config switched (`StorageSwitch`, which the plugin implements, since the storage section is its config's). Writes during the copy can make the counts differ; that fails it with nothing switched, and the reply says to run it on a quiet server, rather than holding the plugin's writes for the length of a copy. `{prefix}meta` isn't copied: the target's migrations write its schema row, and the rest are each writer's own. Tested from SQLite to another SQLite file and, with `XR_MYSQL`, to MariaDB.
- **Forget is a registry of what a plugin keeps per player,** each entry deleting its part (`table(name, db, column)` for a table keyed by the player). Every entry runs even when one fails, and the reply says which failed; the command asks to be typed twice, as declared, and takes a name (through a `PlayerLookup`: the family's player cache, once it's in) or a UUID, since an erasure request often comes with only a UUID from a log.
- **Drivers are fetched on demand through the loader.** The seam "The rewrite's database" left: `core-loader`'s `OnDemandLibraries` reads `META-INF/xena/on-demand-libraries.txt` (the format of `libraries.txt`) and fetches a pinned jar into the family's cache only when asked, and `core-jvm`'s `OnDemandDriverFetcher` is the `DriverFetcher` on it. The build pins them as it does the stdlib: an `onDemand` configuration in `xena.fetched-libraries`, checked against `gradle/library-pins.txt`, which now holds sqlite-jdbc 3.49.1.0 and mysql-connector-j 9.2.0 (both checked against Maven Central's jars). A list of their own, so a server with its own driver never downloads one; `OnDemandDriverTest` keeps `DriverLibrary`, the pins and the version catalog the same.

## The family: one folder, one board, one player cache (2026-11-24)

What the Xena plugins on one server share (ROADMAP.md, The family), in `co.xenastudios.core.common.family`, with the JVM's board in `core-jvm` (#122). It also does the follow-ups the M1 entries above left.

- **`plugins/Xena/config.yml` holds what the family shares** (`FamilyConfig`): the `messages` section (`language`, `default-language` and the `theme`), the shared `database`, and the player cache's size. `Family.load()` reads it through the folder's `Storage`; the first plugin to start finds none and writes the defaults, an old one is copied aside and carried forward as a plugin's own config is, and one that can't be read keeps the last good settings. Each plugin calls it on startup and on every reload, so a change there reaches each plugin as it reloads.
- **A plugin overrides per setting, with the word `shared`.** Its own config has the same `messages` section (`MessagesSection`), but every setting defaults to `shared`, which takes the family's value; anything else is the plugin's own. One section class for both files, so the two can't drift; the family's file refuses `shared`. A theme style is written as the tags that make it (`<#b48cff><bold>`), so it reads back the same. Not chosen: a blank value meaning "the family's" (a blank prefix already means none), or a separate `override: true` switch (one more setting per setting).
- **Storage and network are typed sections every plugin mounts:** `StorageSection` (`type: sqlite | mysql | shared`, `table-prefix`, `mysql`, `pool.readers`), and `NetworkSection` (`enabled`, `check-every`, 1 s to a minute). `shared` puts the plugin's tables in the family's database (`database:` in `plugins/Xena/config.yml`: `none`, `sqlite` for `plugins/Xena/xena.db`, or `mysql`), under its own prefix; with `database.type: none` the plugin falls back to its own SQLite file and says why. `pool.readers` reaches `JdbcDatabase` through `DatabaseSettings.readers`. Both are read at startup only, as CONTRIBUTING.md allows for storage.
- **Copies of the core meet on a board of JDK types.** Each plugin relocates its own core, and on Spigot each also has its own Kotlin (`libraries:` gives each plugin a class loader), so a core or Kotlin class from one plugin is a different class in another, and even a tiny unrelocated API jar would be loaded once per plugin on Bukkit, where a plugin's own jar comes first. So nothing of ours crosses: the board (`FamilyBoard`) is maps of `String` to JDK values only (text, boxed numbers and booleans, `Object[]`), on the JVM one `ConcurrentHashMap` per server (`JvmFamilyBoard`), each plugin wrapping it in its own copy. Values are never changed in place, only replaced compare-and-set. The adapters find the root through the platform's own registry for shared objects, keyed by a JDK type: Bukkit's `ServicesManager` under `ConcurrentMap.class`, registered by every Xena plugin so it survives the first one's disable; Fabric's `ObjectShare` under `xena:board`. `CopiesShareTheBoardTest` loads two copies of the core and of Kotlin in class loaders that can't see each other and checks they share one cache. Not chosen: a service interface of ours (a `ClassCastException` between copies), `System.getProperties()` (code that dumps it casts every value to `String`), JMX (heavy for a map). Pumpkin's plugins share no objects (M0): each has a `MemoryBoard` of its own.
- **One player cache, bounded, saved by whoever changed it** (`PlayerCache`): name, last seen, the client's language, vanished and online, by UUID. Each layout is versioned in its map's name (`xena.players.v1`), so two core versions on one server use separate caches rather than misread each other. Past the cache size (10,000 by default) the least recently seen offline, saved players are dropped down to nine tenths. A change marks the player dirty on the board and schedules one async save; the save claims the board's `saving` slot, so one plugin writes at a time and keeps going until nothing's dirty, and with a database holds the slot until the write commits, so two writers can't land out of order. With the shared database it's the `xena_players` table (the family's own prefix and `xena_meta` schema version, whatever the plugins' prefixes) and players not in memory are read on demand (`lookup`); without one, `plugins/Xena/players.records`, the record file Pumpkin's stores use, holding what memory holds. It's loaded once per board, by the first plugin to start. No repeating task: saves follow changes. `asLookup()` and `asPlayerData()` make it the admin commands' `PlayerLookup` and one of each plugin's `PlayerData`, so `forget <name>` finds a player who's offline and forgets them in the cache too.
- **The i18n viewer is a `PlayerRef`.** `LanguageSource`, `MessageDrawer` and `Delivery` lose their type parameter: a reader is a player's `PlayerRef`, or `null` for the console, as `CommandSource.player` already is. The player cache is a `LanguageSource`: the platform records the client's locale there on join and when it changes, and every plugin's messages read it.
- **`checkTranslations` in build-logic** (in `xena.manifest`, on `check`) runs `core-jvm`'s `TranslationCheckMain` on the plugin's JVM test classpath, with the plugin's `ManifestSource`: the core's `TranslationCheck` on each `lang/<tag>.yml` (`src/commonMain/resources/lang` and the JVM equivalents by default), failing on missing and unknown keys, foreign tags and dropped placeholders, and on a file whose name isn't a tag. In `core-jvm`, not `core-common`, because it reads YAML with `JvmYaml`. `xenaReference { allowMissingTranslations = true }` lets a language being drafted pass.
- **The manifest lists messages and events from the code.** `PluginReference` takes the plugin's `MessageCatalog` (core messages included, since its files hold them) in place of a hand-written list, and `EventInfo.of(type, description)` reads the key, the event class's name and whether it's `Cancellable` from the event type itself: an overload for `Cancellable` events picks that at compile time, so nothing reflects. xSample has messages, a German file and two events, and its manifest in `docs/src/generated/xsample/` shows them.
- **`core-testing` has the fake database and the test YAML reader** (`FakeDatabase`, `FakeSession`, `settled`, `ok`, `row`; `TestYaml`), and `FakeFamily`, the server's `plugins/Xena/` and board, which several `FakePlatform`s share to test plugins together.
- **Left:** the adapters finding the board and the family folder (Bukkit and Fabric, in their PRs) and recording joins, quits and locale changes; language coverage per language in the manifest; carrying today's `theme` and `storage` sections into the new ones when each plugin's rewrite migrates its config.

## The build: the configuration cache everywhere, R8 on every rewrite jar, a scaffolder for the new layout (2026-11-24)

The build half of M1's tooling (#122): caches, R8 and its budgets, and `new-plugin` for the rewrite.

- **The configuration cache is on for every build, and the whole of `build` stores and reuses it with no problems.** Two exceptions, both outside `build`: Minotaur's `modrinth` and `modrinthSyncBody` declare themselves incompatible, so Gradle runs a release's Modrinth upload without the cache (on its own, with nothing to fix on our side); and CodeQL turns it off on purpose, since it must see every compiler run. Gradle 10's two deprecations in our scripts (`by configurations.creating`, a `Project` as a dependency) are gone, so nothing in our build warns.
- **The build cache is local, kept between CI runs by setup-gradle; a remote one waits for a server.** A real remote cache needs a Develocity node or bazel-remote that we'd have to host and secure, and setup-gradle's cache of Gradle's home already carries the local build cache from `main` to pull requests. `settings.gradle.kts` uses an HTTP cache when `XENA_BUILD_CACHE_URL` is set (`XENA_BUILD_CACHE_PUSH=true` to write, `_USER`/`_PASSWORD` for credentials), so one is a secret and a workflow line away. CI saves the configuration cache too once the `GRADLE_ENCRYPTION_KEY` secret exists (setup-gradle encrypts it, since it can hold the environment); without it, CI just rebuilds the task graph.
- **R8 is a convention, `xena.r8`, applied per jar,** with M0's keep rules in build-logic (`xena/r8/common.pro`: stack traces, enums, type tokens, `co.xenastudios.**.api.**`, the loader's `PluginEntry` and `BukkitBootstrap`) plus rules the `shrinkJar` task writes from the jar's own files, so a plugin never repeats them: `plugin.yml`'s and `paper-plugin.yml`'s `main` (and Paper's `bootstrapper`/`loader`), every `fabric.mod.json` entry point, every `META-INF/services` entry. Renamed classes go to a package of the plugin's own (`co.xenastudios.<plugin>.r8`, from the project path unless set), as M0 found Bukkit's shared class cache needs. Output and mapping go to `build/r8/`; the release picks which jar ships when the rewrite's first plugin does. Today's Java plugins keep Shadow's `minimize()` and aren't shrunk.
- **Shrunk jars are run, not just built.** The convention gives tests both jars' paths; the loader sandbox's `JarBootTest` loads each through Bukkit 1.8.8's own `JavaPluginLoader` and `PluginClassLoader` on a stand-in server, runs onLoad and onEnable, and runs its `boot-checks.txt` (the stdlib on the class path, as a server that read `libraries:` has it). Dropping the `PluginEntry` keep rule fails it with the shim's own error, so a bad rule shows up in `check`, not on a server. The shrunk `LoaderSandbox.jar` (35 KiB to 27 KiB) also passed `boot-test.sh` on Paper 1.21.11. xSample isn't shrunk: it has no jar or entry point until a platform adapter does.

## Security CI: CodeQL reads the Kotlin, Jazzer fuzzes the parsers (2026-11-24)

The security half of M1's tooling (#122, ROADMAP.md: "fuzzing for the markup, config ...; CodeQL for Kotlin").

- **CodeQL's `java-kotlin` analysis now builds the Kotlin too,** in the same traced Gradle run as the Java: `compileKotlin`/`compileKotlinJvm` and their tests, with Kotlin's compiler in-process (`kotlin.compiler.execution.strategy=in-process`, non-incremental), since CodeQL only sees a compiler that runs inside the traced build, not one in the Kotlin daemon. wasmWasi is left out: it has no JVM code to read. One language entry, so the Java analysis is unchanged.
- **Jazzer, not kotlinx.fuzz.** Jazzer's JUnit integration is plain JUnit 5 with no Gradle plugin of its own, and kotlinx.fuzz is a Gradle plugin built on Jazzer that's still marked experimental. Its fuzz tests live in their own module, `core/core-fuzz` (never shipped), which reads the markup through core-common and the config files through core-jvm's real YAML reader (`JvmYaml`) and core-common's loader (`Configs`). Keeping Jazzer's agent and JUnit 5 off core-jvm's test class path is a second reason for the module.
- **Each fuzz test is also a regression test.** In `test` (and so in `build`, which the Plugins workflow runs whenever the core changes), each `@FuzzTest` runs once per file in its committed corpus (`src/test/resources/.../<Class>Inputs/<method>/`): real messages and configs from today's plugins as seeds, and every crash found so far. `./gradlew :core:core-fuzz:fuzz -Pfuzz.duration=30s` fuzzes for real: one Gradle task per target, since Jazzer fuzzes one per JVM. The Fuzz workflow runs it for 10 s per target on pull requests that touch the core, and for 10 minutes every night. A crash fails the run and is uploaded, to be committed into the corpus with its fix.
- **What it found:** two stack overflows, both in "never throws" code. Markup rendered a tree as deep as its tags, so ten thousand `<b>`s overflowed the stack. The parser now opens at most 50 tags at once; deeper ones stay as text, and a placeholder that deep is still filled in, just without a shown-or-hidden part. snakeyaml-engine-kmp recurses once per level with no limit of its own, so about ten thousand `{a: ` overflowed it. `JvmYaml` now catches the overflow and reports "nested too deep to read" as a syntax error, keeping the last good config like any other. Regression tests are in `MarkupTest` and `JvmYamlTest`, and the inputs are in the corpus. Neither fuzzer found anything else in 5 minutes per target.

## The core on Bukkit: two APIs to compile against, every path picked by class checks (2026-11-24)

`core/platform-bukkit` implements the platform layer on Bukkit, Spigot, Paper and Folia from 1.8.8 to 26.3 (#122), and xSample runs on it as a Bukkit plugin (`core/core-testing/sample/bukkit`), loaded by the core's Java shim. What wasn't obvious:

- **One module, two source sets, both Java 8 class files.** `main` compiles against Spigot 1.8.8's API, so nothing there can call what the oldest server lacks; `modern` compiles against Paper 1.21.11's, for Folia's schedulers, Adventure sends, and Bukkit's 1.12 locale API and 1.11 `getEntity(UUID)`. Main calls `modern`'s classes directly, each from a small function of its own that runs only once a class check found the API, and the JVM loads a class only when it's first used, so a 1.8.8 server never loads them and nothing is found by reflection. `modern` stays Java 8 because Paper 1.16.5, which has Adventure, runs on Java 8; ROADMAP.md's "Paper-only code is Java 21" allows newer, nothing needed it. Main sees `modern`'s internal declarations through Kotlin's friend paths: `associateWith` would have put Paper's API on main's class path too.
- **What the server is, by its classes, once.** Folia by `RegionizedServer`, Paper by its config class (three names from 1.8.8 to today), Spigot by `SpigotConfig`, CraftBukkit otherwise; Adventure where `CommandSender` is an Adventure audience (Paper and Folia from 1.16.5, PandaSpigot); the rest by `getBukkitVersion()` (RGB colours from 1.16, copy-to-clipboard 1.15, `getEntity(UUID)` 1.11, `syncCommands` 1.13). Forks keep their name with the flavor after it: `Purpur 1.21.11 (Paper)`.
- **Folia's four schedulers, never Bukkit's there.** A place's and an entity's work need the world or the entity when they're scheduled: work for a world that isn't loaded can't run anywhere, so it's cancelled with a warning, and an entity that's already gone is retired at once. Folia disables plugins on its shutdown thread, once every region has stopped; that thread owns the whole server then, so `owns(Global)` says so there, or a development build's `ModuleSet.clear` would throw at every shutdown (found booting Folia 26.3).
- **Everywhere else, Bukkit's scheduler and async threads of our own.** Global, place and entity work go through Bukkit's scheduler, which Paper keeps running while an empty server is paused; entity work checks its entity before each run (players by UUID, other entities by `getEntity` from 1.11 and by looking through the worlds before) and retires it as Folia would. Async work doesn't use Bukkit's async scheduler, which starts tasks only on a tick, while the core promises exact async delays: one timer thread hands tasks to a pool that grows from nothing and shrinks back after a minute idle, a repeating task's next run counts from the end of the last so it never overlaps itself, and a task that throws is logged, as Bukkit's would be. On disable the pool gets five seconds to finish.
- **Text per server, both forms drawn at once for Spigot.** Adventure where it's native; Spigot's `BaseComponent[]` elsewhere on Spigot and its forks, except that from 1.21, where a component costs 12.7 µs to send against 4.6 µs for a `§` string (M0), a message with no click or hover goes as the string. A Spigot message is drawn to both forms once per language, since the console takes only the string (1.8.8's `CommandSender` has no `spigot()`). CraftBukkit, which has no component API, gets `§` strings.
- **Commands on Bukkit's command map, without Brigadier or Cloud yet.** One Bukkit command per root of the tree, registered at runtime under its name, aliases and `<plugin>:`, carrying the root's permission so 1.13+ clients aren't sent what they can't use, and answered and completed by the core's dispatcher. The command map and its names are reached the only way 1.8.8 allows, `getCommandMap()` on the server object and the `knownCommands` field (`getKnownCommands()` from 1.13), each looked up once. A reload re-registers only roots whose name, aliases, permission or description changed, unregistering key by key (Paper's map forwards to Brigadier, and its entry views may not remove), and on 1.13+ sends clients the new tree; at startup the server does that once every plugin is on. Registering through Cloud's Paper module, so clients get argument hints, means fetching Cloud per platform; that's for a later PR, and this direct way is `CommandRegistrar`'s first.
- **Permissions in Bukkit's plugin manager at runtime,** not `plugin.yml`, so a reload that changes a default or a child applies; a changed one is removed and added again, and a node another plugin declared is left as it is.
- **Events bridged as `XenaEvent`,** or `XenaCancellableEvent` for a pre-event, whose cancel is the core event's own flag. The two share one handler list, so a listener of `XenaEvent` hears both. Fired as an async Bukkit event off the server's threads, which Bukkit requires; not made at all when no Bukkit listener is registered. An API can pass its own factory for Bukkit event classes Skript can name.
- **Languages from the client, into the family's player cache.** `Player.getLocale()` from 1.12, with `PlayerLocaleChangeEvent` passed on at the player's next tick, on their thread, because it fires before the server stores the new locale; `player.spigot().getLocale()` before 1.12, where nothing says when the client's settings arrive, so the locale is read again two seconds after a join; none on CraftBukkit before 1.12, whose players read in `default-language`. `record(cache)` puts joins (name and locale), quits and changes in the `PlayerCache`, which is what messages read a player's language from; `locale(source)` gives a command source's for `AdminText.of`.
- **The family's board through `ServicesManager`.** `BukkitPlatform.family` is `plugins/Xena/` (a `FolderStorage`) and the board found under `ConcurrentMap.class`, or made by the first plugin; every plugin registers the same object again, at `Lowest`, so it outlives the first plugin's disable ("The family").
- **What `/<plugin> debug` asks of the platform:** `about()` (the Java running the server, the server's own version line and Bukkit's, the text path, the plugins installed), `dependency(name)` (installed and enabled), and `driverFetcher()`, an `OnDemandDriverFetcher` on the shim's own library cache and mirror settings, which `BukkitBootstrap.onDemandLibraries()` now exposes to the Kotlin side.
- **The Java shim stays in `core-loader`.** The loader's entry above expected it to move here once this module existed, but it must compile with no Kotlin on its class path, which only a Java module guarantees; a plugin's main class still extends `co.xenastudios.core.loader.bukkit.BukkitBootstrap`.
- **A plugin's folder is `FolderStorage`, in `core-jvm`,** for every JVM platform: a temporary file moved over the old one, disk errors as typed `StorageError`s.
- **Not here:** Paper's async chat, which comes with zChat's chat bridge (M3; the core has no chat interface yet), Brigadier, and shrinking: xSample's jar is 2.1 MB, the whole core unshrunk with the YAML parser (snakeyaml-engine-kmp, okio, urlencoder) shaded and relocated until packaging settles how it reaches servers and R8 is set up.
- **Booted** with `boot.sh` (xSample's `PlatformCheck` at startup, which also checks the board's registration, the family's file and the driver fetcher; console commands, `xsample debug` writing its report to `debug/`; a clean stop): Paper 26.3 and 1.21.11, Folia 26.3, Spigot 1.8.8 (Java 8 and 25), 1.12.2 (8), 1.13.2, 1.14.4 and 1.15.2 (11), 1.16.5 (16) and 1.21.11 (21), Paper 1.8.8 and 1.16.5, PandaSpigot 1.8.8, CraftBukkit 1.8.8 and 1.21.11. Enabling takes 50–330 ms with a cold JIT; Paper 1.21.11's is about 200–260 ms, M0's cost of its library class loader, over the 150 ms first-plugin budget, which the budget checks will measure properly.

## platform-fabric: a build of its own, Brigadier without Cloud, and Fabric API's callbacks only (2026-11-24)

The core on Fabric (#122), in `core/platform-fabric`, with xSample built on it as a Fabric mod (`sandbox/`) for boot tests. What wasn't obvious:

- **A Gradle build of its own, not a project of the root build.** Loom sets Minecraft up for every version while the build is configured (151 s cold in M0), so as a root project it would slow every build of today's plugins, and download Minecraft in every CI job that doesn't touch Fabric. It also adds repositories to its projects, which the root build's `FAIL_ON_PROJECT_REPOS` refuses. So `core/platform-fabric` has its own `settings.gradle.kts` (Stonecutter, loom-back-compat, the Kotlin version read from the root's catalog) and includes the root build for the core's modules, substituted by coordinates, so they're built from source there too. It runs as `./gradlew -p core/platform-fabric build`; the root build doesn't configure it at all, and `scripts/affected.sh` already skips a folder with its own settings. Configuration cache on, as in the root build.
- **One jar per Minecraft line, 1.20.1, 1.21.11 and 26.3,** as M0 settled, with the bytecode of each line's Java (17, 21, 25). A new line is a version in `settings.gradle.kts` and its block in `stonecutter.properties.toml` (Fabric API and fabric-permissions-api releases, each pinned to its Minecraft). Five names differ across the three, each a Stonecutter constant: click and hover events as records (1.21.5), `Identifier` (1.21.11), permission sets instead of op levels (1.21.11), and the client's options (1.20.2). fabric-language-kotlin's POM and fabric-permissions-api's metadata both name a Fabric API for a newer Minecraft, which would win over the line's own, so both are excluded from them.
- **Commands go straight onto Brigadier, not through cloud-fabric.** Cloud's Fabric module is pinned to one Minecraft version a release, has no release for 1.20.1, and is about 680 KB jar-in-jar (M0); the core's dispatcher already parses, checks and runs everything. Fabric API's command callback gives Minecraft's dispatcher, and Minecraft sends each player the tree they may use, so registering the shape is enough for the client's hints: a literal per node, a string per argument (a word, the last one the rest of the line) with our suggestions, every node running the whole line through our dispatcher, so a typed-short or mistyped command gets our usage line and errors. Strings rather than Brigadier's number types, because those would reject input with Brigadier's own message before ours, and an argument type of our own would need a client mod. A reload changes the running dispatcher in place and resends the tree, so command changes apply without a restart; Brigadier can't remove a node, so that one step reaches into its private maps, only on reload.
- **Permissions through fabric-permissions-api, with Bukkit's rules around it.** LuckPerms answers through it. Fabric has no registry for nodes, their defaults or their children, so the plugin's declarations live in the adapter: the permission mod's answer first, then a declared parent that grants or takes the node away, then the default by operator. An operator is level 2 (game masters), the console has every level. The API is jar-in-jar in each plugin's mod, as every mod using it ships it.
- **The core is inside each plugin's jar, not jar-in-jar.** Fabric Loader keeps only the newest copy of a nested jar across every mod, which would put one plugin on another's core; a plugin carries its own, as on Bukkit. xSample's jar is 2.1 MB with the whole of `core-common`, `core-jvm` and its YAML parser (snakeyaml-engine-kmp and okio, about 1.2 MB), unshrunk: R8 comes with the plugins' packaging. The stdlib comes from fabric-language-kotlin (M0).
- **No mixins.** Everything is Fabric API's callbacks (lifecycle, ticks, connections, commands) and Minecraft's own classes. The cost: Minecraft 1.20.1 doesn't keep a client's language (1.20.2 does), and reaching its packet needs a mixin, so on 1.20.1 players read `default-language`; and there's no event for a client changing language, so the family's cache compares the online players' languages every 5 seconds instead.
- **The family on Fabric is `config/xena/`, and its board is in Fabric Loader's `ObjectShare`** under `xena:board` ("The family"): the first Xena mod puts a new board there, the rest get it from `putIfAbsent`, and nothing there is dropped while the server runs, so unlike Bukkit's services one registration is enough. `FabricFamily` reads `config/xena/config.yml` as the mod starts, keeps the player cache in `config/xena/players.records`, and records joins, quits and language changes in it, which every plugin's messages read. A plugin that uses the family's shared database will pass the database's store instead.
- **The admin subcommands' platform pieces:** a command source's locale is its player's, from the family's cache; `/<plugin> debug` reports Java, the loader and Minecraft, and the mods installed (top-level ones: not Fabric API's parts or mods' nested libraries); `forget <name>` finds players through the cache's `asLookup()`. `debug` with no paste service writes `config/<mod>/debug/`.
- **JDBC drivers are fetched, not jar-in-jar.** Fabric ships no driver, so every database needs one, but sqlite-jdbc is about 13 MB with its native libraries for every system, too much to carry in every plugin. The loader's `OnDemandLibraries` knows no platform (only the Bukkit shim does), so `FabricPlatform.drivers` reads the mod's pinned list (`META-INF/xena/on-demand-libraries.txt`) and fetches into `config/xena/libraries/`, checked against the pin each time, with `-Dxena.libraries.mirror` as on Bukkit. xSample has no database, so it isn't exercised on a server yet, and the nested build can't apply `xena.fetched-libraries` to write the list: both come with the first plugin that has a database on Fabric.
- **The scheduler knows no Minecraft.** `TickScheduler` takes the server's thread, an entity check and the start of each tick as functions, so its rules are tested on the JVM: due tick then order, delays rounded up to ticks and never zero, work on an entity that's gone retired on the server thread, a task that throws logged without stopping the tick, and a small async pool of daemon threads that end when idle. Before the server starts, the thread that loaded the mods owns global work, and scheduled work waits for the first tick.
- **`FileStorage` is the adapter's own for now,** beside platform-bukkit's `FolderStorage` in `core-jvm` (#156): the same job, so one goes once both are merged.
- **Server events are the adapter's own for now.** Players joining and leaving and the server starting and stopping are fired on the platform's bus from Fabric API's callbacks; their types (`core:player_join` and the others) aren't Fabric's, and move to `core-common`, with the bus on `Platform`, when platform-bukkit fires the same ones.
- **Boot tests: `scripts/boot-fabric.sh`** boots a dedicated server from Fabric's launcher (or Quilt's installer with `--loader quilt`) with Fabric API and fabric-language-kotlin at the versions the line builds against, checked against Fabric's Maven checksums, runs `sandbox/boot-checks.txt` from the console (`debug` among them, writing its report), and fails on any error or a warning of ours. xSample passed it on Fabric 1.20.1 (Java 17), 1.21.11 (21) and 26.3 (25), and on Quilt Loader 0.30.2 at the same three; Quilt stands in as Fabric Loader 0.19.5, so a mod asks for Fabric Loader 0.16 or later rather than the version it builds against. CI doesn't run it yet. `:sandbox:<version>:runServer` is Loom's run, for development.

## One release workflow: every jar built once, attested, then each store alone (2026-11-24)

The rewrite's release (#122, ROADMAP.md's store table) replaces `release.yml` on `main`. Today's plugins keep releasing from `maintenance`, whose tags run that branch's own copy.

- **A plugin's build says what it releases.** `xena.release` in build-logic gives the project a tag names (`<plugin>-v<version>`) an `xenaRelease { jar("bukkit") { platform = ...; file = ...; minecraft("1.8.8") } }` list, one entry per jar (per Minecraft line for mods), and its store project ids. The workflow asks Gradle which project releases the tag's plugin (`releaseInfo`), so nothing in the workflow names a plugin or a platform. A range like `minecraft("1.8.8")` is every Minecraft release from there to `xena.ciNewestMinecraft`, from Modrinth's version list.
- **Built once, then only those bytes.** `releaseAssemble` puts the jars, `SHA256SUMS`, `release.json` (what each store gets) and the update posts in the project's `build/release`. The build job uploads that folder; the attest job signs the jars with `actions/attest-build-provenance`; every later job checks the checksums and publishes those files, never a rebuild.
- **Each store is its own job, with only its own token.** A matrix over Modrinth, Hangar, voxel.shop and CurseForge's three classes, each in the `release` environment with its one secret, so a failure reruns alone and a build script can't reach another store's token. The GitHub release and the attestations run no project code and are the only jobs that can write. Modrinth, Hangar and voxel.shop skip a version they have; CurseForge's upload API can't list files, so its jobs can't, and are only rerun when they failed.
- **Our own store tasks, plain HTTP, like `VoxelPublish`.** Modrinth puts loaders and game versions on a version, so each JVM jar is a version (`2.0.0+fabric-1.21.11` when there are several), which Minotaur's one upload per project can't do. Hangar gets one version with a file per platform (Paper, Velocity), its Minecraft versions narrowed to the ones Hangar lists (it has 1.8.8 but not 1.8.9). `CurseForgePublish` picks the host from the class (dev.bukkit, minecraft, legacy for Hytale) and looks the game-version ids up by type slug each release, leaving out versions a host doesn't list. voxel.shop's code is `VoxelPublish`'s, shared. Version type from the version: no suffix is a release, `-alpha…` an alpha, any other suffix a beta (Hangar's Snapshot channel, voxel.shop's beta flag, a GitHub prerelease).
- **SpigotMC and BuiltByBit get a post to paste:** the version, the GitHub download link for the listing's external download, and the changelog in BBCode, as release assets and in the run's summary. The summary also gives the brand catalog's name, summary, icon and banner for the hand-kept store pages; titles take the catalog's name.
- **A dry run is the same run, sending nothing.** `-Pxena.release.dryRun=true` (locally, `./gradlew <path>:release -Pxena.release.dryRun=true`), or running the workflow by hand with `dry-run` ticked: it builds, checksums and assembles as a release does, then each store task prints the exact request (tokens replaced) to the log and `build/release/dry-run/`, and the workflow puts them in its summary. It needs no token or approval; given `CURSEFORGE_TOKEN`, it also looks CurseForge's ids up, which is how the Hytale id gets checked. The loader sandbox (`core/core-loader/sandbox`) is the first plugin on it, for M1's dry-run exit.
- **Left for later:** CurseForge needs `CURSEFORGE_TOKEN` in the `release` environment and each plugin's project ids, and its tests use responses shaped from the docs until a real one is recorded. Store page syncs (Modrinth's body, Hangar's page) and Maven Central for the rewrite's APIs and Minestom modules aren't in it yet.

## Budgets: the YAML parser downloaded, R8 on the sample jars, the stdlib loaded off the server thread (2026-11-24)

The budgets in ROADMAP.md ("Fast, robust, light") measured and enforced for the rewrite (#122), with xSample on Bukkit and Fabric as the plugin under test. Every number is Paper 1.21.11 on Java 21 on an M1 Pro, median of 3 boots, from `scripts/budgets/check.sh`.

| xSample | Before | After |
|---|--:|--:|
| Bukkit jar | 2,113 KiB (parser shaded, no R8) | 477 KiB (R8) |
| Fabric jars, 1.20.1 / 1.21.11 / 26.3 | 2,088 / 2,090 / 2,038 KiB | 363 / 365 / 412 KiB |
| Startup on the server thread (server's `libraries:` and class loader, onLoad, onEnable) | 521 ms (100, 208, 192) | 271 ms (102, 21, 153) |
| Heap over the same server without it | 3.0 MB | 2.5 MB |
| Metaspace in its own class loader | 2.46 MB, 607 classes | 1.24 MB, 459 classes |

- **The YAML parser is downloaded, as the stdlib is.** snakeyaml-engine-kmp with okio and urlencoder was 870 KiB of every jar. A plugin now lists `snakeyaml-engine-kmp-jvm` under `fetched` (its two dependencies come with it, Kotlin excluded), so the three are pinned in `gradle/library-pins.txt` and listed in `META-INF/xena/libraries.txt`. plugin.yml's `libraries:` names the parser and the server resolves the other two from its POM; below 1.16.5 the loader downloads all three. They aren't relocated any more, so before 1.16.5 the family shares the first plugin's copy, as it does the stdlib's.
- **On Fabric the adapter fetches them as the mod starts, onto the game's class path.** `FabricLibraries` reads the mod's own list (through its mod container, so two mods never read each other's), takes each jar from `config/xena/libraries/` checked against its pin, and adds it with `FabricLauncherBase.getLauncher().addToClassPath`, before anything reads a file. That's Fabric Loader's internal launcher API, which Quilt's loader also has (checked on Quilt 0.30.2); if a loader drops it, the mod fails to start saying so, and jar-in-jar is the fallback. Not jar-in-jar now: every mod would carry the parser's 870 KiB, which the budgets don't allow. A library another Xena mod already added is left alone. The sandbox applies `xena.fetched-libraries` now, so the JDBC drivers' list is written too, which the platform-fabric entry left for later.
- **`xena.r8` on xSample's Bukkit jar and the Fabric sandbox's.** The Fabric build includes build-logic (`pluginManagement`), reads the root's catalog, and sets `xena.repoRoot` and `xena.projectPrefix` (gradle.properties) so the conventions find `gradle/jar-budgets.txt` and the pins, and its jars' budget lines read `:core:platform-fabric:sandbox:1.21.11`. The conventions are loaded once at its root project, or each node would load the Kotlin Gradle plugin again. R8 runs on the jar in Mojang's names, before Loom remaps it; 26.1 and later ship the shrunk jar as it is. New keep rules in `common.pro`: Bukkit events keep their names and `getHandlerList()`, and `PluginEntry.load()` keeps its name, which the shim checks for. Bukkit's R8 run sees Paper's API as a library, for the modern paths and Adventure.
- **Startup: Paper passes every class through ASM, and the stdlib's are big.** Profiling the boot (async-profiler from the JVM's start, and `-XX:LogClassLoadingCauseFor`) showed class loading was most of it: Paper's `BytecodeModifyingURLClassLoader` reads and rewrites each class from `libraries:` for reflection remapping, and Commodore each of the plugin's own. The first `listOf` loads all of `ArraysKt`, 800 KiB of class files, and the stdlib's facades together are 2 MiB. So the shim now loads the plugin's entry point at onLoad without making it, starts a daemon thread that loads (without initializing) the stdlib's biggest classes, and makes the entry point at onEnable, after the server has prepared its worlds; an entry point with its own `load()` is still made at onLoad. onLoad went from 208 ms to 21. JvmYaml's settings and the English formats `AdminText` keeps are now made on first use, off the server thread.
- **Startup is still over its budget: 271 ms against 150.** What's left: Paper resolving `libraries:` with Maven's resolver at every boot (about 100 ms, the same for one library or two), and onEnable defining about 450 of the plugin's classes through Commodore. Measured, not shipped: loading the jar's own classes on the same thread took onEnable from about 145 ms to 95, but loads classes of modules that are off, which the roadmap rules out; a list of the classes a plugin needs at startup, written at build time, would do it properly. Loading the stdlib ourselves on Paper rather than through `libraries:` would skip both the resolver and the rewriting, but needs the JDK's trusted lookup on a modern server, which the loader keeps as a fallback. Both are for the plugins' packaging, before xUtilities.
- **Metaspace counts the plugin's own class loader.** The stdlib's and the parser's (Paper's library loader: 2.7 MB, 314 classes) are reported but not budgeted, as the 150 ms first-plugin allowance treats the stdlib: on Paper each plugin has its own copy, so ROADMAP.md's 1.5 MB can't include it.
- **The runtime budgets: `scripts/budgets/check.sh`,** M0's method as a check (sandbox/m0/budgets): a server without plugins for the heap baseline, a first boot, timed boots, then a measured boot for heap, metaspace, a 60 s idle profile and 60 s of 10 mineflayer bots (`scripts/budgets/bots`, M0's BotMark with the plugin's commands passed in), profiled with async-profiler 4.6 at 200 µs (pinned by SHA-256 for Linux and macOS; Spark's profiles go to its web viewer, which a check can't read). Paper's pause on an empty server is off, since a paused server doesn't tick. The limits are `gradle/perf-budgets.txt`. Startup is read from Paper's library lines and the shim's own `Startup times` line (`-Dxena.startupTimes=true`), because the log can't show where the last plugin's enable ends. Exit 0 within budget, 1 over, 2 usage, 3 when the measurement failed, for the boot matrix's workflow. Several jars measure the family; the first enabled gets 150 ms.
- **The hot paths: JMH in `core/core-benchmarks`,** markup parse and render, messages drawn per language to Adventure and to Spigot's components, the event bus, commands and config reads and loads. `checkBenchmarks` runs a short JMH pass and checks `budgets.txt`: bytes allocated per call (JMH's `gc` profiler) at today's plus a quarter, or 16 where today's is none, and times at five times today's, since those move with the machine. JMH runs through its own generator and main class rather than a Gradle plugin: kotlinx-benchmark and the JMH plugin both call `Configuration.setVisible`, which Gradle 10 removes. Today: a kept message 3.5 ns and nothing allocated, one with placeholders 690 ns and 3.3 KB (Adventure) or 840 ns and 4 KB (Spigot); a command 670 ns and 1.6 KB; firing to three listeners 11 ns and nothing; parsing a message 2.9 µs; a config read 2.7 ns.
- **One storage class.** Fabric uses `core-jvm`'s `FolderStorage`; its `FileStorage` is gone, as the platform-fabric entry planned.
- **xTwin, the family test's second plugin, is built the same way.** On Bukkit it fetches the parser and is shrunk with R8 (387 KiB, budget 420), so the family test boots two R8 jars. Its Fabric mod fetches the parser too, so the family test also checks two mods sharing one copy on the game's class path, but isn't shrunk: Shadow relocates its core after Loom's remap, and R8 would have to run between the two for a jar that never ships, so it has no budget line.
- **In the Boot workflow** (`.github/workflows/boot.yml`): `build-bukkit` checks both R8 jars' budgets and uploads them from `build/r8/`, where `boot.sh` looks; `build-fabric`'s `build` already checks the sandbox's. A `benchmarks` job runs `checkBenchmarks`. Both feed `boot-ok`.
