# xBackup: a content-addressed store, read twice, restored on start (2026-11-18)

xBackup (#23) keeps backups in a small restic-like repository it writes itself: every blob named by its SHA-256, grouped into immutable packs (data and structure in separate packs), index files saying which pack holds which blob, and one text file per snapshot, written last. Nothing is changed in place: a backup writes packs, then their index, then its snapshot, each flushed before the next, so a crash leaves at worst unreferenced packs for garbage collection. Every pack ends with a footer listing its blobs, so the index can always be rebuilt from the packs. Proven by `CrashTest` (operations killed at random writes with no clean-up allowed, 160 rounds) and `KillTest` (a second JVM SIGKILLed mid-backup).

- **Region files chunk by chunk.** Each chunk's record (length, compression byte, payload) is its own blob, and a region's layout (where each chunk sits, its timestamp, its blob) is another. A chunk whose location and timestamp are unchanged is reused from 8 bytes of header. That's safe because the server writes a moved chunk to new sectors before pointing the header at them and never writes into sectors the header points at, so a chunk read between two identical header reads is consistent. A header that doesn't add up is kept as a whole file. Restores put every record back at its offset with zeroed padding: Minecraft reads the same file, and a real 26.3 round trip matched 1,611 of 1,612 chunks byte for byte (the other was written after the backup).
- **Read twice.** M0 settled the pause: `setAutoSave(false)` stops all world writes, `World#save(true)` flushes (per region on its own thread on Folia; from the global thread it throws or silently saves nothing). The worlds are read first with the server saving as usual, then, during the pause, only what changed since. Autosave is off for under a second even on a first backup. Worlds whose owner turned autosave off are neither flushed nor turned on. The worlds actually turned off are remembered under one lock with a "still wanted" flag, and every end (finally, the watchdog, disable) turns exactly those back on, so a late main-thread step can never leave autosave off. On Paper, xBackup's main-thread steps go through the core's `Tasks.nextTick`, which uses the Bukkit scheduler there, not the global region scheduler: with nobody online Paper pauses after `pause-when-empty-seconds`, and its paused tick runs `CraftScheduler#mainThreadHeartbeat` but skips `tickChildren`, where the global region scheduler ticks (read from 1.21.11's and 26.3's `MinecraftServer#tickServer`, and seen on a real server: global-region tasks waited until someone joined). Folia doesn't pause when empty.
- **SQLite by SQLite.** The plan had family plugins pause their writers for a "quiet moment" through the core. Instead, any SQLite file is copied with `VACUUM INTO` through Paper's driver: one consistent read transaction, no cooperation needed, and nothing added to the core. A database that can't be copied that way keeps its last good copy; its raw bytes are never copied. The API's `QuietMoment` remains for plugins with multi-step flat files.
- **The index is a table of parallel arrays**, about 65 bytes a blob, held only while a job runs. Garbage collection marks with a map of 8-byte prefixes (a clash keeps garbage, never deletes data), runs at most daily, and repacks mostly-dead packs: new packs and a fresh index are written before any old file is deleted.
- **Restores swap from the bootstrap, all or nothing.** Staged files are checked against their hashes, then a journal drives the swap on the next start (or straight away from the command line), each step repeatable, so a crash part way is finished next time. Every staged copy is checked before anything moves. A step that fails moves everything back, including what an earlier run cut off by a crash had put in place (every entry journaled as set aside or done), and keeps the journal as `restore/failed`, so a later start never swaps it in by surprise; if moving back fails too, the bootstrap halts the server rather than let it load or generate a half-swapped world. Restores write only inside their folder, through no links, and refuse links leading outside the server folder. The command line refuses while xBackup's `running.lock` (OS-locked from bootstrap until the process exits, since Paper saves worlds after plugins disable) or any world's `session.lock` is held, looking in the restored folders, a few folders deep, and `bukkit.yml`'s `world-container`. An in-place restore takes `running.lock` itself for its whole run and checks the `session.lock`s again just before it swaps; a bootstrap that finds `running.lock` taken halts the server, since staging can take hours. Paths are resolved from the working directory, which is the server folder.
- **One job at a time** on one low-priority worker thread, with an OS file lock on the repository so the command line and the server never write at once. The only timer is the schedule, set again after each backup; checks and clean-ups ride along.
- **Remotes are mirrors.** Packs are immutable, so a backend only needs put, get, list and delete; copies send what's missing (packs, then indexes, then snapshots) and refuse a remote holding a different repository. A copy deletes from the remote only snapshots the repository removed on purpose (noted in a local `forgotten` file, never copied) and older than its newest, and only packs garbage collection deleted on purpose (noted in `collected` before they go), when every snapshot left on the remote is also local. "Not in the local index" never means "unused": a pack that went missing here is noted in `lost`, which a copy never deletes, and the remote keeps its own index files while it keeps such a pack. GC drops missing packs before marking and takes back unindexed packs holding needed blobs. `/backup copy <remote> tidy` is the owner's way to remove what only the remote has, after a confirmation. Local damage, a rolled-back disk, or an empty repository deletes nothing. S3 is SigV4 by hand on `java.net.http` (checked against AWS's published example); WebDAV and the drives are plain REST with a small JSON reader, because the command-line restore has no Gson.
- **Remote secrets live in `secrets.yml`, not `config.yml`.** Owners share their config for help, and xBackup backs it up and copies it to every remote. Passwords and client secrets go in an owner-only `secrets.yml`, which is never backed up, nor are SFTP keys, tokens and the command line's settings file. The command line reads `secrets.yml` itself (a small two-level YAML reader, since it has no SnakeYAML) rather than keeping a copy of the passwords, and drive tokens live in an owner-only `tokens.yml`. S3 uploads still send `Content-MD5`: buckets with Object Lock require it, and it's only a check against damage in transit. Any found in `config.yml` are moved there each time the config loads, before its first load at startup.
- **SFTP and FTP libraries are fetched by xBackup, not Paper's library loader.** The issue planned Paper's loader. It resolves only at startup, so a remote added on reload would need a restart, and the command-line restore has no Paper at all. xBackup downloads JSch or Commons Net (one dependency-free jar each, Google's mirror of Maven Central first, then Maven Central) only when a remote of that type is used, checks a pinned SHA-256 (`LibrariesTest` fails if the catalog version moves without it), and loads the code that uses it through its own class loader: xBackup's `remote.lib` classes only from xBackup's jar, the library's only from its jar.
