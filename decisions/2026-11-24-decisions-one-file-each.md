# Decisions one file each, and rewrite-only pull requests skip today's boots (2026-11-24)

Merging a run of pull requests was slow for two reasons, and each is fixed where it starts.

**DECISIONS.md conflicted with every open pull request.** It was one file: a table of every decision at the top, then each entry, oldest first, and every pull request added a row and an entry at the end. So each merge left every other open pull request in conflict, which meant a rebase and every check again. Now each decision is a file in `decisions/`, `<date>-<slug>.md`, with the entry's text as it was, and DECISIONS.md is an index that `node scripts/decisions.ts` writes from them: one row per decision, by date then file name, each row carrying the anchor its heading had (`<a id>`), so a `DECISIONS.md#...` link from an issue or a commit still lands on its decision.

The index is committed, so DECISIONS.md still reads as the list of every decision on GitHub, but a pull request that adds a decision doesn't touch it: two pull requests adding a row each at its end would conflict just as the entries did. The Docs workflow's `--check` lets the index lag instead. It fails on a misnamed decision file or a row that's wrong, out of order or for a file that's gone, and only notes the decisions with no row yet; release pull requests (`scripts/release.ts`) rewrite the index, as they do the plugin catalog, and so can anyone with the one command. Until the next release, the newest decisions are in `decisions/` alone, which GitHub lists by date, since the names start with it. Two other ways were weighed: not committing the index at all, generating it only for readers, would lose the anchors old links point at and leave GitHub with a folder listing as the only list; a merge driver that keeps both sides (`merge=union`) only helps a local rebase, since GitHub's own merge check doesn't run custom drivers. Within a day, rows are by file name rather than the order they were decided in, since a file can't know that. The site doesn't read DECISIONS.md, so nothing there changed. Comments in code that cite "DECISIONS.md, <title>" still point at the right place: the index lists every decision by title.

**A pull request touching only the rewrite waited on today's plugins' boots.** `plugins-ok` waits on the Plugins workflow's boots of today's Java plugins on Paper and Folia, at 1.21.11 and the newest, and `scripts/affected.sh` ran them for any change to `build-logic/`, `gradle/` or `scripts/`, even the parts only the rewrite uses. Today's plugins build on today's core (`core/src`) and three conventions, `xena.plugin`, `xena.api` and `xena.java`, with the classes those use (`XenaPluginExtension`, `Stores`, `StorePublish`, `VoxelPublish`, `Upload`, `Release`, `BbCode`, `CurseForgePublish`, `ApiSignatures`). The rest of `build-logic/` (`xena.kmp`, `xena.kotlin-jvm`, `xena.r8`, `xena.fabric-mod` and the others, with their classes) is the rewrite's, as are `gradle/jar-budgets.txt`, `gradle/library-pins.txt` and `gradle/perf-budgets.txt`, `scripts/budgets/`, `scripts/boot-seeds/`, `scripts/boot-fabric.sh` and `scripts/new-rewrite-plugin.ts`. A change to those now builds and tests the rewrite's modules and boots the rewrite (the Boot workflow), and skips today's plugins' builds, newest-API compile and boots. `scripts/decisions.ts` and the decisions mean nothing to either.

It stays on the safe side. The rewrite's files are listed by name in `affected.sh`, so a new file in `build-logic/` or `scripts/` means everything until someone lists it. A file of the rewrite's that today's conventions start to use would make the list wrong, so `scripts/affected-test.sh`, which the Plugins workflow runs first, works out what today's conventions reach in `build-logic/` (every class, object and function each file declares, followed from those three files) and fails if any of it is on the rewrite's list; it also checks what runs for each kind of change. A change to `build-logic/`'s own build, the version catalog, `gradle.properties`, the wrapper, the root build files, `scripts/boot-test.sh` (which both workflows boot with) or the Plugins workflow still means everything. If the rewrite's conventions break the build of `build-logic/` itself, the rewrite's own build, which still runs, fails on it.
