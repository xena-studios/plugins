# Fabric jars relocate their core: one convention, relocation then R8 then Loom (2026-11-24)

Every Xena Fabric mod now carries its core under its own package, as every Bukkit plugin does (#162). Fabric loads all mods in one class loader, so before this two Xena mods shared whichever copy of `co.xenastudios.core` loaded first, and R8 didn't help: it keeps the names its rules keep (the core's API, `co.xenastudios.**.api.**`, and what `fabric.mod.json` names), so those stayed shared.

- **`xena.fabric-mod` in build-logic is how a mod is packaged.** A plugin's Fabric module applies it after Loom and says its id: `plugins { id("dev.kikugie.loom-back-compat"); kotlin("jvm"); id("xena.fabric-mod") }` and `xenaFabricMod { id = "xutilities" }`, then puts the adapter, the core and its shared code in `bundle`. It applies `xena.r8` and `xena.fetched-libraries` and owns the `bundle` configuration, the jar's contents, R8's input, libraries and package, Loom's remap input and `collect`, which xSample's and xTwin's builds each spelled out before.
- **The order: relocate, then R8, then Loom.** `relocateJar` (Shadow's task type, without its plugin) moves `co.xenastudios.core` to `co.xenastudios.<id>.core` in the jar in Mojang's names; `shrinkJar` runs R8 on that, renaming into `co.xenastudios.<id>.r8`; below 26.1, `remapJar` maps the shrunk jar to intermediary; from 26.1 the shrunk jar ships. Relocating first means R8's keep rules (`co.xenastudios.**.api.**`) and Loom both see the final names, and nothing rewrites R8's output after it, so its mapping file is the shipped jar's. xTwin relocated after Loom's remap before, which left no room for R8 (DECISIONS' budgets entry); Loom maps only Minecraft's names, so it doesn't care which of ours it sees. Loom's task type isn't on build-logic's class path, so its input is set by property name.
- **A mod's entry point lives in its plugin's package, not the core's.** xSample's moved from `co.xenastudios.core.fabric.sandbox` to `co.xenastudios.xsample.fabric`, as xTwin's (`co.xenastudios.xtwin.fabric`) and every plugin's (`co.xenastudios.<id>.fabric`) are, so relocating the core never moves what `fabric.mod.json` names.
- **Jar budgets for every mod.** xTwin's Fabric jars are now shrunk too and have lines (`:core:platform-fabric:twin:<line>`): 322, 324 and 366 KiB for 1.20.1, 1.21.11 and 26.3. xSample's are unchanged in size (363, 366, 413 KiB). Neither has a class under `co.xenastudios.core` any more.
- **Booted:** the family test on Fabric 1.20.1 and 26.3 passes with both mods relocated and shrunk, each finding the one board in the object share.
