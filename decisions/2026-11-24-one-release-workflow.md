# One release workflow: every jar built once, attested, then each store alone (2026-11-24)

The rewrite's release (#122, ROADMAP.md's store table) replaces `release.yml` on `main`. Today's plugins keep releasing from `maintenance`, whose tags run that branch's own copy.

- **A plugin's build says what it releases.** `xena.release` in build-logic gives the project a tag names (`<plugin>-v<version>`) an `xenaRelease { jar("bukkit") { platform = ...; file = ...; minecraft("1.8.8") } }` list, one entry per jar (per Minecraft line for mods), and its store project ids. The workflow asks Gradle which project releases the tag's plugin (`releaseInfo`), so nothing in the workflow names a plugin or a platform. A range like `minecraft("1.8.8")` is every Minecraft release from there to `xena.ciNewestMinecraft`, from Modrinth's version list.
- **Built once, then only those bytes.** `releaseAssemble` puts the jars, `SHA256SUMS`, `release.json` (what each store gets) and the update posts in the project's `build/release`. The build job uploads that folder; the attest job signs the jars with `actions/attest-build-provenance`; every later job checks the checksums and publishes those files, never a rebuild.
- **Each store is its own job, with only its own token.** A matrix over Modrinth, Hangar, voxel.shop and CurseForge's three classes, each in the `release` environment with its one secret, so a failure reruns alone and a build script can't reach another store's token. The GitHub release and the attestations run no project code and are the only jobs that can write. Modrinth, Hangar and voxel.shop skip a version they have; CurseForge's upload API can't list files, so its jobs can't, and are only rerun when they failed.
- **Our own store tasks, plain HTTP, like `VoxelPublish`.** Modrinth puts loaders and game versions on a version, so each JVM jar is a version (`2.0.0+fabric-1.21.11` when there are several), which Minotaur's one upload per project can't do. Hangar gets one version with a file per platform (Paper, Velocity), its Minecraft versions narrowed to the ones Hangar lists (it has 1.8.8 but not 1.8.9). `CurseForgePublish` picks the host from the class (dev.bukkit, minecraft, legacy for Hytale) and looks the game-version ids up by type slug each release, leaving out versions a host doesn't list. voxel.shop's code is `VoxelPublish`'s, shared. Version type from the version: no suffix is a release, `-alpha…` an alpha, any other suffix a beta (Hangar's Snapshot channel, voxel.shop's beta flag, a GitHub prerelease).
- **SpigotMC and BuiltByBit get a post to paste:** the version, the GitHub download link for the listing's external download, and the changelog in BBCode, as release assets and in the run's summary. The summary also gives the brand catalog's name, summary, icon and banner for the hand-kept store pages; titles take the catalog's name.
- **A dry run is the same run, sending nothing.** `-Pxena.release.dryRun=true` (locally, `./gradlew <path>:release -Pxena.release.dryRun=true`), or running the workflow by hand with `dry-run` ticked: it builds, checksums and assembles as a release does, then each store task prints the exact request (tokens replaced) to the log and `build/release/dry-run/`, and the workflow puts them in its summary. It needs no token or approval; given `CURSEFORGE_TOKEN`, it also looks CurseForge's ids up, which is how the Hytale id gets checked. The loader sandbox (`core/core-loader/sandbox`) is the first plugin on it, for M1's dry-run exit.
- **Left for later:** CurseForge needs `CURSEFORGE_TOKEN` in the `release` environment and each plugin's project ids, and its tests use responses shaped from the docs until a real one is recorded. Store page syncs (Modrinth's body, Hangar's page) and Maven Central for the rewrite's APIs and Minestom modules aren't in it yet.
