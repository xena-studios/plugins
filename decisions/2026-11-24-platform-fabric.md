# platform-fabric: a build of its own, Brigadier without Cloud, and Fabric API's callbacks only (2026-11-24)

The core on Fabric (#122), in `core/platform-fabric`, with xSample built on it as a Fabric mod (`sandbox/`) for boot tests. What wasn't obvious:

- **A Gradle build of its own, not a project of the root build.** Loom sets Minecraft up for every version while the build is configured (151 s cold in M0), so as a root project it would slow every build of today's plugins, and download Minecraft in every CI job that doesn't touch Fabric. It also adds repositories to its projects, which the root build's `FAIL_ON_PROJECT_REPOS` refuses. So `core/platform-fabric` has its own `settings.gradle.kts` (Stonecutter, loom-back-compat, the Kotlin version read from the root's catalog) and includes the root build for the core's modules, substituted by coordinates, so they're built from source there too. It runs as `./gradlew -p core/platform-fabric build`; the root build doesn't configure it at all, and `scripts/affected.sh` already skips a folder with its own settings. Configuration cache on, as in the root build.
- **One jar per Minecraft line, 1.20.1, 1.21.11 and 26.3,** as M0 settled, with the bytecode of each line's Java (17, 21, 25). A new line is a version in `settings.gradle.kts` and its block in `stonecutter.properties.toml` (Fabric API and fabric-permissions-api releases, each pinned to its Minecraft). Five names differ across the three, each a Stonecutter constant: click and hover events as records (1.21.5), `Identifier` (1.21.11), permission sets instead of op levels (1.21.11), and the client's options (1.20.2). fabric-language-kotlin's POM and fabric-permissions-api's metadata both name a Fabric API for a newer Minecraft, which would win over the line's own, so both are excluded from them.
- **Commands go straight onto Brigadier, not through cloud-fabric.** Cloud's Fabric module is pinned to one Minecraft version a release, has no release for 1.20.1, and is about 680 KB jar-in-jar (M0); the core's dispatcher already parses, checks and runs everything. Fabric API's command callback gives Minecraft's dispatcher, and Minecraft sends each player the tree they may use, so registering the shape is enough for the client's hints: a literal per node, a string per argument (a word, the last one the rest of the line) with our suggestions, every node running the whole line through our dispatcher, so a typed-short or mistyped command gets our usage line and errors. Strings rather than Brigadier's number types, because those would reject input with Brigadier's own message before ours, and an argument type of our own would need a client mod. A reload changes the running dispatcher in place and resends the tree, so command changes apply without a restart; Brigadier can't remove a node, so that one step reaches into its private maps, only on reload.
- **Permissions through fabric-permissions-api, with Bukkit's rules around it.** LuckPerms answers through it. Fabric has no registry for nodes, their defaults or their children, so the plugin's declarations live in the adapter: the permission mod's answer first, then a declared parent that grants or takes the node away, then the default by operator. An operator is level 2 (game masters), the console has every level. The API is jar-in-jar in each plugin's mod, as every mod using it ships it.
- **The core is inside each plugin's jar, not jar-in-jar.** Fabric Loader keeps only the newest copy of a nested jar across every mod, which would put one plugin on another's core; a plugin carries its own, as on Bukkit. xSample's jar is 2.1 MB with the whole of `core-common`, `core-jvm` and its YAML parser (snakeyaml-engine-kmp and okio, about 1.2 MB), unshrunk: R8 comes with the plugins' packaging. The stdlib comes from fabric-language-kotlin (M0).
- **No mixins.** Everything is Fabric API's callbacks (lifecycle, ticks, connections, commands) and Minecraft's own classes. The cost: Minecraft 1.20.1 doesn't keep a client's language (1.20.2 does), and reaching its packet needs a mixin, so on 1.20.1 players read `default-language`; and there's no event for a client changing language, so the family's cache compares the online players' languages every 5 seconds instead.
- **The family on Fabric is `config/xena/`, and its board is in Fabric Loader's `ObjectShare`** under `xena:board` ("The family"): the first Xena mod puts a new board there, the rest get it from `putIfAbsent`, and nothing there is dropped while the server runs, so unlike Bukkit's services one registration is enough. `FabricFamily` reads `config/xena/config.yml` as the mod starts, keeps the player cache in `config/xena/players.records`, and records joins, quits and language changes in it, which every plugin's messages read. A plugin that uses the family's shared database will pass the database's store instead.
- **The admin subcommands' platform pieces:** a command source's locale is its player's, from the family's cache; `/<plugin> debug` reports Java, the loader and Minecraft, and the mods installed (top-level ones: not Fabric API's parts or mods' nested libraries); `forget <name>` finds players through the cache's `asLookup()`. `debug` with no paste service writes `config/<mod>/debug/`.
- **JDBC drivers are fetched, not jar-in-jar.** Fabric ships no driver, so every database needs one, but sqlite-jdbc is about 13 MB with its native libraries for every system, too much to carry in every plugin. The loader's `OnDemandLibraries` knows no platform (only the Bukkit shim does), so `FabricPlatform.drivers` reads the mod's pinned list (`META-INF/xena/on-demand-libraries.txt`) and fetches into `config/xena/libraries/`, checked against the pin each time, with `-Dxena.libraries.mirror` as on Bukkit. xSample has no database, so it isn't exercised on a server yet, and the nested build can't apply `xena.fetched-libraries` to write the list: both come with the first plugin that has a database on Fabric.
- **The scheduler knows no Minecraft.** `TickScheduler` takes the server's thread, an entity check and the start of each tick as functions, so its rules are tested on the JVM: due tick then order, delays rounded up to ticks and never zero, work on an entity that's gone retired on the server thread, a task that throws logged without stopping the tick, and a small async pool of daemon threads that end when idle. Before the server starts, the thread that loaded the mods owns global work, and scheduled work waits for the first tick.
- **`FileStorage` is the adapter's own for now,** beside platform-bukkit's `FolderStorage` in `core-jvm` (#156): the same job, so one goes once both are merged.
- **Server events are the adapter's own for now.** Players joining and leaving and the server starting and stopping are fired on the platform's bus from Fabric API's callbacks; their types (`core:player_join` and the others) aren't Fabric's, and move to `core-common`, with the bus on `Platform`, when platform-bukkit fires the same ones.
- **Boot tests: `scripts/boot-fabric.sh`** boots a dedicated server from Fabric's launcher (or Quilt's installer with `--loader quilt`) with Fabric API and fabric-language-kotlin at the versions the line builds against, checked against Fabric's Maven checksums, runs `sandbox/boot-checks.txt` from the console (`debug` among them, writing its report), and fails on any error or a warning of ours. xSample passed it on Fabric 1.20.1 (Java 17), 1.21.11 (21) and 26.3 (25), and on Quilt Loader 0.30.2 at the same three; Quilt stands in as Fabric Loader 0.19.5, so a mod asks for Fabric Loader 0.16 or later rather than the version it builds against. CI doesn't run it yet. `:sandbox:<version>:runServer` is Loom's run, for development.
