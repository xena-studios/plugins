# Security CI: CodeQL reads the Kotlin, Jazzer fuzzes the parsers (2026-11-24)

The security half of M1's tooling (#122, ROADMAP.md: "fuzzing for the markup, config ...; CodeQL for Kotlin").

- **CodeQL's `java-kotlin` analysis now builds the Kotlin too,** in the same traced Gradle run as the Java: `compileKotlin`/`compileKotlinJvm` and their tests, with Kotlin's compiler in-process (`kotlin.compiler.execution.strategy=in-process`, non-incremental), since CodeQL only sees a compiler that runs inside the traced build, not one in the Kotlin daemon. wasmWasi is left out: it has no JVM code to read. One language entry, so the Java analysis is unchanged.
- **Jazzer, not kotlinx.fuzz.** Jazzer's JUnit integration is plain JUnit 5 with no Gradle plugin of its own, and kotlinx.fuzz is a Gradle plugin built on Jazzer that's still marked experimental. Its fuzz tests live in their own module, `core/core-fuzz` (never shipped), which reads the markup through core-common and the config files through core-jvm's real YAML reader (`JvmYaml`) and core-common's loader (`Configs`). Keeping Jazzer's agent and JUnit 5 off core-jvm's test class path is a second reason for the module.
- **Each fuzz test is also a regression test.** In `test` (and so in `build`, which the Plugins workflow runs whenever the core changes), each `@FuzzTest` runs once per file in its committed corpus (`src/test/resources/.../<Class>Inputs/<method>/`): real messages and configs from today's plugins as seeds, and every crash found so far. `./gradlew :core:core-fuzz:fuzz -Pfuzz.duration=30s` fuzzes for real: one Gradle task per target, since Jazzer fuzzes one per JVM. The Fuzz workflow runs it for 10 s per target on pull requests that touch the core, and for 10 minutes every night. A crash fails the run and is uploaded, to be committed into the corpus with its fix.
- **What it found:** two stack overflows, both in "never throws" code. Markup rendered a tree as deep as its tags, so ten thousand `<b>`s overflowed the stack. The parser now opens at most 50 tags at once; deeper ones stay as text, and a placeholder that deep is still filled in, just without a shown-or-hidden part. snakeyaml-engine-kmp recurses once per level with no limit of its own, so about ten thousand `{a: ` overflowed it. `JvmYaml` now catches the overflow and reports "nested too deep to read" as a syntax error, keeping the last good config like any other. Regression tests are in `MarkupTest` and `JvmYamlTest`, and the inputs are in the corpus. Neither fuzzer found anything else in 5 minutes per target.
