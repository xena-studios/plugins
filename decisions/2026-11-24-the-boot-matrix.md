# The boot matrix: every server the rewrite ships for, forks from their own downloads, and a second plugin for the family (2026-11-24)

The CI half of M1's boot tests (#122): `.github/workflows/boot.yml` boots xSample on each server the rewrite ships for, and the family test boots it beside a second plugin. What wasn't obvious:

- **A workflow of its own, with one check to require, `boot-ok`.** The Plugins workflow boots today's plugins on Paper and Folia from one job's jars; the rewrite's jars come from two builds (the root build for Bukkit, platform-fabric's own for Fabric) and Spigot's servers from BuildTools, so they share nothing. `boot-ok` works as `plugins-ok`: it passes when each job passed or was skipped because nothing it covers changed, and fails when any failed, except a cell allowed to fail.
- **Per pull request, the touched platforms at their floor and newest; the whole matrix nightly and by hand.** `scripts/affected.sh` has a `boot` output: `core/platform-fabric/` means Fabric; `core/platform-bukkit/`, the loader and the samples' `bukkit/` folders mean Bukkit; any other module of the rewrite means both, as does everything that means everything (the root build's files, `gradle/`, `scripts/`) and the workflow itself. Bukkit's pair is Spigot 1.8.8 on Java 8 and Paper's newest, Fabric's its oldest and newest lines (1.20.1, 26.3, read from platform-fabric's Stonecutter versions), with the family test on Paper, Spigot 1.8.8 and Fabric's newest. Nightly adds Folia, Spigot 1.13.2, 1.16.5 and the newest, PandaSpigot, Leaf, Leaves, ShreddedPaper, Canvas and Quilt, and refreshes the server caches pull requests read from the default branch. Not chosen: every cell on every pull request (14 boots, and a cold BuildTools run is minutes each).
- **Each server on the newest Java it accepts, from its version** (`scripts/server-jar.sh`): 8 below 1.13, 11 to 1.15, 16 for 1.16, 17 to 1.20.4, 21 to 1.21.x, 25 from 26.1; PandaSpigot on 21, as M0 ran it. So Spigot 1.8.8 runs on 8, 1.13.2 on 11, 1.16.5 on 16, as Spigot's launcher refuses anything newer.
- **Spigot from BuildTools, built once per version and build.** The cache key is the version, Spigot's build of it (`hub.spigotmc.org/versions/<version>.json`) and BuildTools' Jenkins build, so a new Spigot or BuildTools build rebuilds the jar once, and only then does BuildTools run, on Java 8 up to 1.16.5 and 25 for the newest. Spigot's Jenkins records no fingerprint for `BuildTools.jar` (only for the Maven module's unshaded jar), so it's fetched over HTTPS from the build the key names, and its SHA-256 is logged; BuildTools checks what it downloads itself.
- **The forks from their own download APIs, checked against the SHA-256 each publishes:** PandaSpigot from `downloads.hpfxd.com`, Leaves from `api.leavesmc.org` (its newest is 1.21.11, on Java 21), ShreddedPaper from `api.multipaper.io`, Leaf from its GitHub releases (one per Minecraft version, `ver-26.3`, with GitHub's digest). Each boots with the jar of the platform it comes from, xSample's Bukkit jar, at the fork's own newest. Canvas has no stable download: `api.canvasmc.io` answers 525, its Jenkins records no checksums and refuses GitHub's runners (403), so its cell takes the last good Jenkins build and may fail without failing the run. ShreddedPaper and Canvas are Folia's forks, so their cells also check the core took Folia's path (`REGIONS threading` in the log); both do. Leaf's loader writes `config/leaf-loader.yml` and stops on a first start, so `boot-test.sh` has `--seed`, a folder copied into the server's before it starts (`scripts/boot-seeds/leaf`, the loader's defaults).
- **Waterfall waits for the BungeeCord adapter,** which comes with the proxies after M1; its cell comes with it.
- **Fabric through its own build:** `./gradlew -p core/platform-fabric build collect` also runs platform-fabric's tests, which no workflow ran before, and collects xSample's and xTwin's jar for every line. Loom's Minecraft jars and mappings (`~/.gradle/caches/fabric-loom`) are cached on platform-fabric's settings and `stonecutter.properties.toml`, and the servers' launchers and mods (`.cache/fabric`) per line. Quilt boots the newest line's jar through `boot-fabric.sh --loader quilt`.
- **The family test is xTwin, a second plugin, beside xSample.** Not a second copy of xSample: its commands (`/xsample`, `/coins`, `/pay`) would be taken twice, which the registrar warns about, and a warning fails a boot. xTwin (`core/core-testing/twin`, its Bukkit plugin in `bukkit/`, its Fabric mod as platform-fabric's `twin` branch) has the admin subcommands and `/xtwin family`, and its jar carries its own core relocated to `co.xenastudios.xtwin.core`, so the two plugins share no class of ours. On Fabric, where every mod is in one class loader, the relocation is what makes it a test: xSample's Fabric jar has the core under its own names, and xTwin's mod jar is relocated with Shadow after Loom's remap, so two copies meet only on the board.
- **What the family test checks** (`core/core-testing/twin/family-checks.txt`, after xSample's own checks): xTwin records a made-up offline player as it starts; `/xtwin family` finds `config.yml` and `players.records` (with that player) in the family's folder, and the platform's registry holding one board (on Bukkit, the services hold the same object from xSample and from xTwin; on Fabric, the object share holds xTwin's board and xSample is loaded); then xSample's `forget` finds the player xTwin recorded, xTwin's `forget` deletes them from the family's cache (one record), and xSample's `forget` no longer finds them. None of it depends on which plugin starts first: on Spigot 1.8.8 xTwin enabled first, on Paper xSample.
- **The performance budgets plug into the boot jobs,** after each boot step: startup from the boots' logs, a BotMark load with a Spark profile, on the cells that measure them (#122's benchmarks, a separate change).
- **Booted locally, with the scripts and arguments the workflow runs:** every cell of the matrix passed: Paper and Folia 26.3, Spigot 1.8.8 (Java 8), 1.13.2 (11), 1.16.5 (16) and 26.3 (25), each built by `server-jar.sh` through BuildTools 201, PandaSpigot 1.8.8-227, Leaf 26.3-31, Leaves 1.21.11-157, ShreddedPaper 26.3-10 and Canvas build 1047 (both on Folia's path), Fabric 1.20.1 and 26.3, Quilt 26.3; and the family test on Paper 26.3, Spigot 1.8.8 and Fabric 26.3. On GitHub, the pull request's run (Paper, Spigot 1.8.8, Fabric 1.20.1 and 26.3, with the family test) and the whole matrix by hand passed, but for Canvas: its Jenkins answers GitHub's runners 403, which its cell is allowed to fail on. The first run also found Maven Central answering BuildTools 429 on a runner, so BuildTools' Maven goes through Google's mirror of Central (`server-jar.sh`), and every step runs with `pipefail`, since a script piped to `tee` had hidden the failure.
