# The build: the configuration cache everywhere, R8 on every rewrite jar, a scaffolder for the new layout (2026-11-24)

The build half of M1's tooling (#122): caches, R8 and its budgets, and `new-plugin` for the rewrite.

- **The configuration cache is on for every build, and the whole of `build` stores and reuses it with no problems.** Two exceptions, both outside `build`: Minotaur's `modrinth` and `modrinthSyncBody` declare themselves incompatible, so Gradle runs a release's Modrinth upload without the cache (on its own, with nothing to fix on our side); and CodeQL turns it off on purpose, since it must see every compiler run. Gradle 10's two deprecations in our scripts (`by configurations.creating`, a `Project` as a dependency) are gone, so nothing in our build warns.
- **The build cache is local, kept between CI runs by setup-gradle; a remote one waits for a server.** A real remote cache needs a Develocity node or bazel-remote that we'd have to host and secure, and setup-gradle's cache of Gradle's home already carries the local build cache from `main` to pull requests. `settings.gradle.kts` uses an HTTP cache when `XENA_BUILD_CACHE_URL` is set (`XENA_BUILD_CACHE_PUSH=true` to write, `_USER`/`_PASSWORD` for credentials), so one is a secret and a workflow line away. CI saves the configuration cache too once the `GRADLE_ENCRYPTION_KEY` secret exists (setup-gradle encrypts it, since it can hold the environment); without it, CI just rebuilds the task graph.
- **R8 is a convention, `xena.r8`, applied per jar,** with M0's keep rules in build-logic (`xena/r8/common.pro`: stack traces, enums, type tokens, `co.xenastudios.**.api.**`, the loader's `PluginEntry` and `BukkitBootstrap`) plus rules the `shrinkJar` task writes from the jar's own files, so a plugin never repeats them: `plugin.yml`'s and `paper-plugin.yml`'s `main` (and Paper's `bootstrapper`/`loader`), every `fabric.mod.json` entry point, every `META-INF/services` entry. Renamed classes go to a package of the plugin's own (`co.xenastudios.<plugin>.r8`, from the project path unless set), as M0 found Bukkit's shared class cache needs. Output and mapping go to `build/r8/`; the release picks which jar ships when the rewrite's first plugin does. Today's Java plugins keep Shadow's `minimize()` and aren't shrunk.
- **Shrunk jars are run, not just built.** The convention gives tests both jars' paths; the loader sandbox's `JarBootTest` loads each through Bukkit 1.8.8's own `JavaPluginLoader` and `PluginClassLoader` on a stand-in server, runs onLoad and onEnable, and runs its `boot-checks.txt` (the stdlib on the class path, as a server that read `libraries:` has it). Dropping the `PluginEntry` keep rule fails it with the shim's own error, so a bad rule shows up in `check`, not on a server. The shrunk `LoaderSandbox.jar` (35 KiB to 27 KiB) also passed `boot-test.sh` on Paper 1.21.11. xSample isn't shrunk: it has no jar or entry point until a platform adapter does.
- **Budgets for the rewrite's jars are one file, `gradle/jar-budgets.txt`,** one line per project (`:xbans:bukkit 349`), checked against the shrunk jar by `checkJarBudget` on `check`. A jar with no line fails, so a new jar gets a budget on purpose. The file lists today's 1.x sizes from M0 as each plugin's limit when its rewrite lands (ROADMAP.md: no bigger than today on the Bukkit family, today's + 300 KiB where the stdlib is shaded). One table, not a number in each build file, because budgets are reviewed together and the rule is the same for every plugin.
- **`scripts/new-rewrite-plugin.ts` scaffolds the rewrite's layout,** beside `new-plugin.ts` (which still does the brand and docs for today's Java plugins): `<id>/api` and `<id>/common`, a config, permissions, a command and a test on the fake platform, the API's signatures, then a build on the JVM and wasmWasi. `--platforms` adds the Bukkit and Fabric adapters on `:core:platform-bukkit` and `:core:platform-fabric`, and refuses to build until those modules exist, since a project naming a missing one breaks the configuration of every build. `settings.gradle.kts` includes a plugin folder with `common/` and no top-level build file, and `affected.sh` treats it as a unit (no newest-Paper compile or Paper boot, which are for today's Java plugins). CI runs the scaffolder end to end without the flag (`scaffold.yml`).
