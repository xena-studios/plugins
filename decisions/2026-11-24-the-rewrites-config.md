# The rewrite's config: a schema in Kotlin, YAML read by snakeyaml-engine-kmp and written by us (2026-11-24)

The config system is in `core-common` (`co.xenastudios.core.common.config`), with the file's side in `core-jvm`. It keeps what today's does (above: generated from a schema, used when it can't be saved, edited in game); what's new:

- **A schema of typed keys, not `kotlinx.serialization` classes.** A plugin's config is an `object : ConfigSchema` whose properties are keys (`int("limit", 3, "comment", min = 0)`) and sections, in file order; `config[HomesConfig.homes.limit]` reads one. No reflection, so it's the same on Wasm and survives R8. Each bad value is reported with its path and line and falls back to its own default, where a serialization decoder stops at the first. Comments, limits and former defaults live on the key, and `describe()` gives the schema as data for the site's manifest task.
- **YAML is read through a `YamlReader`, and written by us.** The writer is in `core-common`, as today's core has its own emitter: schema order and comments, the owner's values as they wrote them (even ones that can't be used), unknown keys kept after the known ones of their section. A file is rewritten only when loading changed it (a new setting, a carry forward) or by an in-game edit, and then the schema's comments replace the owner's own; today's Bukkit path kept those. The parser's comment events could bring them back if owners miss them.
- **snakeyaml-engine-kmp on the JVM, not kaml.** kaml 0.104.0 is Java 11 class files, which the core's Java 8 floor can't load (`ConfigBytecodeTest` checks the parser and its dependencies), and its serialization layer would go unused. snakeyaml-engine-kmp is the parser kaml is built on: Kotlin Multiplatform, Java 8, and the library whose wasmWasi build is pending (krzema12/snakeyaml-engine-kmp#523). When that's published, `core-common` can depend on it and `JvmYaml` moves there; until then `core-common`'s tests read YAML with a small test-only reader. It costs about 870 KB unshrunk with okio; how it reaches servers (`libraries:`, the loader, R8) is settled with packaging.
- **Migrations edit the file's tree, and can run again.** Each `migrate(from)` step uses operations that leave an already-carried file as it is (a move whose source is gone does nothing; one whose destination the owner set just drops the source), so a carry that couldn't be saved runs again on the next start with the same result.
