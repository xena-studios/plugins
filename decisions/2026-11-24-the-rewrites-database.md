# The rewrite's database: one writer that never repeats a commit, statements per dialect, records for Pumpkin (2026-11-24)

The database layer of the rewrite (#122): `co.xenastudios.core.common.db` and `.storage` in `core-common`, `co.xenastudios.core.jvm.db` in `core-jvm`. It keeps what today's `core/db` proved ("A shared database layer, with no drivers shaded in", "Network mode: one change feed in the database"); what's new:

- **SQL is built, not written, in common code.** A table is declared once (`object Homes : Table("homes")` with typed columns: `INT`, `LONG`, `DOUBLE`, `BOOLEAN`, `UUID` as 16 bytes, `INSTANT`, `BYTES`, `text(max)`, `nullable()`, `map`), and `Sql(dialect, prefix)` writes each statement for the database it's on: `createTable` (`IF NOT EXISTS`, utf8mb4 InnoDB on MySQL, SQLite's own row id), `insert`, `insertIgnore`, `upsert`, `update`, `delete`, `select`, and `raw` with `{p}` for what the builders don't cover. Values are bound, never spliced in, and rows are read back by column (`row[Homes.name]`). No `java.*`, so it compiles for `wasmWasi`, and its tests run on both.
- **Upserts per dialect, because old servers ship old SQLite.** Spigot 1.8.8 bundles sqlite-jdbc 3.7.2, older than SQLite's `ON CONFLICT ... DO UPDATE` (3.24). M0 didn't test SQLite, so the dialect carries the version the driver reports, and below 3.24 an upsert is an `UPDATE` then an `INSERT OR IGNORE`, which run in the same transaction on the one writer, so nothing slips between them (tested on a real SQLite). MySQL and MariaDB get `ON DUPLICATE KEY UPDATE c = VALUES(c)`: MySQL 8.0.20+ calls `VALUES()` there deprecated but runs it, and MariaDB has no row-alias form. The oldest SQLite used is 3.7.0, for WAL.
- **Each plugin's tables have its prefix, so the family can share one database**: one MySQL, or one SQLite file in `plugins/Xena/` that the adapter passes. Each prefix has its own `{prefix}meta` table and schema version. The `meta` and `changes` tables have today's columns, so a plugin can keep its tables across its rewrite.
- **Migrations are numbered steps of statements, each in its own transaction with its new version,** as today. A step can run again: MySQL commits each table change as it goes, so a statement whose table, column or index is already there (`ALREADY_EXISTS`, from MySQL's 1050, 1060 and 1061 or SQLite's message) is skipped. A database made by a newer version is refused, never changed.
- **Errors are `Outcome<T, DbError>`** with a kind code can act on (`UNAVAILABLE` and `BUSY` are worth retrying; `CONSTRAINT`; `CORRUPT` for a stored value its column can't read; `OVERLOADED`, `CLOSED`, `NO_DRIVER` and others). Every `Pending` settles with one; none fails.
- **One writer thread per database, writes acknowledged on commit.** `write(statements)` queues and returns; the writer runs everything waiting (up to 1,000 writes) as one transaction, consecutive statements with the same SQL as one JDBC batch (so `rewriteBatchedStatements` makes one multi-row insert on MySQL), and settles each write's `Pending` once it's committed. While the database is down a batch is kept and retried (at once, then from 250 ms doubling to 30 s), with one line when it goes and one when it's back. A batch the database refuses is split, and only the write at fault fails, as xRewind's writer does. Past 100,000 waiting the console is warned; past a million new writes are refused with `OVERLOADED` rather than run the server out of memory. `transaction { }` runs read-then-write work (a withdrawal) on the writer in its own transaction, rolled back on an error; `session { }` runs migrations there. Closing finishes what's queued, waiting up to 10 s for a database that's down, then fails the rest with `CLOSED`.
- **A commit whose answer is lost is looked up, not repeated.** Each transaction also sets this writer's row in `meta` to the batch's number. When the connection dies after the commit was sent, the writer reads that row on a new connection: if the number is there the batch landed and is acknowledged, otherwise it's run again. Without it, a retried insert after a lost answer (a MySQL restart at the wrong moment) wrote its rows twice. A clean close deletes the row.
- **Reads beside the writer, and no HikariCP.** Each reader thread keeps one connection: one on SQLite, whose WAL lets it read while the writer writes, two on MySQL. A reader idle for a minute closes its connection and ends, and one idle for 30 s is checked before use, since MySQL's `wait_timeout` closes idle connections. SQLite readers are `query_only`, so a write by mistake fails. That's the whole pool: the threads are few and each owns its connection, so HikariCP's checkout, validation and housekeeping (and its jar) would buy nothing. Reads see what's committed; one that must see a write waits for that write's `Pending`, or runs in `session`.
- **Drivers: the server's first, then fetched; never shaded.** `Drivers` loads the server's SQLite driver (Paper's, Spigot's), or MySQL's (Connector/J 8+, then 5.1 on old servers), and uses it directly, not through `DriverManager`, which only hands out drivers the caller's class loader sees. SQLite older than 3.7.0 is passed over. Otherwise a `DriverFetcher` downloads the jar (`DriverLibrary` has the coordinates) and it's loaded in a class loader of its own. The core's loader (#143) has the pinned, shared cache this needs but no hook for optional libraries yet, so `DriverFetcher` is the seam: each adapter passes one built on `LibraryCache` once both are in, with the driver jars' hashes in `gradle/library-pins.txt`. Until then a server without a driver is told which one to install.
- **Network mode's change feed is common code**, the same protocol and table as today's, on the `Database` interface: published in the change's own write (`feed.publishing(topic, payload)` added to the same `write`) or transaction, checked every few seconds off the server's threads, late commits waited for, pruned to ten minutes but never empty, and a resync when a server may have missed changes. The waiting and pruning logic is a pure class tested on both targets. On the JVM it's tested end to end with two databases on one SQLite file and, with `XR_MYSQL` set, on MariaDB.
- **Pumpkin gets the same records in files.** `RecordStore<K, V>` (`get`, `all`, `put`, `remove`) is what a plugin that runs on Pumpkin writes its storage against, from one `RecordType` declaration on a `Table`: `SqlRecordStore` upserts through the writer on the JVM; `FileRecordStore` keeps the records in memory and writes the whole file (all or nothing, through `Storage`) on the next async task after a change, acknowledging it once the file holds it. The file is text with named columns, so a column added later reads as `NULL`. A plugin whose data needs queries (history, leaderboards) uses the database and isn't on Pumpkin.
- **Crash-safety is tested by killing connections.** `ChaosTest` closes the writer's connection under it mid-batch and at commit, before and after the commit reaches SQLite, while four threads write, and checks every acknowledged write is in the database exactly once; it fails if the lost-commit lookup is removed. `MySqlDatabaseTest` does the same against MariaDB, with a migration that got partway and a refused write in a batch.
