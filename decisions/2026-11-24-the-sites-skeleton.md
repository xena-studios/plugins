# The site's skeleton: pages from the manifest, a picker from data, old majors in their own folder (2026-11-24)

The rewrite's part of plugins.xenastudios.co (#122), built on the manifest and the seven reference components from #147, with the core's sample plugin as the fixture.

- **One line per reference section.** `<Reference plugin show />` reads the plugin's manifest from the `references` collection (validated against the schema, so a bad manifest fails `pnpm build`) and renders one section with #147's components, the default `config.yml` under the config table. A section with nothing in it says so in a sentence instead of an empty table, so messages and events read before the core fills them.
- **The page set is a template on xSample.** Overview, install, download, commands, permissions, configuration, messages, placeholders, integrations, importers, FAQ, developer API and changelog live in `docs/src/content/docs/xsample/`, a short hand-written intro above each generated section. xSample is never released, so its pages are hidden rather than left out: built and link-checked on every run, but out of navigation, Pagefind, the sitemap (the site now configures `@astrojs/sitemap` itself, with a filter, which Starlight allows) and search engines (`noindex`).
- **Install tabs and the download picker come from data.** Install has a Starlight tab per platform the manifest releases on, synced across pages. The picker reads the manifest's platforms (and the Minecraft version each starts from) and `docs/src/data/releases/<plugin>.json`: each release's jars, the platforms and Minecraft versions each runs on (explicit lists, as the stores take them, since Fabric ships a jar per Minecraft line) and the stores that carry it. The collection checks its shape; the picker fails the build on a jar for a platform the manifest doesn't release on, or releases out of order. Without JavaScript it's the full list for the latest release; a small bundled script adds the platform and Minecraft menus and hides the rest. The release pipeline writes that file once a rewrite ships; until then it's a fixture on example.com.
- **Old majors move per plugin, only when a rewrite ships.** `docs/src/data/versions.json` lists a plugin's newest and older majors. Its old pages go to `/<plugin>/v<old>/` with their own sidebar (the `v<old>` folder's group, hidden from the newest major's), previous and next kept inside the major, a version switch under every title (a `<details>`, to the same page in the other major or its overview) and a note on old pages. Every old page the new major doesn't have redirects from its old address (Astro redirects, worked out from the files), so no link breaks. Applied to xSample (`v0/`); every live plugin page stays exactly where it is, and the built routes were compared before and after.
- **The family's tokens, and XENA only in the footer.** `pnpm brand:sync` copies the brand's `tokens/plugins.css` to `src/styles/tokens.css`, and the theme and GUI build on its `--plugin-*` colours instead of repeating them. The header's XENA STUDIOS logo is replaced by the family's name ("Plugins", its first letter in the accent), since the brand puts the studio on a product's own site only in the footer. Search stays Starlight's own, which is Pagefind.
- **Left for later:** the per-plugin overview header (version, platforms, Java) from the manifest instead of the catalog, the catalog script writing a rewritten plugin's changelog and download pages, the language-completeness page and support policy, Dokka at `/api/<plugin>/`, and serving the schema for editors.
