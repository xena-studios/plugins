# The update checker and bStats in the rewrite's core: Modrinth's version types as channels, bStats on Bukkit only (2026-11-24)

What today's `XenaPlugin` gives every plugin besides reload (an update checker and bStats), in the rewrite's core, for xUtilities 3.0 (M2, #123).

- **Channels are Modrinth's version types.** A plugin's config mounts `UpdatesSection` (`updates: check, channel`); `channel` is `release` (the default), `beta` (betas and releases) or `alpha` (everything), as ROADMAP.md's "Updates" says. Today's checker showed betas only to servers already on a beta; now the owner picks. A version's own type comes from its suffix as the release workflow decides it (none a release, `-alpha…` an alpha, any other a beta), and build metadata (`+fabric-26.3`) doesn't count in comparisons.
- **Logic in common, HTTP on the JVM.** `UpdateChecker`, `ModrinthReleases` (the query, and reading Modrinth's and GitHub's JSON with a small reader of its own, 64 levels deep at most) and the version rules are in `core-common`, with tests on the fake platform's virtual time; `JvmHttp` in `core-jvm` is the GET, on `HttpURLConnection` like `MclogsPaste`, so it runs on Java 8 and adds nothing to the jar. Its tests run against a local server, as mclo.gs's do.
- **Once a day, off the server's threads, and nothing else.** One async task: a check at start, then every 24 hours; `apply` on reload keeps it, turning `check` off cancels it. It asks for the plugin's versions for the server's loader (`bukkit` for the Bukkit jar, which every Bukkit-family loader name in the release includes; `fabric`) and Minecraft version, as the release lists each jar, and links the version's Modrinth page. A project Modrinth is still reviewing answers 404, so then it reads the GitHub releases, as today's does. A failed check is kept for later (`problem`) and logged nowhere, so a server without internet isn't told daily.
- **The notice is a core message, `core.update.available`,** drawn in the console's `default-language` and in each player's language as they join, if they have `<plugin>.admin.update`, which `AdminCommands` now declares for every plugin (granted by `<plugin>.admin`). Said once per release found in the console; a channel change that brings a newer release in says that one.
- **One call per platform.** `BukkitPlatform.checkUpdates(project, permission, settings, loader, translations)` and `FabricPlatform.checkUpdates(project, permission, settings, translations)` build the checker with the platform's text, locales, permissions and join event; `close()` (or the server stopping, on Fabric) stops it. On Fabric the console notice waits for the server's first tick, since mods start before the server.
- **bStats on Bukkit: bstats-bukkit, relocated per plugin.** `BukkitPlatform.metrics(serviceId)` starts its `Metrics`; the plugin's jar shades `org.bstats:bstats-bukkit` (with bstats-base) and relocates `org.bstats` into its own package, as today's plugins do. Not fetched: bStats refuses to start in its own package, and a shared copy would mix plugins' services. bStats reads `plugins/bStats/config.yml` itself, so the owner's switch for every plugin holds, and 3.2.1 submits from its own thread on Folia. A jar without bStats gets a warning, not a crash. 9 KiB in xSample's R8 jar; the update checker 16 KiB, and the Bukkit side 6 KiB (its budget is now 540 KiB).
- **Not on Fabric.** bstats.org has no Fabric platform: a service is created for Bukkit, BungeeCord, Sponge, Velocity and a few others, and bstats-base needs one of those. So Fabric reports nothing; when bStats adds one, `FabricPlatform` gets the same `metrics`.
- **Tests never reach the network:** `-Dxena.offline=true` keeps both off, as before. The boot tests run both for real: xSample and xTwin check for updates (neither is on Modrinth, so they find nothing) and start bStats under a made-up id (`-Dxsample.bstats`, `-Dxtwin.bstats`, set by `boot.sh`) with `plugins/bStats/config.yml` seeded off, so two relocated copies start side by side and nothing is sent.
