# xUtilities 3.0, the pilot: 2.x's paths kept, messages in lang/, one Server interface per platform (2026-11-24)

M2 (#123): xUtilities rewritten in place on the rewrite's core, as `xutilities/api`, `common`, `bukkit` and `fabric`, the first plugin end to end. What was decided, and what the core had to learn:

- **One `Server` interface, written by each adapter.** The core's platform layer knows players only as `PlayerRef`s; it can't set a gamemode or open an anvil. xUtilities' shared code (`common`: config, messages, commands, `/back`, the API) calls a `Server` of its own, which `bukkit` and `fabric` implement: what it does to a player, on that player's thread, and `Features`, what the server can't do, found once at startup. A command the server can't do (an anvil on Spigot before 1.21.4, `/ping` before 1.17) is still registered and says what it needs (`menu.unavailable`, `unavailable`), rather than vanishing. Not in the core: each plugin's actions are its own; zChat and xTeleport will grow theirs, and what they share then moves down.
- **Bukkit: compiled against 1.8.8, the rest found by method checks.** As platform-bukkit: `main` against Spigot 1.8.8's API, `modern` against Paper's for Folia's region check and `teleportAsync`, `MenuType`, Paper's `openAnvil` and the rest, `getPing`, `setRotation`, `getItemInMainHand` and the damage meta, each used only once a `getMethod` at startup found it. Deprecated 1.8 methods (`getMaxHealth`, `getDurability`, `createInventory(..., String)`) still exist on Paper 26.3, so main uses them everywhere they still work; harmful effects are told by name, since effect categories are 1.20.2's.
- **Fabric: Minecraft's own classes, no mixin.** The workstation menus are Minecraft's, subclassed so `stillValid` always passes; the trash and Ender Chest are chest menus; sounds are a sound packet. Fabric API has no teleport event, so `/back` hears deaths (`ServerLivingEntityEvents.AFTER_DEATH`), xUtilities' own teleports (`/top`, `/back` record their start themselves when `Features.teleportEvents` is false) and other mods' through `setBackLocation`; the docs say so. Two more Stonecutter constants: `effect_holders` (1.20.5) and `modern_teleport` (1.21.2).
- **`xutilities/fabric` is a branch of platform-fabric's build, pointed at the plugin's folder.** `branch("xutilities")` in `core/platform-fabric/settings.gradle.kts`, its project and each version's node given `xutilities/fabric/` and `versions/<line>/` there; the root build's settings and `affected.sh` leave `fabric/` out. Its jar is the sandbox's (R8 before Loom's remap, a budget line per line) with xTwin's last step (Shadow relocates the core after the remap), until the core makes that a convention (#162). Its lang files are read through its own mod container: every Fabric mod shares one class loader, so `LangFolder.shipped`'s class-loader lookup could find another mod's `lang/de.yml`.
- **2.x's config paths are 3.0's.** `commands.<name>.enabled`, `aliases`, `permission`, `permission-others`, the speed bounds, heal's extras, `include-armor`, the sounds and `info-commands` stay where they were. Two reasons: an owner's file needs no move but its messages, and the 2.1.0 jar put back reads 3.0's file (as a newer version, read-only) and keeps every command's settings and link command. It can't restore its own copy: it's released, and it doesn't know about `config.yml.bak-v2`. So going back is "rename `config.yml.bak-v2`", on the upgrade page, and without it 2.1.0 still runs, with default messages; tried on Paper 26.3 (2.1.0, then 3.0, then 2.1.0, then the copy restored). A 2.1.1 on `maintenance` that restores the copy by itself would close the gap.
- **Messages move to `lang/`, an owner's edits with them.** Every message is in `XUtilitiesMessages`, keyed by its 2.x setting (`commands.fly.message-on-self` is `fly.on-self`). On the first start from 1.x or 2.x the loader (`JvmFiles`) writes the messages the owner edited (not on a text 1.x or 2.x shipped: `Legacy.MOVED` lists each) to `lang/en.yml` before the language files are loaded, so they're its starting point; then the config's migration drops them from `config.yml` and copies it aside as usual. A migration step can't write another file, so this is the loader's, beside it. If anything was edited, `messages.language` becomes `en`, so every player keeps reading the owner's words, as in 2.x; `auto` is one setting away. The theme moves into `messages.theme`; a colour still on 2.x's default becomes `shared`. The gamemode names, flight's state and the speed types are messages too, filled in per reader (`Texts` takes a `MessageKey` as a placeholder value).
- **Seven languages drafted, marked `machine-drafted`.** de, es, fr, pt-BR, ru, pl and zh-CN, every message, the core's included, waiting for native review; `checkTranslations` passes without `allowMissingTranslations`.
- **Link commands are a typed map.** `info-commands` is one key whose type reads a section of commands (`LinkCommand.TYPE`), skipping one it can't read; `LinkCommand.problems` says why, read from the raw file, since a type can only refuse a whole key. A link's message stays in `config.yml`: it's the owner's own words, the same for every reader. A command or link whose name or alias another already has loses the alias (or is skipped) with a warning; before, a clash made the core's tree builder throw.
- **Commands and permissions come from the config.** The tree is built from the config on every reload, each command's permission declared under the node the owner named (blank for anyone), two commands sharing a node sharing one `Permission`; `[player]` forms check `-others` in the handler. xUtilities keeps no player data (`/back`'s spots are in memory, gone when a player leaves), so it has `reload` and `debug` only.
- **The API's core types are relocated with the plugin's core.** `XUtilitiesApi` uses core-api's `PlayerRef`, `Location` and `EventBus`, and each plugin relocates its own core ("The family"), so inside the jar they're `co.xenastudios.xutilities.core.api.*`. The published API (Maven Central, #162) has to carry the same relocation, or a consumer's calls won't link. On Bukkit, `/back`'s events are also Bukkit events of xUtilities' own, `BukkitBackRecordEvent` and `BukkitBackTeleportEvent` in `co.xenastudios.xutilities.api.bukkit` (Bukkit types, cancelling the shared event), made only when a Bukkit listener exists, rather than the core's generic `XenaEvent`, so Skript can name them. 2.1's Bukkit-typed `XUtilitiesApi` and event classes are gone: the CHANGELOG and the Developer API page say what replaces each.
- **The config is read as the plugin enables; the rest off the thread.** `config.yml` decides which commands exist, and registering them during enable, as 2.x did, means the server's own startup sync sends them to clients. The family's settings and `lang/` load on an async task and apply on the next global tick (English from the code until then). Startup on Paper 26.3 (`scripts/budgets/check.sh`, median of 3): 248 ms, onEnable 164 ms, over the 150 ms first-plugin budget, like xSample; heap 2.5 MB, metaspace 1.35 MB, idle 0 ms a tick.
- **What the core changed, kept small:**
  - `CoreMessages` has every command result (`core.command.*`: no permission, players only, usage, unknown player, the argument errors, cooldown, confirm, error) and the reload's reply (`core.reload.*`), and `CommandFeedback.of(AdminText)` draws a result in the reader's language; `CommandFeedback.message(result, source)` is the call the registrars make, defaulting to the old one. Fabric's registrar takes its feedback as a settable property, as Bukkit's already did. `AdminText` writes `Duration` and `Double` placeholders for the reader's language. `/<plugin> reload` replies from the lang files, one line per problem and failed module, in the same English. xSample's German and core-jvm's test German have the new keys.
  - `PermissionSet.node(...)` declares a node of any name, for permissions an owner names in the config, and `PermissionSet.isNode` checks one.
  - Bukkit's registrar gives way to a server command of the same name (vanilla `/gamemode`, Bukkit's `/version`), keeps it and puts it back when ours goes, as today's core does; another plugin's command is still never replaced. Fabric's does the same for Minecraft's own commands, told from mods' by the first executor in the node's tree being a lambda of a `net.minecraft.` class (no mixin; a mod that borrows Minecraft's permission check still runs its own code).
  - The root build puts build-logic's conventions on its own class path (`id("xena.kotlin-jvm") apply false`), so a rewritten plugin's `bukkit/` project can ask for Shadow and run-paper by id; `:core` did that for the sample's.
  - `scripts/boot-fabric.sh` runs servers with `-Dxena.debug.paste=false`, and each plugin's entry honours it, so boot tests never upload a debug report.
- **Jars are over 2.x's size.** 571 KiB on Bukkit and 528 to 542 KiB on Fabric, shrunk, against 2.x's 163 KiB: about 420 KiB is the shared core (core-common's i18n, commands, config, markup and family layers are 30 to 45 KiB each), 70 KiB xUtilities and 20 KiB its eight languages. The budget lines are the measured sizes plus a tenth, a tripwire; getting back under 2.x's is the core's work, not the pilot's.
- **Release:** `xutilities/bukkit` applies `xena.release` for every jar: the Bukkit jar and Fabric's three, which `release.yml` now builds first in platform-fabric's own build when a plugin's release has any (`./gradlew -p core/platform-fabric collect`). Modrinth `xutilities`, Hangar `xUtilities`, voxel.shop 10707; CurseForge has no projects yet, so it's skipped. 3.0.0-alpha.1 until the alpha has run on our own servers.
- **Left:** the update checker and bStats (the core's, in progress; `update-checker.enabled` is read but nothing checks yet), relocating Fabric jars as a convention, startup under budget, a real client joining in the boot tests, native review of the seven drafts, the brand catalog's words for the new platforms, `modrinth.md` (published to the live store page on every change to main, so it moves with the release), the alpha on our own servers, and the release.
