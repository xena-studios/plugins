# The chat bridge: one chat event for every platform, drawn once per group, signed where the platform can keep it (2026-11-25)

zChat 4.0 (M3, #124) needs chat from every platform it ships on, so the core has it first: `co.xenastudios.core.common.chat` in core-common, implemented by platform-bukkit (Paper, Folia, Spigot, CraftBukkit) and platform-fabric, and by core-testing's `FakeChat` for plugins' tests. xSample formats chat through it, and the boot tests' real client sees the line. What was decided:

- **A plugin asks for chat; until then nothing listens.** `BukkitPlatform.chat(priority)` and `FabricPlatform.chat(priority)` make a `ChatBridge` and register the platform's listeners then, picking the platform's way once; `close()` takes them away (the platform's `close` closes any left). A module makes its bridge in `enable` and closes it in `onDisable`, so a chat feature that's off costs nothing. Each plugin has its own bridge, with its own bus.
- **One event, plain text, the platform's own set of recipients.** `ChatEvent` (`core:chat`): `sender` (`PlayerRef`), `senderName`, `message` (plain, settable; `originalMessage` kept), `recipients`, `isCancelled`, `rendering` and `async`. The message is a string, not our `Component`, because every platform's chat starts as typed text and a filter, mentions and anti-repeat all work on text. On Paper an unchanged message keeps the component Paper has, so another plugin's additions survive until a plugin changes the text; the rendering gets plain text. `recipients` is a view of the platform's set (Paper's viewers, Bukkit's recipients; on Fabric one copy of the player list a message), never a copy per listener. `ChatSentEvent` (`core:chat_sent`) comes once every plugin on the server has had its say, for cooldowns, anti-repeat and mention sounds, which count only a message that went out.
- **Where it sits among other plugins is the bridge's priority.** On Bukkit it's the Bukkit priority of the same name for the platform's event, with every one of the plugin's `listen`ers inside that slot in their own order; on Fabric, a phase of `ALLOW_CHAT_MESSAGE` per priority (`xena:chat_lowest` to `xena:chat_monitor`) ordered around Fabric's default phase, which is `NORMAL`'s. The rendering is drawn after every plugin's handlers, so it sees the final message (a later plugin's change included: the bridge copies it back into `message` before drawing) and the final recipients, whatever the priority. Sent-listeners hear at Bukkit's `MONITOR` and Fabric's `CHAT_MESSAGE`.
- **Drawn once per group of viewers, never per player unless asked.** A `ChatRendering` is `same` (one line for everyone and the console), `grouped`/`byLanguage` (one per group a `ViewerGroup` says, such as `MessageDrawer.languageOf`) or `perViewer`. `ChatDrawing` renders and draws each group once and hands the same server object to every viewer in it: finding a viewer's line is the group lookup and a look through the few groups drawn so far. Recipients are named by a `PlayerRef` the platform keeps per online player (a map by UUID, dropped on quit), so the hot path makes nothing per recipient: `ChatBenchmark` allocates the same bytes for 100 recipients as for 10.
- **A rendering that throws is logged, and the message goes out in the platform's own format,** rather than being lost.
- **Paper and Folia: `AsyncChatEvent` and a `ChatRenderer`,** found by class and method checks (`viewers()`, `renderer(...)`, `ChatRenderer.viewerUnaware`), so Paper 1.17 and later, and Folia; Paper before 1.17 takes the Spigot path. A `same` rendering is a viewer-unaware renderer, which Paper calls once; the others a renderer Paper calls per viewer, which looks the viewer's group up. **Signing:** a message nobody changed goes out as the client signed it. With a renderer, Paper still sends the player's signed message, with the drawn line as its unsigned content, in a chat type of Paper's that shows that content as it is; a changed message becomes the unsigned content the same way. Chat reports still carry what the player signed, which can differ from what was shown, and a client may mark such a line as changed by the server. The real-client check on Paper 1.21.11 showed it: the client got the plain signed text with the formatted line as unsigned content, so `client.js` now reads what a vanilla client shows, the unsigned content when there is one (mineflayer's `messagestr` doesn't). This is what modern Paper chat plugins do; stripping signatures altogether (as anti-report plugins do) is the owner's choice, not ours.
- **Spigot, CraftBukkit, Paper before 1.17: `AsyncPlayerChatEvent`.** The listeners run at the bridge's priority; the rendering at `MONITOR`. A `same` line with no hover or click becomes the event's format, as `§` text with `%` doubled, so the server sends and logs it as its own. Anything else (a hover, a click, a line per language or viewer) is drawn once per group and sent to each recipient as the server's text (`BaseComponent[]` on Spigot), and the event keeps the console's line as its format with its recipients emptied, so the server logs it and every other `MONITOR` listener sees a message that went out; if another plugin made the set fixed, the event is cancelled instead and the bridge logs the line. The sync `PlayerChatEvent` isn't used: Bukkit fires the async event for chat a plugin makes a player say too, synchronously, on that thread. **Signing:** none before 1.19; from 1.19, Spigot sends chat whose format or message a plugin changed as system messages, unsigned and not reportable, so a format on Spigot always means unsigned chat. Nothing the bridge can do keeps it.
- **Fabric: `ServerMessageEvents.ALLOW_CHAT_MESSAGE` and `CHAT_MESSAGE`, no mixins,** the same on 1.20.1, 1.21.11 and 26.3 (Fabric API's message module is there for all three; 1.20.1 already has 1.19.3's signed chat, so the lines don't differ). Chat is heard on the server thread. Unchanged, Minecraft broadcasts it, signed. Cancelled, the broadcast is refused. Otherwise the bridge refuses Minecraft's broadcast and sends it itself: a new message or other recipients without a rendering is the player's signed message with the new text as unsigned content, in Minecraft's own chat type, to the recipients, so it stays reportable; a rendering goes to each recipient as a system message, drawn once per group, unsigned. **Not possible without more:**
  - a format that keeps the signature. Minecraft shows a signed message only inside a chat type, which for chat is `<name> message`; a type that shows a line as it is (what Paper adds) is an entry in the `chat_type` registry, which every client is sent as it joins. A mod can add one from a data pack in its jar, but that changes what every vanilla client receives, for every Xena mod's server, and the real client can't check it on Fabric yet (boot-fabric.sh has no client step); so it's left for when a plugin needs it.
  - telling other mods. When the bridge sends a message itself, Minecraft's `CHAT_MESSAGE` doesn't fire, so another mod listening there (a Discord bridge) doesn't hear it; the bridge's own sent-listeners do.
  - unregistering. Fabric API events can't drop a callback, so a closed bridge's stays registered and returns at once.
  - what commands say (`/say`, `/me`) and private messages: Fabric API hears the first through `ALLOW_COMMAND_MESSAGE`, not chat, and the bridge hears only chat, as on Bukkit.
- **`FakeChat`** runs a message the way Paper does, on the test's thread: `join` players, `say` something, and the result has each recipient's line, the console's, and how many times a rendering was drawn.
- **A proxy later.** Nothing in the API is a server's: a proxy's adapter (Velocity's `PlayerChatEvent`, BungeeCord's `ChatEvent`) can be a `ChatBridge` too. On Velocity a 1.19.1+ client's signed chat can only be allowed or denied there, not changed, which its adapter will say.
- **In xSample:** a `chat` module (`chat.enabled`, `chat.prefix`), on by default: the prefix, the name with a hover, and the message, `same` for everyone. So its reload now says "2 modules on". Its platform check makes a bridge at startup and checks the path picked for the server and that closing it takes its three listeners away.
- **Measured.** `ChatBenchmark` on an M1 Pro (JMH, `-prof gc`), a message through the bridge, a listener setting the format and the line drawn to Adventure for each recipient (a quick run, so times are rough): a message no one hears 20 to 25 ns and nothing allocated; one line for everyone 3.2 µs and 1,128 bytes at 10 recipients, 4.9 µs and 1,184 bytes at 100; a line per language (two) 0.5 µs and 928 bytes at 10, 4.2 µs and 1,024 bytes at 100. So 90 more recipients add under 100 bytes a message, not an object each, and a message costs a few microseconds off the server thread against the 50 µs a tick a plugin may spend under 10 bots. The budget lines are those, bytes plus a quarter and times five, as the others. Booted with `boot.sh`: Paper 26.3 and 1.21.11, Folia 26.3, Spigot 1.8.8 (Java 8); the real client chats on Paper 1.21.11 and Spigot 1.8.8 and sees `[xSample] Joiner: hello from the client`, and the console logs the same line (`[Not Secure]` on Paper in offline mode). Fabric 1.20.1 and 26.3 boot with the chat module on; no client chats there.
