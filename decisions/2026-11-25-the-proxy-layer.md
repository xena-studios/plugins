# The proxy layer: signed plugin messages on xena:<plugin>, the change feed for what can't be lost (2026-11-25)

How a plugin's server side and its proxy side talk (ROADMAP.md, The family; #124), in `co.xenastudios.core.common.proxy`: zChat's network chat first, then xBans' network-wide bans and xVote's forwarded votes. What wasn't obvious:

- **Plugin messaging, one channel a plugin.** `ProxyChannel` is the plugin's `xena:<plugin>` channel (`xena:zchat`), from `BukkitPlatform.proxyChannel()`, `VelocityPlatform.proxyChannel()` or `BungeePlatform.proxyChannel()`: `send(to, topic, payload)` and `listen(topic, listener)`. A server sends to `Peer.Proxy`; the proxy to `Peer.Server(name)` or `Peer.AllServers`. Topics are short words; payloads up to 30,000 bytes, which leaves room in the 32,767 a server takes in one message, written and read with `ProxyPayload` (numbers, text, UUIDs, a version first by convention). Listeners run async, off the server's threads. The logic is common code (`ProxyEndpoint`); a platform only moves bytes (`ProxyTransport`): Bukkit's messenger, Velocity's channel registrar, BungeeCord's.
- **A message needs a player to carry it, and isn't queued.** A server reaches the proxy only through a player's connection, and the proxy reaches a server only through a player on it, so with nobody on a server nothing goes either way, and `send` says `NO_PLAYER` at once. Bukkit also drops a message on a connection whose client hasn't registered the channel, which the proxy does for each player a moment after they join, so the server picks a player whose connection has it. BungeeCord can queue a message until someone joins; that's turned off, since a chat line delivered minutes later is wrong. What must arrive whether or not anyone is on, or reach a server that was down (a ban, a vote), goes through the change feed in the family's shared database instead (`ChangeFeed`, "Network mode"), which every server reads every few seconds. Not chosen: a socket of our own between proxy and servers (one more port to open and secure), or Redis (one more thing to run).
- **Every message is signed, because a player can forge one.** On a server, a plugin message from the proxy and one a player's client sent arrive on the same connection, so the server can't tell them apart by where they came from. Each message is a small frame (version 1: `X`, the version, who sent it, the topic, when, a random id, the payload) and the first 16 bytes of HMAC-SHA256 over the channel's name and the frame, under a key derived from the network's secret for this use alone. A server acts only on a well-formed frame signed with its secret, for this channel, marked as the proxy's, sent within five minutes either way by the two clocks, and not already heard; anything else is dropped and the console told why, once a minute at most for each reason. The proxy drops every message a player sends on our channels before it reaches a server, warning once per player, and never forwards a server's to a player, so a client never sees a signed frame.
- **The secret is one a network already has, where it can be.** `plugins/Xena/proxy.secret` (`config/xena/` on Fabric), the same on the proxy and every server, comes first. Without one, a Velocity network with modern forwarding uses Velocity's forwarding secret, which the proxy (`forwarding.secret`, or `VELOCITY_FORWARDING_SECRET`) and each Paper server (`proxies.velocity.secret` in `config/paper-global.yml`) already share: nothing to set. BungeeCord's forwarding has no secret, so a BungeeCord proxy that finds none writes a new random one to its `plugins/Xena/proxy.secret` and says to copy it to each server. A server with no secret sends nothing and accepts nothing, which is what a server with no proxy wants. Secrets shorter than 12 characters are refused.
- **The fake: `FakeNetwork` in core-testing.** A proxy and servers made of real `ProxyEndpoint`s on fake platforms, with players to carry messages (`join`, `leave`), the wire's bytes to replay, and `forge` for what a hacked client sends, so a plugin tests its server and proxy sides together without servers. Its signatures are a keyed checksum, not HMAC (common code has no JDK); core-jvm's tests check the real signer.
- **What zChat calls:** `platform.proxyChannel()` on each side; on the server `channel.send(Peer.Proxy, "chat", ProxyPayload.write { int(1); player(sender); text(line) })`, and on the proxy `channel.listen("chat") { message -> ... channel.send(Peer.AllServers, "chat", ...) }`, checking `Sent` and falling back to the change feed where a message must not be lost.
- **Checked** in common tests (both directions, every refusal, limits, payloads) and on real servers: the pair tests ("The proxy platforms") send xSample's hello from Paper 1.21.11 to Velocity and from Spigot 1.8.8 to BungeeCord, and the proxy's welcome back, signed with Velocity's forwarding secret on one network and a `proxy.secret` on the other, while the client sends a forged message on `xena:xsample`, which the proxy drops.
