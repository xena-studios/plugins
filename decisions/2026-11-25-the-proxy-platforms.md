# The proxy platforms: Velocity 3.4 on and BungeeCord, a thread of the plugin's own, the stdlib fetched (2026-11-25)

`core/platform-velocity` and `core/platform-bungee` implement the platform layer on the proxies, for the network side of zChat 4.0 (#124) and later xBans, xVote and xStats. xSample runs on both as a proxy plugin (`core/core-testing/sample/velocity`, `bungee`). What wasn't obvious:

- **Velocity 3.4 to 4.x, one jar.** Velocity 4 (4.3.1 today) is Velocity 3's API on Adventure 5 and Java 25: the API jars differ by one event. The adapter compiles against 3.4.0, the first Velocity on Java 21, and calls nothing newer; the renderer already ran on Adventure 5 (M0, Folia 26.3). Booted on 3.4.0, 3.5.1 (the newest 3.x) and 4.3.1. Velocity 3.3 and older (Java 17) are left out: 3.4 came out in 2024 and Velocity's own plugins have moved on.
- **BungeeCord and Waterfall, one jar, Java 8 bytecode.** BungeeCord's API on Maven Central (1.21-R0.4) is Java 8 class files, so the adapter and its shim are too, as the core is, though BungeeCord itself now needs Java 17. Waterfall, which PaperMC has ended, boots the same jar (boot only, #162).
- **The Kotlin stdlib is fetched on both, not shaded.** ROADMAP.md said "shaded and shrunk with R8 on Velocity"; it doesn't need to be. Velocity has an API for exactly this, `PluginManager.addToClasspath(plugin, jar)`, so the core's loader takes the stdlib and the YAML parser from the family's cache (`plugins/Xena/libraries/`, checked against their pins at every start, as on old Bukkit) and hands each jar to Velocity once it knows the plugin, at `ProxyInitializeEvent`. BungeeCord reads `libraries:` in `bungee.yml` (since 2021, Waterfall too), as Spigot 1.16.5 does, and on a BungeeCord that doesn't the shim adds them to the plugin's class loader as on old Bukkit. So a proxy jar has no stdlib in it: xSample's Velocity jar is 435 KiB and its BungeeCord jar 425 KiB after R8, under the 500 KiB rule. Not chosen: shading and relocating the stdlib (about 300 KiB more per plugin after R8, and a copy per plugin anyway).
- **A shim per proxy, in the loader.** `VelocityBootstrap` (Java 21 class files against Velocity's API) and `BungeeBootstrap` (Java 8 against BungeeCord's), each a source set and a Gradle feature of `core-loader` (`requireFeature("velocity")`), so a Bukkit jar never carries them. Velocity makes its main class with Guice, which fills in the proxy, the plugin's logger and folder on the shim's fields; its `@Subscribe` methods on the shim are found through the subclass. What the three shims share (the Java check, the startup classes loaded ahead, the Kotlin version check, making the entry point) moved out of `BukkitBootstrap` into `Startup`, and the mirror settings into `LibrarySettings`, which reads `plugins/Xena/libraries.yml` without a YAML library.
- **Threads: `Threading.PROXY`, a thread of the plugin's own.** A proxy has no main thread: Velocity runs events and commands on its pools, BungeeCord on its network threads, and both schedulers are pools. So `ProxyScheduler` (core-jvm) gives each plugin one thread for global work and work for a player, which keeps a plugin's state on one thread as shared code written for a main thread expects, and none of its work waits behind another plugin's; async work goes to the pool the Bukkit platform already had (`AsyncExecutor`, moved to core-jvm). Work at a place is refused, since a proxy has no worlds; work for a player is retired once they leave the proxy; delays are exact, since there are no ticks. The thread ends after a minute without work. Commands are handed to that thread too, so a command and a scheduled task never run at once. A new enum value, not `MAIN_THREAD`, so `/<plugin> debug` and code that cares can tell; the fake platform's scheduler knows it.
- **Commands: Velocity's Brigadier, BungeeCord's commands.** On Velocity, platform-fabric's `BrigadierTree`, moved to core-jvm, builds each root as Brigadier nodes, so players are sent only what they may use and get our suggestions; every label (name and each alias) is a Velocity command of its own, re-registered on reload only when its shape changed. On BungeeCord, one command per root with tab completion, as on Bukkit. A label another plugin has is ours as `/<plugin>:<label>`, with a warning. Velocity drops a tab completion that comes within 10 ms of the last (`tab-complete-rate-limit`), which the boot tests' client did; it now pauses before each, as a person would.
- **Permissions: the proxy's, with the plugin's defaults around them.** Neither proxy has a registry of nodes or defaults, so the plugin's declarations go through `PermissionResolver`, moved from platform-fabric to core-common. Velocity's permission API is a tristate, which LuckPerms answers: its answer first, then a declared parent, then the default. Proxies have no operators, so a node for operators is the console's until a permission plugin grants it. BungeeCord's checks are yes or no, through `PermissionCheckEvent`: the defaults go in at its lowest priority, before LuckPerms. With LuckPerms on BungeeCord, LuckPerms' answer is final, and it answers no for a node it has nothing for unless `apply-bungee-config-permissions` is on, so an owner grants a plugin's everyone-nodes to LuckPerms' default group there; Velocity's LuckPerms says "undefined" and the defaults apply.
- **Text:** Adventure on Velocity, through the same renderer as Paper. `BaseComponent`s on BungeeCord, drawn twice per language as on Spigot: in RGB for players, which BungeeCord turns into what each client shows, and in the sixteen colours for the console, which showed `§x` codes otherwise.
- **The family's board, found on the other plugins' main objects.** Neither proxy has a registry for objects plugins share. Each Xena plugin's main object is the loader's shim, which implements `java.util.function.Supplier` and hands out the board its plugin holds; a new plugin asks the proxy's plugin manager for the others, keeps only main objects whose class has a superclass named `*.core.loader.velocity.VelocityBootstrap` (or BungeeCord's), whatever package each plugin relocated it to, and takes the first board (`JvmFamilyBoard.fromShims`). R8 keeps the shims' names for this. Every plugin then hands out the same board, so it stays found whichever plugin stops first. Other plugins' objects are never called. `plugins/Xena/` is the family's folder, as on Bukkit; the player cache records the proxy's logins, quits and the clients' languages (each proxy says when a client's settings arrive).
- **What the platforms fire:** `ProxyJoinEvent`, `ProxyQuitEvent` and `ServerSwitchEvent`, in core-common, the same from both proxies, so a plugin's proxy side is shared code.
- **Updates and bStats:** the update checker asks Modrinth for the `velocity` or `bungeecord` loader with no Minecraft version (`ModrinthReleases` takes none), since one proxy jar fronts servers of every version. bStats through bstats-velocity (its factory is made for Guice, so the platform makes it the way Guice would) and bstats-bungeecord, relocated as on Bukkit.
- **Not here:** a Fabric server's end of the proxy layer (Fabric behind Velocity through FabricProxy-Lite), which comes with zChat's Fabric adapter; LuckPerms itself in the boot tests (a sample-only stand-in answers through Velocity's permission API instead, `-Dxena.test.grants`); unit tests of the adapters against fakes of the proxies' APIs, which are large interfaces: the boot tests run them on real proxies instead.
- **Booted** with `scripts/boot-proxy.sh`: xSample alone on Velocity 3.4.0, 3.5.1 (Java 21) and 4.3.1 (Java 25), BungeeCord build 2111 and Waterfall 1.21 build 615 (Java 21), with its platform checks and console commands; then the pair tests, Paper 1.21.11 behind Velocity 3.5.1 and 4.3.1, and Spigot 1.8.8 behind BungeeCord (Spigot on Java 21 locally, where JDK 8 is x86 only; CI runs it on Java 8), with a real client joining through the proxy: the proxy's commands, completions and replies in German, then English; its join, server switch and quit in both sides' player caches; and the proxy layer's hello and welcome ("The proxy layer"). Then also Paper 1.21.11 behind Velocity 3.4.0, and, after the chat bridge (#172), the same with its chat line through the proxy, and Paper 26.3 with the chat module. Startup below.
- **Startup on the proxies: the libraries checked from the moment the plugin is made, and the startup classes loaded and linked ahead.** The first CI run was over the first plugin's 150 ms on both proxies (Velocity 4.3.1 on Java 25 232.7 ms, BungeeCord 219.3 ms; Velocity 3.4.0 138.6 ms), about 2.5 times the local numbers. A profile of the proxy's thread showed where: on Velocity, hashing the cached libraries against their pins (the JDK's SHA-256 still interpreted that early: about 20 ms locally, more on CI, where xSample's own enable was 77 ms of the 227), loading the first Kotlin classes, and the first `Mac` starting the JDK's crypto providers (7 ms); on both, classes loaded and verified on the proxy's thread, since the jars had no startup list and the shim's preload only loaded classes, leaving the bytecode verifier's pass to their first use. So:
  - **Velocity: a trivial `@Inject` method starts the check.** Guice calls the shim's `prepare(@DataDirectory Path)` once its fields are in, as Velocity makes the plugin; it only starts a thread, which reads the manifest and the settings and starts each library's check on a thread of its own, the biggest first (`LibraryCache.fetchAhead`, which `fetch` then waits on). `ProxyInitializeEvent`, about 10 ms later, picks them up, hands them to `addToClasspath` as before and finds most or all of the hashing done. The jars are still checked against their pins at every start and added only once checked; the classes can't be loaded any earlier, since `addToClasspath` refuses a plugin Velocity hasn't registered yet. Not chosen: adding the jars through Velocity's internal `PluginClassLoader.addPath` before then, or a stamp that skips the hash when the file looks unchanged.
  - **Startup class lists for both proxy jars**, recorded with `scripts/boot-proxy.sh --record-startup <folder>` (the first startup boot logs its class loading; `startup_classes.py --done-ms` takes the JVM's uptime at the proxy's done line, since a proxy's log has no millisecond timestamps). Velocity's list is 595 classes, BungeeCord's 593, beside each build file as on Paper.
  - **The preload links what it loads** (`getDeclaredConstructors()` links a class without initializing it, where `Class.forName(name, false, ...)` only loads it), on two threads taking the list in turn where the machine has more than two cores. On every platform, so Paper's and Spigot's preload does more ahead too.
  - **The proxy channel's key is derived on its first use** (`ProxySecret.signer`), and each platform signs an empty frame on its async pool as a channel opens (`ProxySecret.warm`), so the first `Mac` isn't on the plugin's start, on the proxies or on Bukkit.
  - **The split** is in the shim's line: `Startup times: inject 0.4 ms, libraries 15.1 ms, enable 42.4 ms` on Velocity (the time on Velocity's thread as it made the plugin, waiting for the libraries, then making and enabling the entry point), `onLoad` and `onEnable` on BungeeCord as before.

  On Velocity what's left is about 15 ms waiting for the stdlib's hash and 43 ms making and enabling the plugin, most of that the first Kotlin code and the classes the preload hasn't reached yet, since it can only start once the libraries are added; on BungeeCord, whose `libraries:` the proxy resolves before the plugin's code runs, 14 ms of onLoad and 49 ms of onEnable. BungeeCord's own resolution of `libraries:` isn't in the number: it runs Maven's resolver over them (downloading their POMs and jars from Maven Central into its `libraries/` on a first start) before the plugin's code runs (a follow-up could hand BungeeCord the cached jars as Paper's loader does, which needs the class loader's `addURL`).
