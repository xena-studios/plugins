# zChat 4.0: 3.x's paths kept, formats in config.yml, messages in lang/, one line drawn for everyone (2026-11-25)

M3 (#124): zChat rewritten in place on the rewrite's core, as `zchat/api`, `common`, `bukkit` and `fabric`, on Paper, Folia, Spigot and CraftBukkit 1.8.8+ and Fabric 1.20.1, 1.21.11 and 26.3; network chat through Velocity and BungeeCord comes in a second pull request, on the proxy layer (#171). Laid out, migrated, documented and boot-tested as xUtilities 3.0 was ([the pilot](2026-11-24-xutilities-3-the-pilot.md)). What was decided:

- **3.x's config paths are 4.0's.** `formatting`, `filter` (with `filter.command`), `cooldown`, `anti-repeat`, `mentions`, `clearchat`, `mutechat`, `togglechat` and `private-messages` keep every setting where it was, so an owner's file needs no move but its messages, and the 3.2 jar put back reads 4.0's file as a newer one and keeps its formats, filter and commands. Config version 3; `migrate(1)` is 3.x's (zChat 2's example patterns), `migrate(2)` moves the messages out, the theme into `messages.theme` (a colour still on 3.x's default becomes `shared`) and `update-checker.enabled` to `updates.check`. A zChat 1.x file, another plugin, is moved to `config.yml.old`, as 3.x did. Going back is "rename `config.yml.bak-v2`", on the upgrade page.
- **Messages move to `lang/`; the chat formats stay in `config.yml`.** Every message zChat sends (the filter's, the cooldown's, `/mutechat`'s...) is in `ZChatMessages`, keyed by its 3.x setting (`cooldown.message` is `cooldown.wait`), and an owner's edits are carried into `lang/en.yml` on the first start with `messages.language: en`, as xUtilities did. The formats (`default-format`, the groups', the mention's, `/msg`'s and social spy's) are the server's look, the same for every reader, so they stay where owners set them; the theme's tags work in them. The carrying into `lang/en.yml` moved to core-jvm (`CarriedMessages`), which xUtilities now calls too, rather than a second copy.
- **One line drawn for everyone.** The core's chat bridge ([decisions/2026-11-25-the-chat-bridge.md](2026-11-25-the-chat-bridge.md)) at `LOW`, as 3.x's listener sat, with a `ChatRendering.same`: a format has no words of its own, so a line per language would draw the same thing several times; the mention highlight is the same for everyone, as in 3.x. On Spigot that becomes the event's own format when the line has no hover or click. A line per language (`byLanguage`) is there for a format that ever needs one.
- **The checks are 3.x's, cheapest first,** on one config snapshot per message: `/mutechat`, mute providers, the cooldown, the filter, anti-repeat, then mentions, `/togglechat`'s recipients, `ChatMessageEvent`, the rendering. Only a message that went out (the bridge's sent event) counts toward the cooldown and anti-repeat and pings anyone; what a message's checks worked out waits for that keyed by sender, so a message another plugin cancels leaves one entry until the sender's next message or quit, never a growing map.
- **The filter in common Kotlin, folded from tables.** 3.x folded with `java.text.Normalizer` (NFKD), which common code doesn't have. `Folded` keeps 3.x's rules (lowercase, number-for-letter swaps, a gap for anything else, marks and invisible characters skipped, runs of single letters joined, words split into one- and two-letter pieces) and folds accents from a table of Latin-1 and Latin Extended-A and -B, full-width forms by offset and the maths alphanumerics by block; every 3.x filter test passes on the JVM and on Wasm (Kotlin's own regex there has the lookbehind and `\p{L}` the patterns use). `filter.patterns` are Kotlin regular expressions: Java's on the JVM, as before.
- **Players' formatting:** without `color-permission`, what a player types is `Component.text`. With it, it's read as markup and then made inert (clicks, hovers and line breaks taken out, all the way down), and the filter sees the text with the tags taken out, as 3.x. `<rainbow>`, which our markup lacks, is the gradient it looks like. `%placeholders%` become slots of their own at load (`<papi-0>`), filled after parsing with the value's `&`/`§` colours read as styles, so a nickname can't inject a click, as in 3.x.
- **What 3.x kept on the player moves to a file.** Remembered `/togglechat` and `/socialspy` were Bukkit persistent data, which Spigot before 1.14 and Fabric don't have. 4.0 keeps them in `players.records` (the core's `FileRecordStore`), read once at startup, so a join is a map read; the Bukkit adapter brings a 3.x player's choice over as they join (1.14+, read only, so 3.2 put back still has it). Because zChat now keeps player data, `/zchat forget <player>` deletes it.
- **What only some servers have:** target selectors in `/msg` on Paper and Spigot 1.12.2+ (`Bukkit.selectEntities`; not Folia, which can't look across regions, nor Fabric, where they're names), for senders Minecraft allows them (`minecraft.command.selector`); PlaceholderAPI on Bukkit while it's enabled. MiniPlaceholders and Text Placeholder API aren't read: MiniPlaceholders gives Adventure tag resolvers and our renderer isn't MiniMessage, and Text Placeholder API is a compile dependency per Minecraft line; both wait for a minor, and a plugin can fill a format's tag through the API on every platform meanwhile.
- **Integration seams for the family.** `MuteProvider` (kept in spirit: a reason or `null`, now by `PlayerRef`, in markup) for xBans; `HiddenPlayers` for xVanish, asked beside the server's own visibility for mentions, `/msg` and its completion; `ChatPlaceholder` for tags such as xMoney's `<balance>`. Each list is an array swapped whole on change, so the hot path reads one field, and a hook that throws is dropped and logged. The five events are zChat's own, cancellable where 3.x's were, and on Bukkit also Bukkit events in `co.xenastudios.zchat.api.bukkit` made only when a Bukkit listener exists. The API's breaking changes are in the changelog and the Developer API page.
- **The core changed a little, each tested:**
  - xUtilities' `Sound` moved to core-common (`co.xenastudios.core.common.config.Sound`), since zChat's mention and `/msg` pings are the same setting; xUtilities imports it from there.
  - `locked` and `isFatal` in core-common are public: plugins' shared code has the same threads and the same rule about fatal errors (zChat's hooks).
  - `CarriedMessages` in core-jvm, from xUtilities' `JvmFiles` (above), with a test.
  - platform-fabric's check for Minecraft's own commands follows a redirect: `/tell` and `/w` are Minecraft's redirects to `/msg`, with no executor of their own, so zChat's `/msg` aliases were refused as another mod's (`MinecraftCommandsTest`).
- **Size: the Bukkit jar is 573 KiB, Fabric's 506 to 520 KiB (before Loom remaps them), over the 500 KiB target, and stay so** (the owner's rule: over it only with a recorded reason). About 410 KiB is the shared core zChat reaches, more of it than xUtilities' (the chat bridge on Paper and Spigot, the record store for remembered choices), 100 KiB zChat's own (the filter, formats, commands, five events and their Bukkit twins, the migration table), 13 KiB its seven translations in one entry. Nothing in zChat's own is optional; the core's share is the core's to shrink (#162). The lines in `gradle/jar-budgets.txt` are the sizes plus a tenth on Bukkit, a twentieth on Fabric, as xUtilities' are.
- **Startup and memory**, `scripts/budgets/check.sh` on Paper 26.3, M1 Pro, median of 3: 76 ms with the recorded startup list (678 classes, `zchat/bukkit/startup-classes.txt`), 122 ms without, under the first plugin's 150 ms; heap 1.6 MB; idle 0 ms a tick. **Metaspace is 1.64 MB, over the 1.5 MB a plugin gets** (xUtilities: 1.48 MB on the same machine): 570 classes, three quarters of them the core's. Making `/msg`'s class lazy changed nothing measurable, and the rest zChat loads at startup (its config sections, the filter, the chat module, the events the Bukkit bridge names) is what runs on the first message. So the Boot workflow's zChat budget step reports metaspace rather than failing on it, with this reason; the core's own trim (#162) is what brings it under.
- **Booted** with `zchat/bukkit/boot.sh` on Paper 26.3 and 1.21.11, Folia 26.3 and Spigot 1.8.8 (on Java 21 locally; CI runs it on Java 8), and `scripts/boot-fabric.sh` on Fabric 1.20.1 and 26.3: every command from the console, `/filter`'s edits, a reload, debug and a datapack reload. Two real clients chat on Paper 1.21.11 and Spigot 1.8.8 (`client.js --plugin zchat`: Joiner, an operator in German, and Friend): the format, the filter censoring Friend, a mention highlighted with its ping, `/msg` and `/reply`, `/togglechat` in German. The family test passes with zChat beside xSample, xTwin and xUtilities on Paper 26.3, Spigot 1.8.8 and Fabric 26.3.
- **Release:** `zchat/bukkit` applies `xena.release` for every jar, Modrinth `zchat`, Hangar `zChat`, voxel.shop 10708, bStats 21533 (3.x's); version 4.0.0, unreleased, its pages at `/zchat/next/` and 3.2's at `/zchat/v3/` (`versions.json`'s `unreleased`), `modrinth.md` unchanged.
- **Not done:** an importer from other chat plugins: their per-player data is mostly ignore lists and nicknames zChat doesn't have, and formats don't map one to one, so it's not cheap. Native review of the seven drafts. 3.1.2's keeping of another plugin's component (an `[item]` tag's hover) once zChat draws the format: the bridge carries text on every platform, so the text is kept, its hover isn't (in the changelog).
