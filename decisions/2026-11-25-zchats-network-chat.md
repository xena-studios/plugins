# zChat's network chat: each server draws and checks its own, the proxy only carries (2026-11-25)

zChat 4.0's network part (M3, #124): chat and private messages across a Velocity or BungeeCord network, on the proxy layer ([decisions/2026-11-25-the-proxy-layer.md](2026-11-25-the-proxy-layer.md)). zChat runs on each server and on the proxy (`zchat/velocity`, `zchat/bungee`), talking on `xena:zchat`. What was decided:

- **The sender's server draws the line, once; the others show that line.** A format, the sender's group (a permission check only their server can make) and their placeholders (PlaceholderAPI, other plugins' tags) are known only where the sender is, so the server that heard the message draws it as it does for its own players and sends the drawn line, our `Component` as bytes (`Lines`: text, style, click, hover, children, bounded in depth and parts). Each receiving server puts `network.server-format` (`[lobby] `) in front and sends it to its players who haven't hidden chat. Not chosen: sending the message and redrawing it on each server, which would need every server to know every sender's permissions and placeholders, and would draw a line per server rather than once.
- **The checks stay where the player is.** The filter, `/mutechat`, the cooldown, anti-repeat and other plugins' mute providers run on the sender's server before anything leaves it, exactly as for local chat, so a muted or filtered line never reaches the network. Network-wide mutes are a punishment plugin's (xBans through `MuteProvider`), not zChat's: `/mutechat` and `/clearchat` stay each server's. The receiving server applies what's about its own players: hidden chat, and the mention ping for a player named on another server.
- **The proxy only carries** (`Relay`): it keeps who's on the network and on which server, from its own joins, switches and quits, tells every server (`you` as a server first says `hello`, then `joined` and `left`), relays chat lines to every server with a player on it, with where they came from (the proxy's to say, never the sender's), and routes a private message by name to the recipient's server and the answer back (`pm`, `pm-done`). It has no config: each server decides what it sends and shows (`network.chat`, `network.private-messages`). Its command is `/zchatproxy` (`/zcp`), so a player's `/zchat reload` still reaches their server, which the proxy would otherwise answer.
- **`NO_PLAYER` is fine for chat.** A message rides a player's connection, so a server with nobody on it neither sends nor gets chat, which nobody there would see. Chat is never queued or put through the change feed: a line minutes late is wrong. A server learns its name and the roster from the proxy's answer to its first player's hello (retried for ten seconds, as the connection carries plugin messages a moment after joining). A private message whose answer doesn't come in ten seconds tells the sender the player wasn't found.
- **Private messages:** `/msg` completes and finds players on every server from the roster; the recipient's server delivers it in its own format and sound and keeps the reply target, the sender's server shows the sender's line once the recipient's says it arrived, and `/reply` answers across. Spies see what's sent or received on their own server.
- **Read at startup.** `network.enabled` opens the proxy channel as the plugin enables, as the proxy layer's channels open once; the rest of `network` applies on reload.
- **Not on Fabric yet:** the proxy layer has no Fabric end (FabricProxy-Lite's forwarding and Fabric's plugin messages), so a Fabric server with `network.enabled` says its chat stays on it.
- **The build learnt two things for it:** `scripts/boot-proxy.sh --two-backends` boots a second backend ("game") beside the first with `--backend-seed` for a plugin's config, and `client.js --plugin zchat-network` puts a client on each (Friend moves with `/server game`); `xenaRelease`'s jars take `hangarVersions`, since Hangar lists Velocity's own versions (3.4, 3.5) where Modrinth lists Minecraft's (`ReleaseTest`).
- **Also fixed:** a hand-written `config.yml` holding only 4.0's settings (`network:` alone) was taken for zChat 1.x's and set aside; the check now knows every 4.0 section.
- **The relay's start does only what must happen at enable on the proxy's thread:** the proxy channel and the relay's join, switch and quit listeners. The `/zchatproxy` tree, the admin subcommands and the English fallback messages are made on first use, from the plugin's own thread just after enable (`ZChatProxy.start`), as xSample's proxy entry points do. On BungeeCord, whose onEnable is all core and plugin code, that took the two-core median from 157 to 122-133 ms.
- **Measured:** the relay's jars are 390 KiB on Velocity and 386 KiB on BungeeCord after R8, under 500; the Bukkit jar grows to 615 KiB with the proxy layer's server end. Each proxy jar has its recorded startup list (559 classes on Velocity, 552 on BungeeCord). Startup against the first plugin's 150 ms, median of 3 boots on an M1 Pro (`boot-proxy.sh --startup-budget`): 41.1 ms on Velocity 3.4.0, 43.3 on 3.5.1, 41.1 on 4.3.1, 52.1 on BungeeCord 2111, 44.7 on Waterfall. In a Linux container on two cores of it (CI's runners have 2 vCPUs), median of 7 boots after an unmeasured first boot in the same folder: 80.1 ms on Velocity 3.4.0 (Java 21), 80.1 on 4.3.1 (Java 25), 132.9 and 122.0 on BungeeCord 2111 (two runs; xSample's was 138.6 in the same container that day). BungeeCord is the narrowest, as for xSample.
- **Booted:** Velocity 4.3.1 in front of two Paper 1.21.11 servers and BungeeCord 2111 in front of two Spigot 1.8.8 servers (Java 25 for Velocity, 21 for the rest, locally), a real client on each server: chat from lobby reaches game and back, `/msg` reaches the other server and `/reply` answers it, and each server's console logs the other's lines. The relay alone on Velocity 3.4.0, 3.5.1 and 4.3.1, BungeeCord and Waterfall. Common tests (`NetworkTest`, on `FakeNetwork`) cover the roster, chat in the sender's format with its mention pinged on the other server, the filter applied before a line leaves, hidden chat, private messages and replies across, and an unknown player.
