# xBans 2.0: the database is the truth, the proxy is the door, and nothing gets in when it can't check (2026-11-26)

M6 (#127): xBans rewritten in place on the rewrite's core, as `xbans/api`, `common`, `bukkit`, `fabric`, `velocity` and `bungee`, on Paper, Folia, Spigot and CraftBukkit 1.8.8+, Fabric 1.20.1, 1.21.11 and 26.3, Velocity 3.4+ and BungeeCord. Laid out, migrated, documented and boot-tested as xMoney and xTeleport 2.0 were ([xTeleport 2.0](2026-11-26-xteleport-2.md)); the Java 1.x plugin is gone from the tree (the `maintenance` branch keeps 1.x), and with it 1.x's flaky prune test (#149), replaced. What was decided:

- **1.x's tables and rules, byte for byte.** `punishments`, `removals`, `players` and `ips` keep 1.x's columns, types and schema version (1), made with 1.x's own statements (`store/Tables`, `{rowid}` and `{table}` filled per dialect); 2.0 adds no table and no column, so either jar reads the other's database, hashed IPs and `ip-salt.txt` included. 1.x's rules are 2.0's: LiteBans' arguments (`Args`), lengths (`model/Length`), what a new ban replaces and when it's refused (`model/Entry`'s `Replacing`, 1.x's table), weights, limits, templates and ladders, IP keys as Java's `InetAddress` writes them. Tested against a 1.0.1 database (`bans-1.0.1.sql`), and its config as shipped and as edited (`config-1.0.1*.yml.txt`, kept as `.yml.txt` because their blank MySQL password is a setting, not a credential, as xTeleport's).
- **1.x's config paths are 2.0's.** Config version 2; `migrate(1)` moves the messages to `lang/en.yml` (the owner's edits carried, 1.x's keys kept for screens and broadcasts, `messages.<x>` becoming `<x>`, `messages.error.*` the core's), the theme into `messages.theme` and `update-checker` into `updates`. The old file is copied aside as `config.yml.bak-v1`, and going back is renaming it, on the upgrade page; without it the 1.0.1 jar reads 2.0's file as a newer one and keeps every setting.
- **The network: the shared database is the source of truth, the proxy enforces at the door.** Not chosen: the proxy layer as the truth (a ban kept by the proxy and pushed to servers), which would lose bans with the proxy, and leave a server without one on its own. Every server and the proxy run xBans on one MySQL database, each with what's in force in memory, kept current by the core's change feed (`Network`, with resync and retries, as 1.x's network mode). The proxy runs the whole plugin against the same database: it refuses a globally banned player at `LoginEvent` (asynchronously: Velocity's `EventTask`, BungeeCord's intent), refuses a scoped ban at the server switch (`ServerPreConnectEvent`, `ServerConnectEvent`), and disconnects a player banned or kicked while online. It tells players nothing on its own: on a network the servers broadcast, so the proxy's broadcasts go to its console only (`tellsPlayers`).
- **The fast path rides the proxy channel; `NO_PLAYER` falls back to the feed.** A server that bans or kicks someone sends the proxy the punishment's id on `xena:xbans` (`enforce`, signed like every proxy-channel frame), and the proxy reads it from the database and acts at once, marking it heard so the feed's copy isn't applied twice. A message rides a player's connection, so with nobody on the server, or no secret, it isn't sent: the feed brings the same punishment within `check-every` seconds. Nothing is ever carried only by the channel.
- **Fail closed, and say so.** A ban plugin that lets everyone in while its database is down lets banned players in. Until a server or the proxy has read every ban in force, nobody joins: a login waits up to 10 seconds (`WAIT_SECONDS`), then is told the server is starting; a database that won't open is tried again every 15 seconds, said once in the console. Once open, what's in force stays in memory and is enforced through any database outage; writes fail visibly. Without xBans on the proxy, each server enforces at its own login, as 1.x did.
- **zChat reads xBans' mutes** through zChat 4.0's own seam (`ZChatApi.registerMuteProvider`), by reflection, since zChat's `PlayerRef` is its own relocated core's: a muted player can't chat or `/msg` through zChat, on every server of a network. The family test boots both on Paper 1.21.11 and Spigot 1.8.8 with real clients.
- **The staff layer for xVanish** is in the API: `isStaff` (`xbans.staff`, which operators have, or any permission to punish), `onlineStaff`, `notifyStaff`, and `StaffNotifyEvent` before every staff notification, xBans' own included, whose recipients a vanish plugin can change. Silent punishments are `withSilent` and `withExtraSilent`.
- **Events:** `PunishEvent` and `PardonEvent` cancellable, `PunishedEvent`, `PardonedEvent`, `LoginDeniedEvent`, `StaffNotifyEvent`, each fired only when something listens, and on Bukkit also Bukkit events (`co.xenastudios.xbans.api.bukkit`). **`LoginDeniedEvent` can't be cancelled:** a plugin that wants a banned player in should lift the ban, which is recorded, rather than undo a refusal nobody sees.
- **Admin under `/xbans`** (the proxy's `/xbansproxy`, `/xbp`, so a player's `/xbans` still reaches their server): reload, debug, import (vanilla, EssentialsX, LiteBans, AdvancedBan; LiteBans and AdvancedBan from MySQL or MariaDB only, as servers have no H2 or HSQLDB driver) and forget. **`forget` deletes a player's IPs and their `players` row, and keeps their punishments.** A ban is a record of what someone did, kept so they can't come back on it: a legitimate interest, and a ban plugin whose bans its players could erase by asking would ban no one. `/prunehistory` still deletes what's no longer in force, as 1.x did. Both are on the privacy page.
- **Messages** in `lang/en.yml`, every 1.x message among them, ban screens drawn per the player's language (the family's player cache knows the language of a player who isn't online yet), de, es, fr, pt-BR, ru, pl and zh-CN drafted by machine and marked as drafts. A message about a punishment may use any of a punishment's placeholders: the core's `MessageBundle` learnt optional placeholders for it (below).
- **Fabric's limits:** Minecraft has no event before a command runs, nor for signs, books or anvils, so on Fabric a mute blocks chat, `/me` and `/say` (Fabric's message events) and zChat's `/msg` and `/reply`, and `mutes.blocked-commands`' other commands, signs, books and anvils are Bukkit's. Said in the config's comments and on the overview.
- **Tests can't hang.** Every command test runs on the fake platform with virtual time (`VirtualScheduler(Threading.PROXY)`, which runs work when it's due, not on the next tick) and waits on what it awaits, never on sleeps; `xbans/common` gives every test task a 5-minute timeout. #149's guarantee (a dry run first, then only what's no longer in force goes) is `XBansTest.pruneDeletesOnlyWhatsOver`, deterministic.
- **The core changed, a little, each tested:**
  - `MessageBundle.message(..., optional = ...)` and `MessageKey.optional`: placeholders a message may use and its English doesn't, which `TranslationCheck` doesn't count as dropped (`anOptionalPlaceholderMayBeUsedOrLeftOut`). No class more at startup.
  - `core/platform-fabric/settings.gradle.kts`: the `xbans` branch and its substitution.
  - `scripts/boot-proxy.sh --proxy-seed` (a folder copied into the proxy's, for the network test's database settings), and `scripts/budgets/bots/client.js`'s `xbans` and `xbans-network` scenarios.
- **Startup and memory.** On Paper 26.3 in a Linux container on two cores (`scripts/budgets/check.sh`, median of 5): startup 68 ms with the recorded startup list, heap 0.9 MB, idle 0 ms a tick, **metaspace 1.483 MB** of the 1.5 MB a plugin gets (456 classes); on an M1 Pro 50 ms and 1.479 MB (xTeleport, measured the same day beside it: 1.478 MB). On the proxies, alone, median of 3 on an M1 Pro (`scripts/boot-proxy.sh --startup-budget 150`, with their recorded lists): Velocity 4.3.1 51 ms, BungeeCord 55 ms; metaspace in xBans' own loader on BungeeCord 1.43 MB (419 classes; its libraries, in a loader of their own, 3.0 MB), and on Velocity 4.39 MB in one loader that holds xBans and its libraries together (808 classes), about what BungeeCord's two loaders hold together. The proxies' metaspace isn't budgeted in CI; these are for the record. The first build was at 1.591 MB without a startup list, and 1.533 MB with one after the first trims: what brought it down, each the lighter core's method ([decisions/2026-11-25-a-lighter-core.md](2026-11-25-a-lighter-core.md)): what runs only past startup is in classes of its own, loaded with its first use (the API's calls, joins, logins and the proxy's fast path in `Calls`; the database's writes and lookups in `store/Writes.kt` and `store/Lookups.kt`; IP hashing, which only a hashed database needs, in `store/IpHashing.kt`; what messages draw in `TextsDrawing.kt`; the punisher, the commands' actions and the admin parts), pinned in `bukkit/r8/xbans.pro` so R8 doesn't inline them back; the functions handed to the core at startup (a length's config type, the first tables, the 1.x migration) one class (`Startup`) rather than a lambda each, `Texts` its own `AdminText`, a field rather than `by lazy`, a loop rather than a regex for the catalogue's tags, no `when` over an enum where it's read at startup, and the Paper listeners loaded only where the server has what they use. The startup lists are recorded (`bukkit/`, `velocity/`, `bungee/startup-classes.txt`). A startup list adds about 40 KB to the metaspace measured, as every class it names is loaded and linked ahead rather than as found, so the budget is met with it in the jar, as CI measures.
- **Size: the jars are over the 500 KiB target, and stay so.** Shrunk: Bukkit 815 KiB, Velocity 741, BungeeCord 732, Fabric 718-727 (its core relocated). About 420 KiB is the shared core xBans reaches: its database layer and change feed, the proxy layer's server end, commands, config, messages and the family. About 300 KiB is xBans' own with its API: 1.x's punishing rules, what's in force, the store and its 1.x statements, network mode and the proxy's door, every command, four importers, IP keys with their own SHA-256 and HMAC (no `java.security` in common), the Bukkit and Paper guards and the five Bukkit events; 36 KiB the seven translations, 7 KiB bStats. The drivers aren't in it: they're downloaded where the server has none. Cutting it would cut features 1.x has.
- **Booted** (locally, and in the Boot workflow's cells): Paper 1.21.11 and 26.3, Folia 26.3, Spigot 1.8.8 (Java 8), every console command and a reload; Velocity 3.4.0 and 4.3.1 and BungeeCord alone; Fabric 1.20.1, 1.21.11 and 26.3. Real clients with zChat on Paper 1.21.11 and Spigot 1.8.8: a ban, a tempban expiring, a mute blocking zChat's chat and `/msg`, a kick, replies in German. The network test, Velocity in front of two Paper 1.21.11 servers and BungeeCord in front of two Spigot 1.8.8 servers, all on one MariaDB, with real clients: a mute made on lobby blocks chat on game, a ban made on lobby takes the player off the network, the proxy turns them away at login, and an unban lets them back.
- **Release:** `xbans/bukkit` applies `xena.release` for the Bukkit, Velocity, BungeeCord and Fabric jars, Modrinth `xbans`, Hangar `xBans`, voxel.shop 10714, bStats 35418 (1.x's); version 2.0.0, unreleased, its pages at `/xbans/next/` and 1.0.1's at `/xbans/v1/` (`versions.json`'s `unreleased`), `modrinth.md` unchanged.
- **Not done:** native review of the seven drafts; an import from LibertyBans; LiteBans' and AdvancedBan's local H2 and HSQLDB files (no driver on servers); wildcard IP bans, `/staffrollback`, `/lockdown` and a web interface, as in 1.x; the proxy channel and xBans' commands on Fabric behind a proxy (the proxy layer has no Fabric end yet: a Fabric server on a network works through the database alone).
