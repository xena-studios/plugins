# xMoney 2.0: 1.x's tables and paths kept, Vault from 1.8.8, the database off the server thread (2026-11-26)

M4 (#125): xMoney rewritten in place on the rewrite's core, as `xmoney/api`, `common`, `bukkit` and `fabric`, on Paper, Folia, Spigot and CraftBukkit 1.8.8+ and Fabric 1.20.1, 1.21.11 and 26.3. Laid out, migrated, documented and boot-tested as zChat 4.0 was ([zChat 4.0](2026-11-25-zchat-4.md)); the Java 1.x plugin is gone from the tree. What was decided:

- **1.x's tables, byte for byte, so either jar reads the other's database.** `accounts`, `balances` and `transactions` keep 1.x's columns, types, indexes and schema version (1), uuids as their 36 characters, amounts as `BIGINT`s of ten-thousandths. 2.0 adds no table and no column, so the 1.0.1 jar put back reads a 2.0 database as its own: checked on Paper 26.3 with the released jar, 1.0.1 → 2.0 → 1.0.1, balances, history and the edited messages (from `config.yml.bak-v1`) all there. 1.x's `commit_id` stays, empty: the core's writer finds a lost commit by its own marker now.
- **1.x's config paths are 2.0's.** Config version 2; `migrate(1)` moves the messages to `lang/en.yml` (the owner's edits carried by `CarriedMessages`) and the theme into `messages`. The old file is copied aside as `config.yml.bak-v1`, and going back is renaming it, on the upgrade page. Every 1.x feature keeps its command, permission and setting: `/balance`, `/pay` (with its confirmation above `pay.confirm-above`), `/baltop`, `/eco give|take|set|reset|history`, `/xmoney status` and `import`, the formats, the starting balance, the limits.
- **Money is exact, and the server thread never waits for the disk.** Amounts are `Long` units of 1/10000, as in 1.x; the API's `Amount` takes `BigDecimal` and `double` in with an explicit rounding, and Vault's doubles are rounded as 1.x did (deposits down, withdrawals and `has` up). The database is opened, migrated and every balance read on an async task (1.x opened it in `onEnable`: 232 ms on the server thread). A player's pre-login waits for the balances; a Vault call made in the moments before they're read waits for them, at most 30 s.
- **On one server memory is the truth; on a network the database decides what takes money.** As 1.x: a change is checked and applied under the account's lock and queued, with its ledger row, for the core's one writer, so a crash or kill loses at most what wasn't committed and never doubles anything (KillTest kills a writing JVM and checks every balance against its ledger). On a network (MySQL, `network.enabled`), withdrawals, transfers and `set` run as their own transaction (`UPDATE ... WHERE balance >= ?`), queued then either started by the writer or abandoned by the caller, never both; deposits are applied at once and saved in batches; the change feed tells the other servers. 1.x's network tests are ported (two servers on one MariaDB, the database going away mid-payment, a lost commit answer, concurrent writers) and pass against MariaDB 11.
- **Vault from 1.8.8.** The Bukkit jar carries VaultUnlockedAPI 2.20 with Vault's API, unrelocated and unmodified (LGPL-3.0), says `provides: [Vault]` and `loadbefore: [Vault]`, and registers both economies at the highest priority as it enables. Bukkit has `provides` from 1.15.2; below it Vault.jar goes beside xMoney, and xMoney registers under Vault.jar's own `Economy` class too, through a proxy, whichever copy a plugin was linked against. The Permission fallback (`SuperPerms`) only when no real Vault is installed, as Vault did.
- **Fabric: the Common Economy API.** xMoney is its provider on every line: 1.1.1 on 1.20.1 and 1.2.1 on 1.21.11 (`long` amounts), 2.0.0 on 26.3 (`BigInteger`), told apart by a Stonecutter constant (`economy_bigint`). **Text Placeholder API isn't read:** it's a compile dependency per Minecraft line and has no build for 1.21.11; zChat's `<balance>` tags work on Fabric meanwhile.
- **zChat's tags and the family's seams.** On Bukkit and Fabric xMoney fills zChat 4.0's `<balance>`, `<balance_raw>`, `<balance_short>` and `<baltop_*>` through its `ChatPlaceholder` seam, found by name (each plugin has its own relocated core and Kotlin, so the seam is called through a proxy of zChat's own interface). For xPlots, xVote and xMarket: every change has a `TransactionKind` and a source, `PreTransactionEvent` is cancellable, `TransactionHook`s let an add-on refuse a change with a reason, and `BalanceChangedEvent` comes after it's saved; on Bukkit all of them are Bukkit events too.
- **Admin under `/xmoney`:** reload, debug, import (EssentialsX, CMI, the economy registered with Vault, with 1.x's dry run and confirmation) and forget. **`migrate` isn't there:** the core's command switches storage on a running server, which for money means stopping every write and every other server first; 1.x had no such command, and it isn't cheap to make safe. Moving between SQLite and MySQL is the upgrade page's steps.
- **Messages** in `lang/en.yml`, with de, es, fr, pt-BR, ru, pl and zh-CN drafted by machine and marked as drafts in their files and on the docs, as zChat's are.
- **The core changed, each change tested:**
  - In #180: `concurrentMap()` in core-common (xMoney's accounts; zChat's own copy removed), `Database.available` (whether the writer can reach its database, for `/xmoney status` and the network's refusals), the lost-commit lookup locking on MySQL (`LOCK IN SHARE MODE`, so it waits for a commit still being made; a MySQL test fails without it), `JdbcDatabase.openWith` public for plugins' own crash tests.
  - In #181: a database's close copies its open readers before closing them (a reader closing itself at the same moment threw on the writer, and close never answered).
  - Here: `CommandTypes.PERMISSION` and `ALIAS` in core-common, the config types zChat and xUtilities each had; platform-fabric's `xmoney` branch, its `economy_bigint` constant and the Common Economy API versions; and three startup trims, below.
- **Startup and memory.** On Paper 26.3 in a Linux container on two cores (`scripts/budgets/check.sh`, median of 5): startup 50 ms, heap 1.9 MB, idle 0 ms a tick, **metaspace 1.486 MB** of the 1.5 MB a plugin gets (459 classes); on an M1 Pro 36 ms and 1.495 MB. The first build was at 1.77 MB: a database, Vault's two APIs and their economies are what zChat doesn't load. What brought it under, each the lighter core's method ([decisions/2026-11-25-a-lighter-core.md](2026-11-25-a-lighter-core.md)): what runs only once there's money moving is made then, not at enable (the ledger's writes and network code, the commands' actions, the API's changes, hooks and events, the Bukkit event bridge and Bukkit's event classes, the Vault bridge, the placeholders, debug and forget's parts, the 1.x config migration, the change feed off a network); startup callbacks are one class each rather than a lambda each; config amounts in plain form are parsed without loading the general decimal parser; and in the core, `Sql` joins column names with a loop rather than `joinToString`'s lambdas, the JDBC writer's threads, reads and connections are classes, and `AdminCommands`' handlers are one class (every plugin with a database or admin commands starts with fewer lambda classes). Classes R8 would inline back into what loads at startup are pinned (`bukkit/r8/vault.pro`). The startup list was recorded again (`bukkit/startup-classes.txt`).
- **Size: the Bukkit jar is 762 KiB, over the 500 KiB target, and stays so** (over only with a recorded reason). 416 KiB is the shared core xMoney reaches, more than zChat's: the database layer (JDBC writer, migrations, the change feed for networks, driver fetching), on top of config, messages, commands and the family. 179 KiB is xMoney's own (the ledger and its network transactions, Vault 1 and 2 economies and the Permission fallback, imports from three plugins, commands, placeholders), 28 KiB its API (kept whole for plugins), 25 KiB Vault's and VaultUnlocked's APIs, which must ship whole and in their own names, 17 KiB the seven translations, 15 KiB the licence texts the LGPL needs. SQLite and MySQL drivers aren't in it: fetched on demand when the server has none. Fabric's jars are 605 to 635 KiB for the same reason. `gradle/jar-budgets.txt` has the sizes plus a tenth on Bukkit and a twentieth on Fabric.
- **Booted:** see the pull request for the matrix that ran (Paper and Folia 26.3, Paper 1.21.11, Spigot 1.8.8 with Vault.jar, Paper 26.3 beside VaultUnlocked, Fabric 1.20.1, 1.21.11 and 26.3, a real client paying another on Paper 1.21.11 and Spigot 1.8.8, zChat's `<balance>` in chat), each in the Boot workflow.
- **Release:** `xmoney/bukkit` applies `xena.release` for the Bukkit and Fabric jars, Modrinth `xmoney`, Hangar `xMoney`, voxel.shop 10715, bStats 35421 (1.x's); version 2.0.0, unreleased, its pages at `/xmoney/next/` and 1.0.1's at `/xmoney/v1/` (`versions.json`'s `unreleased`), `modrinth.md` unchanged.
- **Not done:** native review of the seven drafts; Text Placeholder API (above); `/xmoney migrate` (above); a real multi-server network on separate machines (the network tests run two servers' ledgers against one MariaDB in one JVM).
