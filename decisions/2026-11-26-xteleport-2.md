# xTeleport 2.0: 1.x's tables and paths kept, teleports and RTP off the server thread where the server allows, seams for the family (2026-11-26)

M5 (#126): xTeleport rewritten in place on the rewrite's core, as `xteleport/api`, `common`, `bukkit` and `fabric`, on Paper, Folia, Spigot and CraftBukkit 1.8.8+ and Fabric 1.20.1, 1.21.11 and 26.3. Laid out, migrated, documented and boot-tested as xMoney 2.0 was ([xMoney 2.0](2026-11-26-xmoney-2.md)); the Java 1.x plugin is gone from the tree (the `maintenance` branch keeps 1.x). What was decided:

- **1.x's tables, byte for byte, so either jar reads the other's database.** `homes`, `warps`, `spawns` and `players` keep 1.x's columns, types, keys and schema version (1), uuids as their 36 characters; 2.0 adds no table and no column. 1.x's single database thread is the core's one writer now, and a player's homes are read on the writer too (`Database.session`), so a read always sees every write asked for before it, as 1.x's thread guaranteed. Tested against a 1.0.1 database (`teleport-1.0.1.sql`, made with 1.x's own statements): read as it is, written as 1.x writes, the schema unchanged and 1.x's own queries reading 2.0's rows.
- **1.x's config paths are 2.0's.** Config version 2; `migrate(1)` moves the messages to `lang/en.yml` (the owner's edits carried by `CarriedMessages`), the theme into `messages.theme` and `update-checker` into `updates`. The old file is copied aside as `config.yml.bak-v1`, and going back is renaming it, on the upgrade page; without it the 1.0.1 jar reads 2.0's file as a newer one and keeps every setting. 1.0.0 and 1.0.1 shipped the same config and schema, so one fixture (and an edited copy of it) covers every release. Every 1.x feature keeps its command, aliases, permission and setting: homes (limits by permission and group, the bed home, staff's `<player>:<home>`), TPA (several requests, `/tpahere` paid by whoever asked, `/tptoggle` kept through restarts), warps (per-warp permissions), the spawn on first join, every join and respawn, `/rtp` with both cooldowns, the warmup with its countdown, cooldowns, costs, the safe-arrival check, `/xteleport import essentials` and `rtpcheck`, PlaceholderAPI's five placeholders. 1.x had no `/back`: it's xUtilities', which hears xTeleport's teleports on Bukkit as before.
- **One server seam, `TeleportServer`, written by each adapter**, as xUtilities' `Server`. The shared code works out every teleport, the safety check and the RTP search itself; the adapter reads blocks as `BlockKind` flags (solid, full, water, hurts, climbable, leaves, bedrock, the two short heights, liquid), worked out once per block type from Bukkit's `Material` names (1.8.8's included) or Minecraft's tags, so `common` never names a platform's materials and the rules are the same everywhere.
- **Nothing waits on a chunk on a server thread where the server can help it.** Paper and Folia: `getChunkAtAsync` and `teleportAsync`, the column read on the region's thread. Fabric: the chunk system's own future (`getChunkFuture`, generating off the server thread; `only-generated` reads the chunk only as far as `EMPTY`, which makes nothing, and goes on only if it's `FULL`), then Minecraft's teleport. Spigot and CraftBukkit have no background loading: chunks load on the main thread through a queue that loads every chunk already loaded at once and at most one that isn't a tick, and runs only while chunks are waiting. Each RTP search reads at most one column a tick (the next candidate waits for the last), one search per player, `max-searches` at once.
- **Spawn without a teleport where the server allows.** Paper's `AsyncPlayerSpawnLocationEvent` where it has it; Spigot from 1.8.8 (and Paper before it): `PlayerSpawnLocationEvent`; CraftBukkit and Fabric: a teleport just after joining. `/spawn` before `/setspawn` stands on the main world's spawn point, lifted onto the ground when the point isn't safe: servers before 1.13 keep it below the surface (found on Spigot 1.8.8 with a real client).
- **Costs through xMoney's API, Vault's economy as before.** xMoney has its own relocated core, so its `PlayerRef` and `Amount` aren't ours: `XMoneyEconomy` (jvmMain) calls the API by name through xMoney's class loader (`PlayerRef.parseOrNull`, `Amount.ofUnits`), the methods found once. The teleport is the ledger's reason ("Teleport: home"), a refund its own. Without xMoney on Bukkit, any economy registered with Vault, called the same way, as 1.x took them. A real client paid 5 for `/spawn` through xMoney on Paper 1.21.11 and Spigot 1.8.8.
- **The family's seams, in the API.** `teleport(player, location, options)` with xTeleport's warmup, cooldown, cost and safety check, and `teleport(player, destinationName, options)` for destinations add-ons register by name (`registerDestination`: xLimbo's way back, a plot's entrance); `PreTeleportEvent`, `HomeSetEvent` and `TpaRequestEvent` cancellable as 1.x's were; `registerHomes` for homes from another plugin (xPlots' plot homes), listed and gone to but not counted or deleted; `registerVisibility` for who's hidden from whom, with the family's player cache's vanished players hidden too (xVanish, later), beside Bukkit's `canSee`. All by `PlayerRef` and core `Location`, `CompletableFuture`s for I/O and teleports, `XTeleport.api()` also in Bukkit's services manager, the events also Bukkit events in `co.xenastudios.xteleport.api.bukkit` (made with the first event, not at startup). ABI dumps in `xteleport/api/api/`; the breaking changes are on the Developer API page and in the changelog.
- **Admin under `/xteleport`:** reload, debug and forget (a player's homes and TPA setting), import (EssentialsX, Bukkit only: Fabric has nothing to import from, so the subcommand isn't there), and 1.x's `rtpcheck`. **`migrate` isn't there**, as for xMoney: 1.x had none, and moving between SQLite and MySQL is a restart with the data moved.
- **Messages** in `lang/en.yml`, with what 1.x wrote in code (the import's and `rtpcheck`'s replies) there too, and de, es, fr, pt-BR, ru, pl and zh-CN drafted by machine and marked as drafts. The page footers keep 1.x's own keys (`homes.footer`, `warps.footer`), so an owner's edit carries.
- **Tests can't hang.** 1.x's tests sometimes held CI for 20 minutes. 2.0's command tests run on the fake platform with virtual time (no real waits); the database tests on SQLite have a 15-second bound on every future; `xteleport/common` gives every test task a 5-minute timeout.
- **The core changed, little:** three Stonecutter constants in platform-fabric (`chunk_result`, 1.20.5's `ChunkResult`; `respawn_data`, 1.21.9's `RespawnData`; `overlay_message`, 26.1's `sendOverlayMessage`), its `xteleport` branch and substitution. Nothing else: no core class loads more at startup, so xMoney's metaspace is untouched.
- **Startup and memory.** On Paper 26.3 in a Linux container on two cores (`scripts/budgets/check.sh`, median of 5): startup 65 ms with the recorded startup list (114 ms without), heap 2.7 MB, idle 0 ms a tick, **metaspace 1.474 MB** of the 1.5 MB a plugin gets (465 classes). The first build was at 1.497 MB: what brought it down, each the lighter core's method ([decisions/2026-11-25-a-lighter-core.md](2026-11-25-a-lighter-core.md)): the Bukkit event bridge made before the first event, not at enable; the stores' callbacks one class rather than a lambda each; Spigot's chunk queue and the block-kind table made with their first use; the placeholders with PlaceholderAPI's first ask; the teleporter, the RTP search and what the commands do (`Actions`) with their first use, pinned in `bukkit/r8/xteleport.pro` so R8 doesn't inline them back.
- **Size: the Bukkit jar is 727 KiB, over the 500 KiB target, and stays so** (over only with a recorded reason). About 400 KiB is the shared core xTeleport reaches, the database layer among it (as xMoney's): config, messages, commands, the family, the JDBC writer and migrations. About 212 KiB is xTeleport's own with its API: the teleport pipeline and warmups, the safety check and RTP search, homes, TPA, warps and the spawn, the store, every command, the import, the Bukkit and Paper paths and the four Bukkit events; 22 KiB the seven translations, 7 KiB bStats, 3 KiB the startup list. The drivers aren't in it: fetched on demand. Fabric's jars are 644 to 652 KiB. `gradle/jar-budgets.txt` has the sizes plus a tenth on Bukkit and a twentieth on Fabric.
- **Booted** (locally, and in the Boot workflow's cells): Paper and Folia 26.3 (three real RTP searches each, the End's on its outer islands), Spigot 1.8.8 (the End skipped: before 1.9 it has no outer islands), Paper 1.21.11 and Spigot 1.8.8 with two real clients (a home set and gone back to, `/tpa` accepted and Friend arriving after the warmup, an `/rtp`) and xMoney beside it (Friend paying 5 for `/spawn`), Fabric 1.20.1 and 26.3 (the same console checks; worlds as dimensions, typed without `minecraft:`).
- **Release:** `xteleport/bukkit` applies `xena.release` for the Bukkit and Fabric jars, Modrinth `xteleport`, Hangar `xTeleport`, voxel.shop 10712, bStats 35423 (1.x's); version 2.0.0, unreleased, its pages at `/xteleport/next/` and 1.0.1's at `/xteleport/v1/` (`versions.json`'s `unreleased`), `modrinth.md` unchanged.
- **Not done:** native review of the seven drafts; imports from HuskHomes and CMI (planned in 1.x too); Fabric's `xteleport.homes.<n>` read for a fixed set of numbers (its permission API answers one node at a time); the countdown on Spigot 1.8.8 (no action bar without NMS).
