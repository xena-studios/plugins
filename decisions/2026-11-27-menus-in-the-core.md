# Menus in the core: chest menus and deposits on every platform, made on first use (2026-11-27)

xMarket 1.0 (M9, #110) is the first rewritten plugin with inventory menus, and xPlots (M13) and xLimbo (M15) have menus today, so the core has them first: `co.xenastudios.core.common.menu` in core-common, implemented by platform-bukkit (`BukkitPlatform.menus`), platform-fabric (`FabricPlatform.menus`) and core-testing's `FakeMenus` for plugins' tests. What was decided:

- **A plugin's shared code says what a menu shows and does; the platform draws it.** A `Menu` is a title, 1 to 6 rows and an `Icon` per slot; an `Icon` is an item by its namespaced id (`minecraft:diamond`), an amount, the menu's own name and lore (our `Component`s, so they're translated like any message) and a shine, or the platform's full text of an item (`Icon.data`, as `Menus.data` writes it) for one that's more than its id: an enchanted book, a head, another plugin's item. Clicks come to a `MenuHandler` with the slot and a `Click` (left, right, shift, number key, drop and so on), on the viewer's thread. A `MenuView` changes a slot in place for one viewer, which an amount screen needs, rather than opening a new chest per click.
- **Nothing in a menu is real.** Every click and drag in a menu is cancelled, the player's own inventory below it included (a shift-click there would move an item into the chest), and only clicks on the menu's own slots reach the handler. On Bukkit it's cancelled at `HIGHEST`, after any other plugin had its say; on Fabric the menu's `clicked` never calls Minecraft's, then sends the client the truth again. A plugin creates items only once it has decided to (after a payment), so a menu can't be a source of duplicated items, which every shop plugin we looked at has had.
- **A deposit is the one menu with real items** (`Menus.deposit`: xMarket's `/sellgui`, later a plot's chest). Its items leave it as it closes, for whatever reason: closed, another menu opened, a quit or kick, a death, the plugin stopping (`closeAll`, which each platform's `close` or server stop runs). The chest is emptied before its `DepositHandler` hears of the items, so they're in exactly one place at every moment, and the handler gives back what it doesn't keep (`Menus.give`: into the inventory, the rest dropped). On a death, Bukkit fires the death event before clearing the inventory, so what's given back during it joins the drops (or stays, with `keepInventory`); Fabric closes the deposit in `ALLOW_DEATH`, before the inventory drops. A handler that throws gets its items given back rather than lost.
- **Made on first use, so no plugin pays for menus it doesn't open.** `BukkitPlatform.menus` and `FabricPlatform.menus` are a field and a getter until first asked (no class of the menus loads at startup, per decisions/2026-11-25-a-lighter-core.md); Bukkit's listeners are registered with the first menu (`registerEvent` with one executor class told apart by kind, no reflection) and unregistered by `closeAll`. Fabric's disconnect and death hooks are registered when its menus are made, and do nothing once closed, since Fabric's events can't be unregistered.
- **Bukkit 1.8.8 to the newest, one code path.** A menu's inventory is a chest whose holder is the menu's own; a click is matched by the viewer's open menu first (a map lookup) and the holder only for a chest, never by title. `InventoryView` is never called: it became an interface in 1.21, so code built against 1.8.8's API can't call it, and the top inventory and the raw slot come from the event. Names and lore are `§` strings with a reset first (no client italics), which every Bukkit server takes; a title is cut to 32 characters before 1.9. From 1.13 an icon's id is its material's key; before, a plugin that knows the old names and data values sets `BukkitMenus.legacyItems` (xMarket does). Full item data is Bukkit's own serialisation (`YamlConfiguration`), which reads back on the same or a newer server. The shine is 1.20.5's glint override, or a hidden enchantment before.
- **Fabric 1.20.1, 1.21.11 and 26.3:** vanilla's `ChestMenu` and `SimpleContainer`, players install nothing. Names and lore are data components from 1.20.5 and display NBT before; full item data is the item's SNBT (`ItemStack.CODEC` with the server's registries from 1.20.5, `save` before), so it reads back on that Minecraft line. 26.1 renamed a click's `ClickType` to `ContainerInput` and gave a drop a `Prediction`; Stonecutter switches both (`container_input`, `item_prediction`, `item_components`).
- **Not in the core:** Geyser forms for Bedrock players, Paper's dialogs, and anvil or sign text input. A plugin asks for a number in chat (xMarket's amount screen does), which works everywhere.
- **Tested** with `BukkitMenusTest` against Spigot 1.8.8's API (a menu's clicks cancelled and passed on by slot, the inventory below cancelled, a deposit emptied once on a close, a quit and a death, `closeAll`) and `MenusTest` on `FakeMenus`; on real servers through xMarket's boot tests and its real client, which opens `/shop` and buys from it.
