# The rewrite's APIs on Maven Central, made from the shipped jar (2026-11-27)

Each rewritten plugin with an API publishes it with its release ([the release set](2026-11-27-the-release-set.md)), as [developer APIs ship inside the plugin](2026-11-17-developer-apis-ship-inside-the-plugin.md) planned and xUtilities 3.0 required: "the published API has to carry the same relocation, or a consumer's calls won't link" ([the pilot](2026-11-24-xutilities-3-the-pilot.md)). Nothing is published yet: it ships as code and dry runs (#162, #120).

- **Two artifacts a plugin:** `co.xenastudios.<plugin>:<plugin>-api` (the API, plus the core's api types it exposes: `PlayerRef`, `PlayerRefs`, the event bus, relocated to `co.xenastudios.<plugin>.core.api` as the jar has them) and `co.xenastudios.<plugin>:<plugin>-api-bukkit` (its Bukkit events, `co.xenastudios.<plugin>.api.bukkit`, depending on the first). Each has sources and javadoc jars. The `-api` POM depends on `kotlin-stdlib` (its types are in the signatures; every Xena plugin downloads it at runtime). `-api-bukkit` leaves the server's API to the caller, as Spigot's isn't on Maven Central.
- **The classes are the shipped jar's.** `xena.release-api` (applied by `xena.release` to a rewritten plugin's release project when the plugin has an `api/` folder) takes them out of R8's output, the Bukkit jar that servers run. So a caller compiles against exactly what links at runtime: no relocation step of its own to drift, and no core type that R8 shrank away. Fabric and the proxies relocate to the same names, so the one artifact serves them all. `checkApiJar` (part of `check`) fails when an API jar names a class of the plugin's that isn't in it, counting only names that are real classes in the unrelocated JVM jars (Kotlin's metadata also names typealiases, such as `Pending`). It also fails when `PlayerRef` is there without `PlayerRefs`. That check is how #214 was found: R8 had shrunk `PlayerRefs`, the Java helpers every API page points to, out of every jar.
- **Checked by compiling a caller:** a Java plugin using `XBans.api()`, `PunishRequest`, `PlayerRefs.of`/`javaUuid`, `PunishEvent.TYPE` and a `@EventHandler` on `BukkitPunishEvent` compiles with `javac --release 8` against `xbans-api` and `xbans-api-bukkit` from the bundle (with Spigot 1.8.8's API and the stdlib). It runs against the shipped `xbans-2.0.0-bukkit.jar`, where `PlayerRefs` round-trips a UUID.
- **Sources and docs are the JVM's view, relocated.** `apiSources` merges each multiplatform file with its JVM side (a common file loses the `expect`s its `.jvm.kt` file has `actual`s for, and those lose `actual`), rewrites `co.xenastudios.core.` to the plugin's package, and leaves out core files the jar has nothing of (`Location`, `WorldRef`, `CoreApi` for xBans). Top-level functions whose file class isn't in the jar (`Pending`'s Kotlin helpers, which are `@JvmSynthetic` and shrunk) get `@suppress`. Dokka 2.3.0 (the version M0 tried) renders that view as HTML: the javadoc jar, and what `/api/<plugin>/` will serve. xBans' is 317 files and 4.6 MB.
- **Signing and upload run no project code.** Gradle writes each plugin's unsigned bundle (`releaseMavenBundle`, after `releaseAssemble`: POMs, jars, md5 and sha1 checksums) into `release/<plugin>/maven/`, which is attested with the jars. The verify job checks it against Central's requirements (`releaseMavenCentral`: name, description, url, license, developer and scm in each POM, sources and javadoc jars, checksums, no SNAPSHOT). Then release.yml's `maven` job, in the `release` environment, signs every file with `gpg` and uploads each bundle to the Central Portal's API (`publishingType=AUTOMATIC`), waiting for Central to accept it. Neither the signing key nor the Portal's token ever reaches a build script, as with the store tokens. It reuses the environment's `MAVEN_CENTRAL_USERNAME`, `MAVEN_CENTRAL_PASSWORD`, `SIGNING_KEY` and `SIGNING_PASSWORD`, which today's releases use. If any is missing the job stops with what to set and where, having sent nothing. A bundle Central already has is skipped on a rerun. A dry run never reaches the job. The job's signing was checked locally with a throwaway key: an imported ASCII-armored key and passphrase sign each of the 8 files, and each signature verifies.
- **Checked:** the full dry run of all seven merged rewrites writes and passes six artifact jars per plugin.
- **Dokka at `/api/<plugin>/`: not wired into the site yet. The plan:** the Docs workflow's build gains a JDK step that runs `./gradlew <project>:releaseApiDocs` for each plugin whose `versions.json` line has no `"unreleased"` (none today, so nothing would change until the release; an unreleased API's reference must not go live early). It copies each `build/dokka/api` over `dist/client/api/<plugin>/` before `scripts/postbuild.ts`, replacing the stub page `src/routes/api/$plugin.tsx` renders. Then `postbuild.ts` needs four changes, which is why this waits for a pull request of its own with the site build verified: hash Dokka's inline scripts in its CSP step (M0 counted 6); leave `/api/<plugin>/**` out of Pagefind and the sitemap (or index it on purpose); exempt Dokka's own links from the links validator or check them as they are; and give `/api/*` its own `Cache-Control`. File count: 317 files a plugin, about 4,500 for fourteen, under Cloudflare's 20,000 per version with today's site.
- **Left for later:** a Kotlin caller can't reach top-level extension functions (`uuid.toPlayerRef()`), because the plugin jars drop `META-INF/*.kotlin_module`. Java's `PlayerRefs.of` and Kotlin's `PlayerRef.of(uuid.toKotlinUuid())` work. Each Developer API page could add `-api-bukkit`'s coordinates beside `-api`'s.
