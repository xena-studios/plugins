# The family's backup seam: each database on the board, copied by its own writer (2026-11-27)

ROADMAP.md's family table says "xBackup: every plugin registers its data and pauses its database for a backup" (#130). xBackup 1.x had settled half of it (decisions/2026-11-18-xbackup.md, "SQLite by SQLite"): any SQLite file is copied with `VACUUM INTO` through the server's own driver, one read transaction, no cooperation needed. That stays as the fallback for every plugin that isn't one of the rewrite's. What it can't do is what the rewrite's plugins now need:

- **Spigot 1.8.8's SQLite is 3.7.2**, which has no `VACUUM INTO` (3.27), and Fabric has no driver of its own: the rewrite's core uses whatever driver it found or fetched, which xBackup, a separate plugin with its own relocated core, can't reach.
- **The family's shared file** (`plugins/Xena/xena.db`) has several plugins' writers on it at once.
- **MySQL** is outside the server: a backup should say whose data isn't in it, not leave the owner to find out at a restore.

So the core does it, and no plugin has code of its own for it.

- **The board carries it** (`FamilyBackups`, core-common: names and positions only, all `const`, so using it loads no class). As a `JdbcDatabase` starts it puts one entry in the board's `xena.backups.v1` map, keyed by plugin name and place, and takes it off as it closes (only if it's still its own: two plugins on the family's file each keep theirs). The entry is an `Object[]` of text, the board's rule: kind (`sqlite` or `mysql`), plugin, where (the file's absolute path, or `host:port/database`), description, table prefix, and for SQLite a handle.
- **The handle is the one thing on a board that runs.** It's a `java.util.function.Function<Object, Object>`, a JDK interface, so it's the same type in every plugin's copy of the core and of Kotlin, and only JDK values cross it: asked `{"snapshot", "<path>"}`, it answers at once with a `CompletableFuture` that completes with `null` once a consistent copy is whole at that path, or with a `String` saying why there's none. Not chosen: an interface of ours (a `ClassCastException` between relocated copies, the reason the board is JDK types at all), reflection on another plugin's classes (breaks under R8's renaming), or a pause/resume pair (a plugin that dies between the two would leave its writer stopped; one request that settles by itself can't).
- **The copy is made by the plugin's own writer, between two batches.** The handle queues it on the writer like a migration (`session`), so every write queued before the request is in the copy, none queued after it is, and the plugin's writes wait behind it in the queue, never on a game thread: that's the "pause", and it ends by itself. SQLite 3.27 and later: `VACUUM INTO`. Older (Spigot 1.8.8's 3.7.2): the driver's online backup (`backup to`), and if the driver has none, the file and its write-ahead log copied while this connection holds the write lock (`BEGIN IMMEDIATE`, so no connection, the family's on a shared file included, can commit meanwhile), then the log folded into the copy by a connection of its own. Proven by `FamilyBackupsTest`: a copy taken while another thread writes as fast as it can passes `integrity_check` and holds every write acknowledged before the request; each older path copies rows still only in the log.
- **No class at startup.** The handle is the readers' thread factory, `Runner`, which already existed (it now implements `Function` too); the entry is an array and a map the player cache already made; the work is `DatabaseSnapshot`, loaded the first time a backup asks. `JvmFamilyBoard.server` is where the database finds the board: each platform sets it as it finds the board (Bukkit and Fabric; the proxies have no xBackup). A plugin's core is its own relocated copy, so the static is one plugin's.
- **MySQL's entry has no handle.** xBackup records which plugins keep their data there and where, in the backup and in `/backup status`; dumping it is `mysqldump`'s job, on the database's own machine.
