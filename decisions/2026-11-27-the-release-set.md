# The release set: every new major in one run, checked before anything is sent (2026-11-27)

The release milestone ships every rewritten plugin at once ([the rewrites release together](2026-11-24-rewrites-release-together.md)). [One release workflow](2026-11-24-one-release-workflow.md) released one tag per run; this teaches it, and `scripts/release.ts`, to release the whole set. Nothing is released by it yet: it ships as code and dry runs (#162, #120).

- **One run for every plugin, not a tag push each.** `node scripts/release.ts --tag <release pull request>` starts the Release workflow once with every `<plugin>-v<version>` the pull request releases and its merge commit (`gh workflow run release.yml -f tags=... -f sha=...`). Separate runs couldn't stop together, and GitHub starts no workflow at all for a push of more than three tags. The github job makes each tag on that commit with its release (`gh release create --target`); a tag made with the workflow's token starts no other run. Pushing a single tag by hand still releases that one plugin.
- **All or nothing, as far as stores allow.** The build job assembles every plugin's jars into `release/<plugin>/` (`-Pxena.release.root`, one artifact). The verify job then runs every store task of every plugin with nothing sent, and each checks its exact payload against the store's schema and lists: Modrinth's `CreatableVersion` with Labrinth's own limits (version number 1-32 characters of its URL-safe set, name 1-64, changelog up to 65536) and its live loader and Minecraft version tags; Hangar's `VersionUpload` with its config's limits (version and channel patterns, 1-3 platforms, description up to 32000, 7 MB a file, 15 MB a version) and its live versions per platform; CurseForge's documented upload metadata; voxel.shop's form fields; both store pages' length limits. The schemas are vendored in build-logic (`xena/release/schemas/`), each saying where it was read. Attestations, stores and GitHub only start once all of that passes. After that, each store is a job of its own that publishes every plugin, rerunnable alone, and skips versions it has (CurseForge can't tell).
- **The same checks run before every real upload**, so a payload a store would refuse fails before the first byte leaves, in a dry run or not.
- **Hangar gets Waterfall and Velocity right.** A BungeeCord jar goes to Hangar as Waterfall's, whose versions are its own lines (`hangarVersions = listOf("1.21")`, the one CI boots); a jar without them fails rather than guessing from Minecraft's. A Velocity jar can say `hangarFrom = "3.4"`: every Velocity version Hangar lists from 3.4 on, read at the release, so 4.x (which CI boots) is listed without a change. xBans' and zChat's were `3.4, 3.5` only.
- **The release pull request switches the site.** `node scripts/release.ts --together` (every plugin whose `versions.json` line is "unreleased", or those named) takes `(unreleased)` and the "Not released yet" note off each changelog section, deletes `"unreleased"` from each line, renames a new plugin's `modrinth.draft.md` to `modrinth.md`, and adds the release to `docs/src/data/releases/<plugin>.json`, the download picker's list, with each jar's size and SHA-256 from a build of the set (`releaseAssemble` writes the entry as `site-release.json`, platforms filtered to the site manifest's released ones). Checked end to end without pushing: the commit touched 24 files, and the site built from it serves each new major at `/<plugin>/` with every jar in its picker, the old ones at `/<plugin>/v<old>/`, xVanish and xMarket live.
- **The site's jars are the released jars.** The build is reproducible: two clean builds of the Bukkit, Velocity and Fabric jars gave the same bytes. So the releases file is written before the tag, and `releaseAssemble` refuses to release a jar whose bytes differ from what the file records, naming each; the dry run on the release pull request checks the same. If CI's bytes ever differ from a local build's, `node scripts/release.ts --site-data <the run's release artifact>` writes the entries from CI's.
- **A real release refuses a set that isn't ready:** a changelog section still headed `(unreleased)`, or a `versions.json` line still `unreleased`, means the release pull request isn't merged, and the run stops before uploading. A dry run says so in its summary instead.
- **The full dry run runs in CI** on every pull request that touches the release code or the site's release data, and by hand (`tags: all`): every rewritten plugin's release set, built and checked against the live stores, each request printed in the summary. Locally, the same: `./gradlew -p core/platform-fabric collect`, then `./gradlew <each project>:releaseAssemble -Pxena.release.root=release -Pxena.release.dryRun=true` and `<each project>:releasePublish <each project>:releaseStorePage` with the same properties. On 2026-11-27 all seven merged rewrites (xUtilities 3.0.0, zChat 4.0.0, xMoney 2.0.0, xTeleport 2.0.0, xBans 2.0.0, xVanish 1.0.0, xMarket 1.0.0) passed every store's checks.
- **Store pages for rewritten plugins** go through `releaseStorePage` (the Store pages workflow finds the plugin's project on `xena.release`), which checks both stores' limits first; before, a change to a rewritten plugin's `modrinth.md` on main would have run a task that no longer exists.
- **SpigotMC and BuiltByBit** have no upload API: their update posts are still written to paste, and the site lists them only once `spigotMcId` and `builtByBitId` are set.
- **Left for later:** CurseForge's project ids and token (its payload is checked, but its game-version ids need the token), and the first real upload, which is the test the stores' own validation can't give before it.
