# xBackup 2.0: 1.x's repository byte for byte, a pause per platform, and each database copied by its own writer (2026-11-27)

M11 (#130): xBackup rewritten in place on the rewrite's core, as `xbackup/api`, `common`, `bukkit` and `fabric`, on Paper, Folia, Spigot and CraftBukkit 1.8.8+ and Fabric 1.20.1, 1.21.11 and 26.3. Laid out, migrated, documented and boot-tested as xBans 2.0 was ([xBans 2.0](2026-11-26-xbans-2.md)); the Java 1.x plugin is gone from the tree (the `maintenance` branch keeps 1.x). 1.x's design ([decisions/2026-11-18-xbackup.md](2026-11-18-xbackup.md)) holds: what follows is what 2.0 decided on top of it.

- **1.x's repository, byte for byte, both ways.** Packs (the `XBPK` footer and `XBPF` trailer), the deflated index, snapshots as key=value text, `config`, `keep/` and the note files, region files chunk by chunk (`RegionLayout`), FastCDC with 1.x's SplitMix64 gear table and masks: written in common Kotlin from 1.x's code and its tests. `CompatTest` downloads the 1.0.1 jar (pinned by SHA-256) and proves it: 1.0.1's command line verifies and restores a repository 2.0 wrote, and 2.0 reads and restores one 1.0.1 wrote. The only addition is a snapshot's `external` lines (data the backup can't hold), which 1.x reads past as it does any key it doesn't know. The restore journal (`restore/pending`) is 1.x's too, so a restore 1.x staged is put in place by 2.0.
- **The formats are common, the disk is the JVM's.** commonMain holds the formats, the chunker, retention, globs, restore paths and the secrets file's text, tested on the JVM and on Wasm; the repository on disk, the scanner, restores, remotes and the engine are jvmMain, which every platform xBackup runs on has. No Wasm platform needs a backup engine yet, and pretending one could have a file system it lacks would add an abstraction with one implementation.
- **The pause, per platform** (`Backup.Pause`; autosave always back on from `finally`, a watchdog at `performance.max-pause`, and on disable):
  - **Paper:** `World#setAutoSave(false)`, the players saved, `World#save(true)` (by reflection, since 1.8.8's API has none), which writes every changed chunk before it returns: 1.x's way.
  - **Folia:** the same, with `save(true)` once per region on that region's thread, in parallel: 1.x's way.
  - **Spigot, CraftBukkit and Paper before `save(true)`:** `World#save()`, which only queues chunks for the server's writer thread, then a wait off the server's threads until the region files stop changing (`Pauses.awaitQuiet`: two looks 250 ms apart see the same sizes and times, at most 20 s). Waiting costs nothing on the server's thread; a chunk still moving as it's read is read again by the strict pass, so the wait only saves re-reads. Measured on Spigot 1.8.8: an 11 ms pause.
  - **Fabric:** each level's `noSave`, as `/save-off` does, then `MinecraftServer.saveAllChunks(suppressLog, flush = true, force = true)`, as `/save-all flush` does, which writes every changed chunk, entities and `level.dat` and waits for the region writers, on every line from 1.20.1. `force` writes even with `noSave` on. A chunk the server unloads meanwhile can still be written on Fabric; the strict pass handles it as it does on Spigot.
- **The family's databases are copied by their own writers**, through the core's backup seam ([decisions/2026-11-27-the-familys-backup-seam.md](2026-11-27-the-familys-backup-seam.md), #200): each Xena plugin's `JdbcDatabase` puts its SQLite file on the family board, and for each backup xBackup asks for a copy, which the database's own writer makes between two writes (VACUUM INTO, else the online backup API, else a locked copy with the log folded in). Not chosen: xBackup copying those files itself through SQLite, as 1.x did for every database, which works but races the plugin's own writer for the file and can take a moment where a payment is half written across two tables. `Databases.Family` copies a file once however many plugins share it (`plugins/Xena/xena.db`), and falls back to SQLite's own copy for databases no Xena plugin has open; on Fabric, which has no driver, SQLite's is downloaded the first time a backup needs it. A database that can't be copied either way is left out of that backup with a warning, never stored as raw bytes. **MySQL and MariaDB are outside the server**: xBackup doesn't dump them (it would need the plugins' credentials, and a dump of a live database is the database tools' job), but each backup records which a Xena plugin uses (`external`), and `/backup status` shows them as not in the backups, so nobody mistakes a backup for a copy of them. `FamilyTest` opens xMoney's and xBans' real tables through `JdbcDatabase`, backs up while xMoney writes a payment every few milliseconds, and restores whole copies; the boot checks (`--family`) do the same with the real plugins on Paper and Fabric.
- **1.x's config paths are 2.0's.** Config version 2; `migrate(1)` moves 1.x's edited messages to `lang/en.yml` (`messages.error.*` to the core's `core.command.*`, `messages.broadcast-start` and `-done` to `broadcast.start` and `.done`, whose switches, `broadcasts.start` and `.done`, are turned on where 1.x had text), the theme into `messages.theme` (dropping 1.x's defaults, so they become `shared`), and `update-checker.enabled` into `updates.check`. **Passwords leave a 1.x config line by line**: moving them to `secrets.yml` by rewriting the file through the config schema would fill in 2.0's defaults before the migration ran, hiding the owner's 1.x values (the first test caught it: `update-checker.enabled: false` came through as `true`); so the lines holding them are removed from the text, checked by reading both files back, and the copy aside (`config.yml.bak-v1`) holds no password either. 1.0.1 put back reads `secrets.yml` too.
- **The command line runs on Java 8** in the Bukkit jar (`java -jar xBackup.jar list|restore|verify`), for a Fabric server's `config/xbackup/` too: a Java shim (`XBackupCli`) puts the Kotlin stdlib on a class loader of its own from the family's library cache, as the core's loader does for the plugin. That needed a core fix: R8 had repackaged the loader's classes into the plugin's package, so the loader's child-first class loader took the whole package as its own and loaded `PluginEntry` twice, which broke the isolated fallback of every shrunk plugin on a server too (#220, the loader keeps its names).
- **Startup does nothing with the repository.** As the plugin enables: `config.yml`, the commands, and the schedule armed from `last-backup` in `state.properties`; the eight languages in `lang/` and the player cache are read on an async task right after and used on the global thread, as xBans does (English until then, a few hundred ms); the repository is opened the first time a command or backup needs it, on xBackup's worker thread. A restore staged for the next start is put in place in `onLoad` (Fabric: the mod's initializer), before any world loads, holding `running.lock` from then until the process exits, as 1.x's bootstrap did.
- **API:** `XBackup.api()` (and Bukkit's services manager), the same on every platform: plugins named by name, paths as strings relative to the server folder, times in milliseconds. `backupNow` returns a `Pending`; `BackupStartEvent` is cancellable, `BackupFinishedEvent` and `BackupFailedEvent` follow, and on Bukkit each is also a Bukkit event (`co.xenastudios.xbackup.api.bukkit`; the start event on the main thread, the others async). Sources, quiet moments and storage backends a plugin registers go when it's disabled.
- **Tests can't hang:** every test task has a timeout (10 minutes on the JVM, 5 on Wasm). The command test runs on the proxy platform's real scheduler, waiting on what it awaits with a deadline; 1.x's crash, kill, swap, restore-safety, mirror, HTTP, cloud-drive, secrets, libraries, FTP-trust, command-line and throttle tests are ported, and `RemoteTest` runs against real servers in Docker with `XB_REMOTES`, as in 1.x. Porting them found one bug: a read or upload limit past about 9 GB/s overflowed the throttle's refill.
- **Startup and memory.** The first CI run failed the `budgets` job: startup 226.1 ms against 150 on Paper 26.3 (the other plugins' were 79–111 ms in the same job). A profile of the enable (async-profiler, the server thread) put about two thirds of it in reading `lang/`: the jar's eight translations and the eight files on disk, each a YAML parse with a parser not yet compiled, which the enable did itself through `JvmFiles.load()`. xBans reads only `config.yml` there. So does xBackup now, with the jar's translations read with the files on the async task. On Paper 26.3 on an M1 Pro (`scripts/budgets/check.sh`, median of 5, back to back, with other agents' builds running): **187.6 ms before (onEnable 163.4), 38.9 and 52.9 ms after** in two runs (onEnable 26.9 and 31.2); heap 1.6 MB, idle 0 ms a tick and 0 ms a second off the server thread, **metaspace 1.31 MB** of 1.5 (413 classes). The startup list was recorded again. Without the list, on Paper 1.21.11: 276 ms (before this change). CI measures both on its runners.
- **Size: the jars are over the 500 KiB target, and stay so.** Shrunk: Bukkit 856 KiB, Fabric 765-779 (its core relocated). Of the Bukkit jar's 781 KiB of compressed entries, 347 KiB is the shared core it reaches; 405 KiB is xBackup's own: 1.x's formats and chunker, the backup's two passes and region files, the restore and its journal, seven remotes (SigV4, WebDAV, OAuth for three drives, an HTTP/1.1 client of its own since Java 8 has none with WebDAV's methods, and the isolated SFTP and FTP loaders), the command line, the API and its Bukkit events, three pauses; 24 KiB the seven translations, 8.5 KiB bStats. JSch, Commons Net and SQLite's driver aren't in it: they're fetched when needed, pinned by SHA-256. 1.x's jar was 483 KiB with no Spigot, Fabric, translations or family seam; cutting 2.0 to that would cut features.
- **Booted** (locally): Paper 1.21.11 (alone, with xMoney and xBans, and with real SFTP and FTP remotes in Docker through the shipped jar's isolated loader), Folia 26.3, Spigot 1.8.8 on Java 8 (also with `-Dxena.libraries.loader=isolated`), Fabric 1.20.1, 1.21.11 and 26.3 (and 1.21.11 with xMoney and xBans). Real clients on Paper 1.21.11, Spigot 1.8.8, Fabric 1.21.11 and 1.20.1: a backup, a restore planned, staged and called off in German, completion, and a player without the permission refused.
- **Release:** `xbackup/bukkit` applies `xena.release` for the Bukkit and Fabric jars, Modrinth `xbackup`, Hangar `xBackup`, voxel.shop 10717, bStats 35420 (1.x's); version 2.0.0, unreleased, its pages at `/xbackup/next/` and 1.0.1's at `/xbackup/v1/` (`versions.json`'s `unreleased`), `modrinth.md` unchanged.
- **Not done:** native review of the seven drafts; dumping MySQL; a restore that puts plugin jars back on the same start (the server loads jars before any plugin runs, as in 1.x); the Fabric command line in the Fabric jar (the Bukkit jar's serves both).
