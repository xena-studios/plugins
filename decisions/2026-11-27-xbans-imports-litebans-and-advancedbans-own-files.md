# xBans imports LiteBans' H2 and AdvancedBan's HSQLDB files, with the driver each file needs, fetched for the import (2026-11-27)

xBans 2.0 imported LiteBans and AdvancedBan from MySQL or MariaDB only, "as servers have no H2 or HSQLDB driver" ([xBans 2.0](2026-11-26-xbans-2.md)). But both plugins' defaults are local files, LiteBans' H2 database (`plugins/LiteBans/litebans.mv.db`) and AdvancedBan's HSQLDB files (`plugins/AdvancedBan/data/storage.*`), so most servers switching couldn't import without first moving their old plugin to MySQL. `/xbans import litebans` and `/xbans import advancedban` now read those files, on every platform whose xBans offers them (Bukkit, Paper, Folia, Spigot; and Velocity and BungeeCord, for the files of a LiteBans or AdvancedBan on the proxy). Part of #127.

- **The driver is fetched when such an import runs, never shipped and never loaded at startup.** Through the core's existing on-demand libraries ([the core's library loader](2026-11-24-the-cores-library-loader.md)): pinned at build time with their SHA-256 in `gradle/library-pins.txt`, listed in the jar's `META-INF/xena/on-demand-libraries.txt`, downloaded into the family's cache (`plugins/Xena/libraries/`) the first time and checked against the pin each time. Offline, the loader's own message names the jar and the path (`Or put h2-2.1.214.jar from Maven Central at plugins/Xena/libraries/com/h2database/h2/2.1.214/h2-2.1.214.jar`), shown in `imports.no-driver`; put there, it's used without a download (`LocalImportTest.offlineSaysWhichJarToPutWhereAndThenWorks`).
- **One H2 per file format, picked from the file's header.** H2's MVStore files say their format in the first line (`H:2,...,format:1,...`), and each H2 reads only its own: checked with files written by 1.4.199, 1.4.200, 2.0.206, 2.1.214, 2.2.224, 2.3.232 and 2.4.240 against each driver, every other pairing fails ("File corrupted" or "Unsupported database file version"). So three are pinned: `format:1` (H2 1.4.x, and 1.4's older `litebans.h2.db` page store) is read with **H2 1.4.200**, `format:2` (2.0.202–2.1.214) with **H2 2.1.214**, `format:3` (2.2.220 and later) with **H2 2.4.240**, which is Java 11 class files: on Java 8 such a file is refused before anything is downloaded, saying so (a format-3 file was written on Java 11 or newer, so it's rare). Trying 2.x then 1.4 would have downloaded and loaded drivers that can't read the file; the header costs one 4 KiB read. AdvancedBan ships HSQLDB 2.4.0 (2.2.0 to 2.3.0, its pom), whose files any later 2.x reads: **HSQLDB 2.5.2**, the newest whose jar runs on Java 8 (2.6 and later are Java 11 class files, with Java 8 only as a `jdk8` classifier, which the loader's pins don't carry). Which LiteBans shipped which H2 isn't public; the header makes it not matter: every LiteBans on H2 (from 2.1, which moved it from SQLite to H2) is covered, as is every AdvancedBan 2.x.

  Renovate leaves them alone (`renovate.json`): a bump of the 1.4 or 2.1 pin would stop reading the files it's there for.
- **Three versions of one library, so `onDemand` resolves each on its own.** `xena.fetched-libraries` resolved every on-demand library in one configuration, where Gradle settles on the newest H2. Each `onDemand` dependency now gets a configuration of its own (they're all `isTransitive = false`, one jar each), so the pins and the jar's list carry all three; `OnDemandLibraries.find(group, artifact, version)` picks the one asked for, and `OnDemandDriverFetcher` asks for `DriverLibrary`'s version first (the SQLite and MySQL drivers, pinned once, are found as before).
- **In a class loader of its own, and let go after.** `IsolatedDriver` (core-jvm) loads the jar under the platform class loader (`java.sql`, none of the server's classes, so a plugin's shaded H2 is never the one used) and, on close, takes the driver out of `DriverManager` and closes the loader. H2 and HSQLDB register themselves in `DriverManager` as they load, which would hold the loader until the server stops, and `DriverManager` only lets code that sees a driver's class deregister it. So `DriverRelease`, plain Java in core-loader, is defined again from its own bytes inside the driver's loader and run there (R8 keeps it whole, `xena/r8/common.pro`). `LocalImportTest.eachDriverIsLetGoAfterwards` checks the loader is collected for H2 and HSQLDB, and fails without the release. H2 is opened with `DB_CLOSE_ON_EXIT=FALSE` (no shutdown hook holding it), HSQLDB with `shutdown=true`.
- **The source's files are never opened by a driver: a copy is.** Each file is copied while a shared lock on it is held, the copy is read and then deleted, so LiteBans' and AdvancedBan's files are byte for byte as they were (the tests hash them) and nothing is added beside them. Not chosen: H2's and HSQLDB's read-only modes on the files themselves. They still take locks, a 1.4 file may want recovery a read-only open can't do, and a read-only open of a file the plugin has open still races its writes; a copy taken under a lock doesn't.
- **A plugin still running is said, not read around.** Asked first: whether the server lists the plugin as on (`/xbans debug`'s `Plugins` line, already handed to xBans; nothing new at startup). Then the file: H2 holds a lock on its file while it's open, so a shared lock that can't be had (`tryLock` returns nothing, or `OverlappingFileLockException` when it's this server's own LiteBans) means it's in use; AdvancedBan turns HSQLDB's lock file off, so a fresh `storage.lck` counts only for another program. Either way, `imports.in-use` says which plugin and file, and to take its jar out (keeping its folder) and restart. A plugin installed but stopped, its folder left, is the case that imports.
- **Shared with the MySQL path, not copied.** `FileImports.Tables` is what each source's `readFrom` reads, by table name; MySQL's is the core's `Database`, the local files' a JDBC connection whose rows go through the core's own row reading (`ResultSet.rows()`, the sessions' `JdbcSession.read`). So bans, temporary bans, IP bans, mutes, warnings, kicks, history, in force or ended, staff, reasons, scopes and timestamps map the same from both. Tables are found by name in the `PUBLIC` schema whatever their case (H2 and HSQLDB upper-case unquoted names) and quoted exactly.
- **LiteBans' H2 login:** `sql.username` and `sql.password` from its `config.yml`, then H2's defaults (`sa`, and an empty user), each tried on a refused login (SQLSTATE 28…). AdvancedBan opens its file as `SA` with no password, as xBans does.
- **HSQLDB's settings that are the JVM's.** `hsqldb.reconfig_logging=false` (otherwise HSQLDB resets the JVM's logging, the server's), and `hsqldb.method_class_names=java.lang.Math` for the import only, put back after: HSQLDB before 2.7.1 lets a database's SQL call any static Java method, and 2.5.2 is what runs on Java 8; this is 2.7.1's default. HSQLDB's INFO lines as it opens and closes the copy (logger `hsqldb`) are kept out of the console.
- **Messages:** `imports.reading` (which file, with which driver), `imports.in-use` and `imports.no-driver`, in `lang/en.yml`'s English and the seven machine-drafted translations (still marked `machine-drafted`). They're 2.0's own, not 1.x's, so the 1.x migration doesn't carry them (`Legacy.MOVED`).
- **Tested** with real fixtures written by the drivers those plugins ship, generated in the test (`LocalImportTest`, the drivers handed over by path, each in a loader of its own): LiteBans' tables (its MySQL schema in H2's types) in each H2 format and in 1.4's page store, AdvancedBan's tables made with AdvancedBan's own HSQLDB statements and URL by HSQLDB 2.4.0; through the command twice (the second adds nothing); a file in use (its H2 held open in the same JVM, a running plugin, a fresh HSQLDB lock file); offline; the drivers let go. **Booted** on Paper 1.21.11 and Spigot 1.8.8 (Java 8): `xbans/bukkit/import-checks.txt` imports a seeded LiteBans H2 file (written by H2 1.4.199) and AdvancedBan's HSQLDB files (written by 2.4.0) through `/xbans import`, each twice, the drivers downloaded from Maven Central. `boot.sh` seeds `import-seed/` and runs these after `boot-checks.txt`, so every Bukkit-family cell of the Boot workflow runs them (Spigot 1.8.8 on Java 8 among them) without a workflow change; `./gradlew :xbans:common:jvmTest -PupdateBootSeed` writes the seed again.
- **Size and startup.** Nothing new runs or loads at startup: what reads the files (`LocalFiles`, `IsolatedDriver`, `DriverRelease`, `ImportContext`) loads with the first such import. What startup's classes gained is four `DriverLibrary` entries, three message keys and `Drivers.fetcher`'s getter. On Paper 26.3 on an M1 Pro (`scripts/budgets/check.sh`, median of 3, with the recorded startup list), xBans' loader holds the same 456 classes before and after, in 1.486 MB of metaspace on main and 1.477 MB here, within one run's noise; the startup list is unchanged. The jars grow by about 16 KiB each, shrunk, which is the code that reads the files (`LocalFiles` 8 KiB, `IsolatedDriver` 2.4 KiB), against 2.3 to 2.7 MiB for any one driver had it been shaded: Bukkit 815.5 to 831.8 KiB (of 880), Velocity 743.8 to 759.9 (of 810), BungeeCord 734.1 to 750.1 (of 800), Fabric 720 to 734 (its xBans offers `vanilla` only, but shares the common code). Also booted on Spigot 1.8.8 on Java 8 with the same checks.
- **Not covered:** H2 files from before 1.4 (H2 1.3's `.h2.db`, older than any LiteBans on H2 that we know of), LiteBans on PostgreSQL or SQLite, wildcard IP bans (as before), and a format-3 H2 file on Java 8 (it says to import on Java 11 or newer). Not booted: the import on Velocity or BungeeCord (the same code, unit-tested; their plugin lists name LiteBans in lower case on Velocity, which the check ignores). A real LiteBans or AdvancedBan jar wasn't run here: LiteBans is paid and closed, so its schema is the one its MySQL tables have, in H2's types, and the boot test imports files those plugins' drivers wrote, not files those plugins wrote.
