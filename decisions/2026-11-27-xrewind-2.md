# xRewind 2.0: 1.x's history on every platform, logged through the world hooks, and rollbacks a restart doesn't lose (2026-11-27)

M12 (#131): xRewind rewritten in place on the rewrite's core, as `xrewind/api`, `common`, `bukkit` and `fabric`, on Paper, Folia, Spigot and CraftBukkit from 1.13, and Fabric 1.20.1, 1.21.11 and 26.3. Laid out, migrated, documented and boot-tested as xBans 2.0 was ([xBans 2.0](2026-11-26-xbans-2.md)); the Java 1.x plugin is gone from the tree (the `maintenance` branch keeps 1.x), and with it the sandbox consumer's check of 1.x's API. What was decided:

- **1.x's tables, byte for byte.** `user`, `world`, `state`, `item` and the five history tables keep 1.x's columns, types, indexes and schema version (1), made with 1.x's own statements (`store/Tables`, `{rowid}`, `{blob}` and `{table}` filled per dialect as the old core did); times are 1.x's seconds since 2026, items hashed with 1.x's FNV-1a so 2.0 finds what 1.x stored. 2.0 adds no table and no column, so either jar reads the other's database, and nothing is copied aside: there's nothing to convert. Its 1.x lookups are 1.x's SQL. Tested against a 1.1.1 database (`history-1.1.1.sql`) read, rolled back and written to, then read with 1.x's own lookup statement, the schema unchanged.
- **1.x's config paths are 2.0's.** Config version 2; `migrate(1)` moves the messages to `lang/en.yml` (an owner's edits carried, `messages.<x>` becoming `<x>`, `messages.error.*` the core's), the theme into `messages.theme`, `update-checker` into `updates`; `log`, `rollback`, `purge` and `storage` stay. The old file is copied aside as `config.yml.bak-v1`; going back is renaming it, on the upgrade page.
- **Logged through the core's world hooks** ([the world hooks](2026-11-27-the-world-hooks.md)), at MONITOR, each cause subscribed only while one of 1.x's switches wants it. 1.x's listeners map onto the causes: a player's changes are 1.x's `block-break`, `block-place`, `liquids` (buckets), `fire` (ignites) and `mobs` (trampling) by what changed; `EXPLOSION`, `FIRE`, `FLUID`, `PISTON`, `ENTITY` (less 1.x's everyday animals) and `DECAY` their own; containers, hoppers and kills the hooks' own. Sources are 1.x's names: `#tnt`, `#creeper`, `#water`, `#piston`, `#fire`, `#decay`, `#hopper`, a bed's `#bed`. Joins and quits, signs, commands and clicks are the adapters' (Bukkit's events, Fabric API's), chat the core's chat bridge. Fabric has no event for a sign or a command before it runs, so those two are Bukkit's, said in the config and on the overview.
- **The writer is 1.x's, on the core's database layer.** Records queue without blocking (a lock and an array slot), and one writer turns them into rows with its dictionaries and hands up to 10,000 at a time to the core's database writer as one write, every half second or once 2,000 wait. One batch is in flight at a time, so the dictionaries are only ever touched by whoever holds it; a new name's row goes in the same write as its first use and stays pending until that commits. A batch the database refuses is tried record by record and only the record at fault dropped; a database that's down is the core's to wait for. 1.x's limits stand (warn at 100,000 waiting, drop past a million), and `flush` waits for what was queued before it, as 1.x's did.
- **A rollback a restart stops carries on.** As a command's rollback or restore starts, its parameters, centre and the time it reaches up to are written to `rollback-running.txt`; each chunk's rows are marked rolled back as that chunk is done, not at the end as 1.x did. The next start reads the file, plans the same search again up to the same time (so what's logged since isn't touched), finds only what isn't marked, applies it, and deletes the file. A plugin's plan (whose region may be code) and an undo can't be planned again, so a restart reports those. A crash between a chunk's blocks and its marks' commit can put a container's items back twice; blocks are set to a state, so setting them again changes nothing.
- **Applying is 1.x's applier in common**: each block set once without physics (a container emptied first so nothing spills), what it was kept for undo, at most `rollback.ms-per-tick` of a tick; on a server with one main thread one task a tick works through the chunks with the next eight loading ahead, on Folia each chunk on its own region's thread, eight at a time, each with its own budget. The adapters only load chunks and set blocks.
- **Contents and items are each platform's own bytes.** On Paper, 1.x's formats exactly (`I` and Paper's items, `S` and a sign's sides as chat JSON, Paper's item bytes); on Spigot, Bukkit's object stream (`J`; an item's bytes then start `0xACED`, never Paper's gzip header) and a sign's front; on Fabric, the block entity's own saved data (`B`, gzipped NBT: a chest, a sign, a banner, anything) and the item's (`F`). A rollback leaves what this server can't read as it is and says how many, as 1.x did for unreadable states.
- **The xPlots seam is the API's `Query.Builder.area` and `filter`**: a box SQL keeps to, and a predicate the planner asks of each block, so a plot of any shape is rolled back alone. Not chosen: a region type of xRewind's own, which xPlots would have to translate its regions into anyway.
- **1.x's `pause()` and `WriterHold` are gone**: the family's backup seam ([the family's backup seam](2026-11-27-the-familys-backup-seam.md)) copies every Xena plugin's database between two of its writer's batches, xRewind's included, with nothing for a backup plugin to hold.
- **CoreProtect's import is 1.x's**, `/xrewind import coreprotect [#again]` with 1.x's permission (`xrewind.admin`) and its `coreprotect-import` row in `meta`, not the core's resumable importer: the core's needs records it can write twice without a second copy, and a block log's rows have no key to tell. CoreProtect's SQLite file is opened read-only with the server's driver, or, where there's none, one fetched for the import (xBans' on-demand drivers, `IsolatedDriver`). Bukkit only: CoreProtect isn't on Fabric.
- **`/xrewind forget` deletes a player's chat, commands and sessions**, and keeps what they did to the world, as xBans keeps punishments: a rollback needs it, and a griefer could otherwise erase their tracks by asking. On the privacy page. No `/xrewind migrate`: 1.x had none (changing `storage` switches databases without copying), and a block log's tables, declared as raw 1.x statements, aren't the core's `Table`s its migration copies.
- **Commands are 1.x's.** One greedy argument takes the parameters, since Minecraft's Brigadier (which Fabric's commands are) takes no `:` or `#` in a word but the last; the core now completes a greedy argument's last word from what its type suggests (below), so `u:`, `a:`, `w:` and the rest still complete.
- **The core changed, a little, each tested:**
  - `BukkitWorldHooks`' `Keys.entityKey` finds `EntityType.getKey()` by name once: its cast to `Keyed` was dropped by R8, which shrinks against Paper's API (where `EntityType` is `Keyed`), so a shrunk jar called `getKey()` on Spigot 1.13.2 at its first falling block.
  - `CommandDispatcher.suggest` completes the words of a greedy argument from its type's suggestions (`aGreedyArgumentCompletesEachOfItsWords`); the core's own greedy `text` suggests nothing, so nothing else changes.
  - platform-fabric's Stonecutter constants `value_io` (1.21.6's `ValueInput`/`ValueOutput` for block entities) and `registry_lookup` (1.21.2's registries as their own lookup).
  - `core/platform-fabric/settings.gradle.kts`: the `xrewind` branch and its substitution; `scripts/budgets/bots/client.js`' `xrewind` scenario.
- **Boot matrix:** xRewind boots on every Bukkit cell from 1.13 (older ones skip it), Spigot 1.13.2 joins pull requests' cells as xRewind's floor, with a real client there and on Paper 1.21.11 (break, place, look up in German, roll back, undo, the inspector); Paper and Folia also blow a block of planks and a double chest up with TNT and roll it back, each half with its own items. Fabric's three lines run the same TNT loop through the mixins, with real clients on 1.20.1 (English, as Minecraft keeps no client language there) and 1.21.11.
- **Startup and memory.** On Paper 26.3 in a Linux container on two cores (`scripts/budgets/check.sh`, median of 5, on an M1 Pro other agents' boots were also using): startup 43 ms with the recorded startup list, metaspace 1.477 MB of the 1.5 MB a plugin gets, heap +2.7 MB, idle 0 on the server thread and 0.04 ms a second off it. The first build was at 1.621 MB with a list: what brought it down, each the lighter core's method ([a lighter core](2026-11-25-a-lighter-core.md)): rollbacks, lookups, the CoreProtect import, the writer's batches (`Batches`) and rows (`Rows`), what each change is logged as (`Changes`), Bukkit's blocks, contents and items (`BukkitBlocks`), the inspector's listeners (`Inspection`), the daily purge's work and the API's filters, each in a class of its own made the first time it's used and pinned in `bukkit/r8/xrewind.pro` so R8 doesn't inline it back. The world hooks themselves are about 30 of the classes loaded at startup, which xBans doesn't have.
- **Size: the jars are over the 500 KiB target, and stay so.** Shrunk: Bukkit 815 KiB (with its startup list), Fabric 686-701 KiB. About 420 KiB is the shared core xRewind reaches (its database layer, commands, config, messages, the family) and the world hooks' listeners; the rest xRewind's own with its API: the writer, 1.x's lookups across five tables, the planner and the chunked applier with its restart record, purges, the import, the inspector, the config migration, each platform's contents and items, the Bukkit events, and seven translations. 1.x's 327 KiB ran on Paper 1.21.11+ alone, on the old core. Cutting it would cut features 1.x has.
- **Not done:** native review of the seven drafts; Fabric's runtime budgets (not measured for any plugin yet); signs and commands on Fabric; trampling on Fabric (the hooks don't hear it yet); importing CoreProtect's items' enchantments and names (1.x didn't either); history moved between Bukkit and Fabric keeps its blocks only.
