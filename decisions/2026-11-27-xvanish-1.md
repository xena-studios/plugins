# xVanish 1.0: Bukkit's own hiding, memory for every check, a file for what lasts, and Fabric's gaps said plainly (2026-11-27)

M7 (#109): xVanish, a new plugin, built on the rewrite's core as `xvanish/api`, `common`, `bukkit` and `fabric`, on Paper, Folia, Spigot and CraftBukkit 1.8.8+ and Fabric 1.20.1, 1.21.11 and 26.3. Laid out, documented and boot-tested as xTeleport and xBans 2.0 were ([xBans 2.0](2026-11-26-xbans-2.md)). #109 predates the rewrite: where it says Paper 1.21.11 and Folia only, ROADMAP.md's floor (1.8.8) and platforms win. What was decided:

- **Hidden with the server's own `hidePlayer`, never packets or NMS, on Bukkit.** So `canSee` is false for every other plugin, a new Minecraft version needs no change, and the tab list, the world and the other plugins (zChat's mentions and `/msg`, xTeleport's `/tpa`, completions) agree without being told. 1.13 on with the plugin's own handle (`hidePlayer(plugin, player)`), so another plugin's hiding isn't undone; before, the old call. Every route has a test on the fake platform (`XVanishTest`), run twice: once with each viewer told one by one, once hidden by default first, as on Folia.
- **On Folia, hidden from everyone at once, then shown to staff.** A viewer's `hidePlayer` belongs on the viewer's thread, so a vanish told one viewer at a time would show the player to viewers on other regions for a tick, and a join to everyone until each viewer's thread ran. Folia (1.19.3's API on) makes the player hidden by default (`setVisibleByDefault(false)`) on their own thread, then each viewer who may see them is shown them on theirs: never shown for a moment to anyone who mayn't. On Paper and Spigot every viewer is on the main thread, so they're told at once, inside the join event, before the server sends anyone the joiner's tab list entry. Checked with real clients on Paper 1.21.11, Folia 1.21.11 and Spigot 1.8.8.
- **Who's vanished is in memory; every check answers from it.** `isVanished`, `canSee`, each listener's first question ("is anyone vanished?") and the placeholders read a concurrent map, on any thread. Levels and `xvanish.see` are worked out from permissions as a player joins, vanishes, and on reload, never per check.
- **What lasts is a file, not each player's own data.** #109 planned Paper's persistent data container; Spigot 1.8.8 and Fabric have none, and a file lists who's vanished while they're offline too (the import fills it, `forget` empties it). `vanished.txt`, a player a line, read once before anyone can join and written whole on the next async task after each change, through a temporary file renamed over it: a crash loses nothing, a join reads nothing. No database on a single server.
- **No repeating tasks; a listener only for a switch that's on.** State changes on a command, a join or a quit; the boss bar stays on screen by itself. Each switch is a module with its own listener class, registered only while its setting is on (`switchesThatAreOffListenToNothing`). With nobody vanished every listener returns at its first line.
- **Fake join and quit messages are ours, in lang/.** zChat's API has no join format to borrow, and Minecraft's own text can't be sent through the core's markup, so `fake.join` and `fake.quit` look like Minecraft's in each reader's language (German as Minecraft's German says it), and owners edit them to match their join format. They go to whoever can't see the player; the staff who can get `staff.vanished` instead.
- **Silent containers are a read-only copy.** Bukkit has no way to open a chest without its lid moving: a copy of its contents opens instead, clicks in it change nothing, and sneaking opens the real one. An ender chest opens the player's own, which makes no sound. Bukkit only.
- **`xvanish.join` is nobody's by default**, operators included: an operator default would vanish every operator at every join (found with a real client, whose operator joined vanished).
- **The family's seams:** the family's player cache marks who's vanished (`setVanished`, again once the cache has recorded the join, which may come after xVanish's), which xTeleport already reads; zChat asks Bukkit's `canSee`, and on Fabric, which has none, xVanish's hook through zChat's `registerHiddenPlayers`, by reflection on zChat's own classes as xBans' mutes reach it (each plugin relocates its own core). **xBans' staff layer:** the players xBans counts as staff (`xbans.staff`) see level-1 vanished players (`vanish.xbans-staff-see`); punishments are unchanged, as #109 says.
- **Events:** `VanishEvent` cancellable before, `VanishedEvent` and `UnvanishedEvent` after, fired only when something listens, on the player's thread; on Bukkit also Bukkit events (`co.xenastudios.xvanish.api.bukkit`), bridged with the first event, not at startup. `XVanish.api()`, also in Bukkit's services manager. ABI dumps in `xvanish/api/api/`.
- **Network mode** (`network.enabled`, `storage` on a shared MySQL or MariaDB, or the family's): one table, `{prefix}vanished`, kept whole in every server's memory, and the core's change feed (topic `vanish`) so a change on one server reaches the others within `check-every`. Its classes load only when it's on. Tested (#195) by `NetworkTest`, two plugins on one SQLite file through the feed with a database a test can take away, and by a network boot (`xvanish/bukkit/network.sh`, the Boot workflow's proxy cells): Velocity in front of two Paper 1.21.11 servers and BungeeCord in front of two Spigot 1.8.8 ones, on MariaDB, real clients: a player vanished on lobby is named by `/vanish list` on game, switches to game still hidden from a player there, and shows again. What the tests found, and so how it works:
  - **A row stays once a player has vanished**, `vanished` off when they show, with their `level` and the `server` they're on (its feed's id). Deleting the row on showing left another server's `vanished.txt` listing them, so their next join there vanished them again; and a server that was down when they showed couldn't tell its old file from a player the table never heard of. Now each server's file follows the table as it hears of changes (so a server that can't reach the database keeps everyone vanished as last known: fails safe), a server starting drops from its file whoever the table says showed, and adds to the table whoever its file lists that the table has never seen (network mode turned on, an import, an outage). `/xvanish forget` turns the row off rather than deleting it, so every server's file forgets them. The rows are staff, a few dozen: never pruned.
  - **A `remember: false` quit doesn't show a player who's switching servers.** It published "shown" at once, which reached the next server after the player had arrived there vanished, and showed them. Now the quit shows them here at once (a relog shows them, as `remember: false` says) and on the network only after 10 seconds, and only if the row still names this server: the next server writes itself in as they join, and a proxy connects them there before it lets go of the last.
  - **Staff see a player vanished on another server by level**, from the row's level, as they would on the same server; before, `canSee` was false for everyone, staff included.
  - **A change heard from the network isn't published back**, and a server's own writes in flight win over an older read of the table (a resync after an outage reading before its own write lands).
  - Writes made while the database is away are the core writer's to keep and try again; nothing more here.
  - "You joined vanished" is sent a second after the join, so it's in the client's language (a client's settings reach the server after it joins, a proxy's switch too; before 1.12 the server reads them only as it joins, so on 1.8.8 behind BungeeCord it's English).
- **Importers:** SuperVanish's and PremiumVanish's `data.yml` (`InvisiblePlayers:`, the one thing to carry), through the core's `Imports`, so `--dry-run` and the rest are the core's. Their `sv.*` and `pv.*` permissions are declared granting xVanish's with `vanish.other-plugins-permissions`. Checked (#195) against SuperVanish's own `plugin.yml` and `LayeredPermissionChecker` (PremiumVanish, closed source, documents the same names under `pv.` in its config, `LayeredSeeAndUsePermissions`; its full node list wasn't checked): `use`, `see`, `list`, `login`, `logout`, `toggleitems`, `others` and `joinvanished` are theirs; the levels were wrong (`pv.level.<n>`, which neither has): now `sv.use.level<n>` and `pv.use.level<n>` give that level, and `sv.see.level<n>` and `pv.see.level<n>` see up to it, with or without `sv.see`. A layered level alone doesn't give `/vanish`, as declared nodes can't take a number: `sv.use` or `xvanish.vanish` does.
- **Admin:** `/xvanish reload`, `debug`, `forget` (`vanished.txt` and the network's row) and `import`. No `migrate`: a single server has no database.
- **Fabric, without mixins.** The tab list entry is taken off each viewer's list (`ClientboundPlayerInfoRemovePacket`) and the entity off their world as Minecraft starts tracking it for them (Fabric API's `EntityTrackingEvents.START_TRACKING`). A player is decided on as their connection is made (`ServerPlayConnectionEvents.INIT`), so their join message (Fabric's game-message event) can be left out, and everything is sent once they're placed. Join, quit, death and advancement messages, invulnerability, chat, flight, night vision, the boss bar and (1.21.11 on) the locator bar work. Showing a player again takes them out of their world's tracking and puts them back (`ServerChunkCache.removeEntity`, `addEntity`), the one public way to pair them with viewers in range again; it resends the shown player's own chunks once. **Not on Fabric**, as there's no event for them: the server list, mob targeting, pickup, physical blocks, sculk, raids, silent containers, collisions, sleeping, spawning and hunger; and the joining player's tab list entry reaches other players a moment before it's taken off (the same tick: Minecraft broadcasts it before Fabric's join event). The switches say so; the docs list them. Booted on Fabric 1.20.1 and 26.3 from the console; no real client on Fabric yet.
- **Per version on Bukkit:** collisions and the boss bar from 1.9 (1.8.8 has neither, so no reminder there); raids 1.14; sculk 1.17; the locator bar 1.21.6; advancement messages and mob spawning Paper only (Spigot has no way); projectiles pass through where the hit can be cancelled (Paper, Spigot 1.20.4 on) and elsewhere only do no harm.
- **No bStats:** xVanish has no bStats service id yet, so bStats isn't in the jar and nothing is sent. Add the id and the library with the first release.
- **The core changed, not at all:** `core/platform-fabric/settings.gradle.kts` has the `xvanish` branch and its substitution, and `docs/src/plugins.ts` learnt a new plugin's first major (#191). No core class loads more.
- **Size: the Bukkit jar is 595 KiB, over the 500 KiB target, and stays so.** About 400 KiB is the shared core it reaches, the database layer among it for network mode (as xTeleport's); xVanish's own with its API about 100 KiB: the hiding and levels, a listener per switch, the Paper paths, the commands, network mode, the importers and the Bukkit events; the seven translations about 25 KiB. Leaving network mode out would bring it near the target and break #109's networks. **Fabric's jars are 528 to 536 KiB (#195), over the target too, for the same reason:** of about 475 KiB of compressed classes and files, about 390 KiB is the shared core (its database layer, `core.common.db` and `core.jvm`, about 95 KiB of it; commands, config, translations' machinery, text, the family's cache and the admin commands most of the rest; the Fabric platform layer about 33 KiB), xVanish's own about 74 KiB, the translations 13 KiB, and on 1.21.11 and 26.3 Fabric's permissions API nested (13 KiB); the jar's own entries and Loom's remapping add the rest. Nothing in it is unused: R8 has already taken out what xVanish doesn't reach, the core is relocated (each mod carries its own), and the one large piece xVanish could drop is the database layer, network mode. `gradle/jar-budgets.txt` has each size plus about a tenth.
- **Startup and memory.** On Paper 26.3 on an M1 Pro, beside other boots (`scripts/budgets/check.sh`, median of 5): with the recorded startup list (`bukkit/startup-classes.txt`), startup 51.2 ms as the first plugin (150 ms budget), heap 1.37 MB, idle 0 ms a tick, **metaspace 1.164 MB** of 1.5 MB (372 classes); without it 96.5 ms and 1.129 MB. CI's budgets job measures it on two cores.
- **Release:** `xvanish/bukkit` applies `xena.release` for the Bukkit and Fabric jars, Modrinth `xvanish`; no Hangar, voxel.shop or CurseForge project yet, so those stores are skipped. Version 1.0.0, unreleased, its pages at `/xvanish/next/` (`versions.json`'s empty `unreleased`). Its store page is drafted as `xvanish/modrinth.draft.md`, so the Store pages workflow (every `*/modrinth.md` changed on main) publishes nothing; it's renamed at the release, with its brand catalog entry (`pnpm new-plugin xvanish` in the brand repo, not made yet).
- **Not done:** native review of the seven drafts; a real client on Fabric; network mode on Fabric (it's the same common code, tested on the fake platform, but no Fabric network boot); Fabric's gaps above; PremiumVanish's editable silent chests (no API without NMS).
