# xVote 2.0: received anywhere, counted once in the ledger, paid on the player's server (2026-11-27)

M8 (#128): xVote rewritten in place on the rewrite's core, as `xvote/api`, `common` (Kotlin Multiplatform, no `java.*` in commonMain, built for wasmWasi too), `bukkit`, `fabric`, `velocity` and `bungee`. It runs on Paper, Folia, Spigot and CraftBukkit 1.8.8+, Fabric 1.20.1, 1.21.11 and 26.3, Velocity and BungeeCord. Laid out, documented and boot-tested as xBans 2.0 was ([xBans 2.0](2026-11-26-xbans-2.md)). Every 1.0.1 command, permission and setting keeps its meaning. What was decided:

- **Where a vote is received, deduplicated and paid.** It's received wherever a list sends it: the proxy's receiver, or a server's. It's deduplicated in the ledger, the `votes` table every receiver writes to: a repeat from the same site inside its window is dropped before it's stored. It's paid by the server the player is on, and only after that server claims the vote: `UPDATE votes SET claim = <server> WHERE id = ? AND claim IS NULL`. Whichever server's update changes the row pays; any other server racing it changes nothing and pays nothing. That covers a player switching servers mid-vote, two servers hearing the same news, and a restart halfway through. Each case has a test (`NetworkTest`).
- **The proxy never pays.** It stores the vote, counts it (`VoteCountedEvent`, once per vote on the whole network) and tells the player's server. It sends a fast `vote <id>` on the proxy layer's `xena:xvote` channel and publishes the vote on the change feed (topic `vote`). A server that missed both claims the vote as the player next joins it. Offline votes are rows with no claim, so a restart, a full proxy or a server that's down loses nothing.
- **A proxy needs the servers' database.** The proxy only stores votes, so its receiver is useful only on the servers' shared MySQL or MariaDB with `network.enabled`. On its own SQLite file it still listens, and `/xvoteproxy status` and the startup log say that no server pays those votes.
- **NuVotifier on the proxy, as it is.** NuVotifier's `proxy` forwarding (Votifier v2 to each server's receiver, with the token in xVote's `tokens.yml`) works unchanged. Its plugin-message forwarding works too: set `receiver.nuvotifier-channel` to NuVotifier's channel and the backend reads it (`NuVotifierListener`). A vote that came this way is `VoteSource.FORWARDED`.
- **1.x's schema, byte for byte.** It stays at schema 2, with the tables `votes`, `voters`, `held` and `state`, the same columns and the same meta table. 1.0.1 opens a database 2.0 has used, and that is the downgrade path. Fixtures from 1.0.1 (`votes-1.0.1.sql`, `config-1.0.1*.yml.txt`) are read back in `MigrationTest`. The config goes to version 2: messages move to `lang/`, `theme` moves into `messages.theme` and `update-checker` becomes `updates`. The old file is copied aside as `config.yml.bak-v1` first, and a message changed in 1.x is carried into `lang/en.yml`.
- **Rewards.** Money goes through xMoney 2.0's API when xMoney is installed, recorded as xVote's reward in `/eco history` (the family test boots both and pays 25). Otherwise Vault's economy is used, as in 1.x. Both are reached by reflection, so neither is needed at build time. Commands, items, sounds, messages and broadcasts work as in 1.x. Add-ons register reward types (`XVote.api().registerRewardType(owner, id, type)`). Items that don't fit are held for `/vote claim`, stored as 1.x stored them (Paper's `serializeAsBytes`, else Bukkit's object stream).
- **The xStats seam.** `VoteCountedEvent` fires once per vote, wherever it was counted, for a stats plugin to listen to. xStats 2.0 isn't written yet, so nothing listens to it today.
- **Events and the API.** `XVote.api()` works on every platform. `VoteReceivedEvent`, `VoteRewardEvent` (its rewards can be changed) and `VotePartyEvent` are cancellable and fire before. `VoteCountedEvent` and `VoteRewardedEvent` fire after. On Bukkit the same events are also Bukkit events (`co.xenastudios.xvote.api.bukkit`), bridged with the first listener rather than at startup. It's Java-friendly (`fun interface RewardType`, no suspend). ABI dumps are in `xvote/api/api/`.
- **Importers.** VotingPlugin's SQLite `Users` table (`AllTimeTotal`, `LastVotes`) and SuperbVote's `votes.json` (both its formats) bring in totals and last votes. NuVotifier's keys, tokens and port are taken over, with xVote's own kept aside. A second import of the same plugin needs `again`. Their files are only ever read.
- **Admin.** `/xvote reload`, `debug`, `import` and `forget <player>` (votes, totals, held items: an erasure request) are on every platform. On the proxies the command is `/xvoteproxy` (`/xvp`), so it doesn't take the servers' `/xvote`.
- **Fabric, through Minecraft's own commands.** Items go through `/give`, so what doesn't fit drops at the player's feet rather than being held. Sounds go through `execute … playsound`. Money goes through xMoney when it's installed; Fabric has no Vault. Fabric can't read the held items a Bukkit server on a shared database wrote, so they stay for a Bukkit server to hand out. Fabric has no end of the proxy layer yet, so behind a proxy a Fabric server learns of votes from the change feed and on join. There's no PlaceholderAPI, and no bStats (it has no Fabric platform).
- **Startup without the slow parts.** Enable reads the config, opens the database on an async task, reads every voter, then starts the receiver on its own threads. Everything else is deferred to first use: the ledger's writes, the reads, the receiver's conversations, the importers, the admin parts, payouts, PlaceholderAPI, the economies, and parsing reward items (about 50 ms on 1.8.8 when it ran in enable). Each deferred class is pinned with `-keep,allowobfuscation` in `bukkit/r8/xvote.pro` so R8 doesn't inline it back. Startup lists are recorded for Bukkit, Velocity and BungeeCord.
- **bStats 35422, 1.x's id, on Bukkit only.** The proxies have no xVote service ids. The update checker runs everywhere.
- **The core changed in tests only.** #194 taught `scripts/budgets/bots/client.js` to send real Votifier v1 and v2 votes (the `xvote` and `xvote-network` scenarios). `core/platform-fabric/settings.gradle.kts` has the `xvote` branch and its substitution. No core class loads more.
- **Size: the Bukkit jar is 787 KiB, over the 500 KiB target (and 1.x's 320 KiB), and stays so.** About 420 KiB is the shared core it reaches, the same parts as xBans': the database layer and change feed, the proxy layer's server end, commands, config, messages and the family. About 330 KiB is xVote's own code and its API: the Votifier v1 and v2 receiver with RSA, tokens and HMAC, the ledger, rewards, streaks, milestones, the party, reminders, the commands, the importers, the events, PlaceholderAPI, Vault and xMoney. The seven translations add 22 KiB and bStats 7 KiB. Velocity's jar is 691 KiB, BungeeCord's 683, Fabric's 675 to 690. Dropping network mode would break the reason 2.0 exists. `gradle/jar-budgets.txt` has each size plus 5 to 9%.
- **Startup and memory.** Measured on Paper 26.3 on an M1 Pro, beside other boots (`scripts/budgets/check.sh`, median of 3), with the recorded startup list: startup 44.2 ms (150 ms budget) and **metaspace 1.492 MB** of 1.5 MB, at the edge of the budget. It was 1.557 MB before the deferrals above. Velocity 3.4.0 alone: 29.9 ms median. BungeeCord alone: 75.0 ms. Both are within 150 ms. CI's budgets job measures them on two cores and is the final word.
- **Tested on real servers.** The boot checks ran on Paper 1.21.11 and 26.3 and on Spigot 1.8.8 (Java 8), each with a real client voting through the receiver's socket. They ran on Velocity 3.4.0, Velocity 4.3.1 and BungeeCord alone, and on Fabric 1.20.1, 1.21.11 and 26.3 from the console. The family test with xMoney paid 25. The network test sends a real vote to the proxy, for a player online on one server and for a player offline who then joins: on Velocity 4.3.1 with Paper 1.21.11, and on BungeeCord with Spigot 1.8.8, all on one MariaDB.
- **Release:** `xvote/bukkit` applies `xena.release` for the Bukkit, Velocity, BungeeCord and Fabric jars: Hangar `xVote`, voxel.shop 10713, Modrinth `xvote`. Version 2.0.0, unreleased, with its pages at `/xvote/next/` (`versions.json`'s `unreleased`, which keeps 1.0.1 as the release). The 1.x pages are at `/xvote/v1/`. `modrinth.md` is unchanged until the release.
- **Not done:**
  - No native speaker has reviewed the seven machine-drafted translations.
  - No real client has voted on Fabric, Folia or a proxy's backend after a server switch mid-vote; only the unit tests cover that.
  - Fabric has no fast path behind a proxy.
  - The VotingPlugin import covers its SQLite file, not its MySQL tables.
  - Proxy-side placeholders don't exist.
