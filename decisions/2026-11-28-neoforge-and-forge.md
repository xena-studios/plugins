# NeoForge 1.21.1 to 26.3 and Forge 1.20.1, server-side, and platform builds in each plugin's unreleased version (2026-11-28)

M16 (#134) starts with `core/platform-neoforge`: the core on NeoForge, server-side (players install nothing), built and booted the way `core/platform-fabric` is.

## Versions: NeoForge 1.21.1, 1.21.11 and 26.3

- **Lines, one jar each, through Stonecutter** (`core/platform-neoforge/settings.gradle.kts`): **1.21.1** (NeoForge 21.1.268), **1.21.11** (21.11.48) and **26.3** (26.3.0.118), the newest builds NeoForge publishes for each (maven.neoforged.net, 2026-11-28). A NeoForge jar runs on the Minecraft it was built for, as a Fabric one does: `neoforge.mods.toml` asks for that Minecraft exactly.
- **Not 1.20.4.** NeoForge 20.2 to 20.4 run with SRG names on a server, so a jar would have to be remapped per line; ModDevGradle, NeoForge's Gradle plugin, builds NeoForge 21.0 (1.21) and later only (its README), and its SRG remapping is for Forge 1.20.1 alone. 1.20.2 to 1.20.4 had a short life on NeoForge before 1.20.5's Mojang names; servers that stayed on 1.20 are on Forge 1.20.1, which M16 covers next. **1.21.1 is the floor**: NeoForge's long-lived line, where most NeoForge modpacks and their servers are.
- **1.21.11** as on Fabric, the last 1.21 line and the newest a real client (mineflayer) joins; **26.3** the newest. The lines between (1.21.2 to 1.21.10, 26.1, 26.2) get no jar, as on Fabric; a line is a version in settings.gradle.kts and its block in stonecutter.properties.toml.
- **Java** follows Minecraft: 21 for 1.21.x, 25 for 26.x.

## Kotlin through Kotlin for Forge

The stdlib comes from **Kotlin for Forge** (KFF), a dependency the mod declares (`kotlinforforge`, required), never shaded, as fabric-language-kotlin is on Fabric. Each line takes the newest KFF for its Minecraft that carries the rewrite's Kotlin, 2.4.21: **5.13.0** on 1.21.1 (1.20.6 to 1.21.8), **6.5.0** on 1.21.11 and 26.3. Its Maven artifact `kotlinforforge-neoforge` is only the libraries; the boots use the mod owners install, `kotlinforforge-<v>-all.jar` from Modrinth, checked against Modrinth's SHA-1. Mods use `javafml` with an ordinary `@Mod` class: nothing of KFF's own API, so nothing ties a mod to a KFF major.

## The platform

- **A build of its own**, `./gradlew -p core/platform-neoforge`, as platform-fabric's, for the same reasons (decisions/2026-11-24-platform-fabric.md): ModDevGradle sets up Minecraft for every line while the build is configured, and adds repositories. Its nodes are the adapter, `sandbox` (xSample) and `twin` (xTwin, for the family test); a plugin's `neoforge/` will be a branch of it, in the plugin's folder, as its `fabric/` is of platform-fabric.
- **`xena.neoforge-mod`**, the packaging every Xena mod gets, as `xena.fabric-mod`: the core bundled and relocated to `co.xenastudios.<id>.core` (NeoForge puts every mod in one module layer, where two jars may not share a package, so two Xena mods with the core under its own names couldn't even start together), R8 against Minecraft, NeoForge and the stdlib, then the jar as it ships: NeoForge runs Mojang's names, so nothing is remapped. R8 keeps the `@Mod` class and `@EventBusSubscriber` classes, which NeoForge finds by annotation.
- **The same members as FabricPlatform** (NeoForgePlatform: scheduler, events, commands, permissions, players, family, menus, chat, delivery, about, drivers, checkUpdates), so a plugin's NeoForge entry reads as its Fabric one. The tick scheduler is core-jvm's, which platform-fabric and platform-sponge use too. The vanilla parts (the text renderer, chest menus, Brigadier registration, player references) are platform-fabric's code with its package and names changed, Stonecutter comments included (the same constants, plus two for 1.21.1: `tag_parser_fully`, `fml_environment_methods`). A shared module for the vanilla code would need one Gradle build holding Loom and ModDevGradle together, or Stonecutter reading sources from outside its project; neither is worth it for about 700 lines that change when Minecraft does, in both copies at once.
- **A plugin starts at its mod's common setup, not in its constructor** (`NeoForgePlatform.whenSetUp`, `enqueueWork`): on the main thread, one mod at a time. NeoForge and Forge make every mod at once, on several threads, before Minecraft's own classes are set up, and advise mods not to touch them there: two mods setting up the same class at once can each wait for the other for good. A server with xBans and zChat hung that way once in seven starts (zChat stopped halfway through its start). By common setup Minecraft is bootstrapped, and the server's commands aren't built yet, so a plugin's commands come with them as before.
- **Events from NeoForge's game bus**, no mixins and no coremods: server starting, started, stopping and stopped, `ServerTickEvent.Pre` for the scheduler, players logging in and out, `LivingDeathEvent` (highest priority, before drops) for menus.
- **Commands on Brigadier through `RegisterCommandsEvent`**, with the core's `BrigadierTree`, as on Fabric; not Cloud's NeoForge module, which ROADMAP.md named: the core already is the bridge, and Cloud would add its jars to every mod for nothing a server sees.
- **Permissions through NeoForge's permission API** (LuckPerms answers through it). It knows only nodes registered as the server starts (`PermissionGatherEvent.Nodes`), so each declared node is registered then, with the plugin's own resolution (a parent the permission mod grants, then the declared default by operator level) as the node's default; a node declared by a later reload gets its declared default until the next start. The console and command blocks go by operator level.
- **Chat through `ServerChatEvent`**, which can cancel a message or give it a new text, but neither names recipients nor hands over the signed message. Unchanged: Minecraft's broadcast, signed. A new text everyone sees: the event's, which NeoForge sends as the signed message's unsigned content. Other recipients: cancelled, and sent by the bridge in Minecraft's chat type, unsigned. A rendering: system messages, as on Fabric. Our priorities run LOWEST first, NeoForge's HIGHEST first, so the order turns over.
- **The family's board in the JVM's system properties** (`xena:board`): NeoForge has nothing like Fabric Loader's object share, and makes mods on several threads at once, so the first mod's board is taken with `putIfAbsent`, which is atomic there. It's a map of JDK objects, never a string, so `System.getProperty` and the property listings, which read strings only, never see it.
- **The world hooks are platform-fabric's mixins** (`NeoForgePlatform.world`), copied with the package changed: NeoForge runs Mojang's names and Mixin, and every one of them is an injection at the head or return of a vanilla method NeoForge keeps, so they apply as they are; xSample's WorldCheck proves it on 1.21.1 and 26.3. NeoForge's own events (block breaks and places, explosions, pistons) were the other way, but they don't cover the same changes (hoppers, fluids, decay, spawn eggs) nor let a listener see a change after it's decided as the mixins do, and two implementations of one interface would drift. A mod lists its mixin config in its `neoforge.mods.toml` (`[[mixins]]`), and R8Shrink reads it there, as in `fabric.mod.json`. **Not on Forge 1.20.1**, which runs SRG names: a mixin there needs a refmap, which the relocation of each mod's core would break; its node has no world hooks, and xRewind, xLimits and xPlots aren't on it.

## Forge 1.20.1: a node of the same tree

ROADMAP.md drew `core/platform-forge` as a module of its own. It's a node of platform-neoforge's Stonecutter tree instead, **`1.20.1-forge`**, built from the same source: NeoForge forked from Forge 1.20.1, and what the core uses of either (the game bus and its server, tick, player, death, chat and command events, the permission API, `@Mod`, `ModList`, `FMLPaths`) kept its shape and changed its package. A module of its own would be a third copy of the same code.

- **Forge's names come from Stonecutter's string replacements** on that node only (`stonecutter.gradle.kts`): `net.neoforged.neoforge.` to `net.minecraftforge.`, `net.neoforged.fml.` to `net.minecraftforge.fml.`, `net.neoforged.bus.api.` to `net.minecraftforge.eventbus.api.`, `NeoForge.EVENT_BUS` to `MinecraftForge.EVENT_BUS`. The source stays NeoForge's; the Forge node is never the active one. The rest is the `forge` constant (`//? if forge`): the tick event (Forge's `TickEvent.ServerTickEvent` with its phase), the loader's name and Modrinth id, and Forge's item registry deprecation. Minecraft 1.20.1's own differences are platform-fabric's constants, which already switch 1.20.1.
- **Built with ModDevGradle's legacy plugin** (`net.neoforged.moddev.legacyforge`, Forge 47.4.29, Java 17), applied by the node's script instead of NeoForge's. Forge 1.20.1 runs SRG names, so `xena.neoforge-mod` remaps the shrunk jar (the legacy plugin's `reobfJar`, its input pointed at R8's output, as `xena.fabric-mod` points Loom's `remapJar`). The jar budget measures the shrunk jar, before the remap (5–10 KiB less).
- **A mod's resources have both descriptors**, `META-INF/neoforge.mods.toml` and Forge's `META-INF/mods.toml` (`mandatory = true` where NeoForge says `type = "required"`); the convention keeps the one for the jar's loader. A plugin's Forge jar comes from the same `<plugin>/neoforge/` folder, `<plugin>-forge-<version>+1.20.1.jar`.
- **Kotlin for Forge 4.13.0** (2026-11-19), the first 4.x with Kotlin 2.4.21, on its Maven and CurseForge; Modrinth's newest 4.x is 4.12.0 (Kotlin 2.2.21), which a mod built on 2.4.21 can't run on. The boots take 4.13.0's jar from its Maven, checked against its SHA-1.
- **Each player's language works on Forge 1.20.1**, unlike Fabric 1.20.1: Forge keeps the client's language (`ServerPlayer.getLanguage()`), which `NeoForgeLanguages` reads there. Two gaps of Forge's are covered: the options packet comes just after the login, so the family reads a joining player's language every quarter second for two seconds; and Forge doesn't copy its `language` field to the player a respawn makes (`restoreFrom`), so it's put back on `PlayerEvent.Clone`, by reflection on that one field, which is Forge's own and keeps its name on a server (only vanilla's members are SRG names there). A real client found both: German after a death came back English.
- **Forge deprecates vanilla's registries** (`BuiltInRegistries.ITEM` and the rest) for its own, which are the same objects. The Forge node compiles with deprecation warnings off (`-Xwarning-level=DEPRECATION:disabled`); the NeoForge lines check the same source with every warning an error.
- **Every plugin's branch gets the Forge node** (Stonecutter gives each branch every version), so a plugin's `neoforge/` build script picks its ModDevGradle plugin the way the adapter's does, and a plugin on NeoForge is on Forge 1.20.1 with it: xUtilities' Forge jar comes with this change (465 KiB, booted with a real client).
- **The library loader is unchanged:** Forge 1.20.1's securejarhandler (2.1.10) has the same public `setFallbackClassLoader`, and modlauncher 10 sets the boot layer as the fallback, as modlauncher 11 does.
- **Booted:** xSample, the family test with xTwin, and a real client (commands, chat through the bridge, completion, German then English) pass on Forge 1.20.1 locally; the Boot workflow runs that cell on every pull request that touches the platform.

## The downloaded libraries: the game's fallback class loader

The YAML parser (snakeyaml-engine-kmp, okio, urlencoder: 870 KiB) is downloaded into `config/xena/libraries/` and pinned, as on Fabric, not carried. NeoForge builds its game layer before any mod runs and has no way to add a jar to it, and the system class loader isn't on a mod's path (tried: a jar appended to it stays invisible on 1.21.1). But the game layer's class loader asks a **fallback loader** for a class no module has, and lets a mod set it: `setFallbackClassLoader`, public on securejarhandler's `ModuleClassLoader` (to 1.21.8) and on FML's own (1.21.9 on). So `NeoForgeLibraries` puts one loader of ours there, holding the jars: a class the game asks for comes from the jars, then from the fallback it replaced (modlauncher's boot layer to 1.21.8, FML's own loader after, which every line sets the same way); a class the jars' own code asks for goes to the game's loader first, which is how okio reaches the stdlib. Forge 1.20.1's loader is the same as NeoForge 1.21.1's (securejarhandler's), and the same code serves it. One loader serves every Xena mod: the first makes it under a lock in the system properties, the others add their missing jars to it through `Consumer<URL>`, a JDK interface their relocated cores share. Proven on 1.21.1 and 26.3 with a probe mod before the platform was written, then by xSample and xTwin starting together, on two threads, on every line.

Jar-in-jar was the other way: NeoForge loads one copy of each nested jar across mods, but every mod would carry the parser's 870 KiB.

## Boots

`scripts/boot-neoforge.sh`, the NeoForge side of `boot-fabric.sh`, with the same steps and checks files: NeoForge's installer's server at the line's build (cached in `.cache/neoforge/`), Kotlin for Forge from Modrinth, the mods; fails on any ERROR or FATAL line, or a warning from our mods. In the Boot workflow, `build-neoforge` builds and tests the whole build; the `neoforge` cells boot xSample on **1.21.1** (with a real vanilla client: commands, chat through the bridge, tab completion, a reply in German, then English) and on **26.3** (with the family test, xSample and xTwin), per pull request, and **1.21.11** (with a client) nightly. All three passed locally, the family test on each line. `scripts/affected.sh` boots NeoForge for `core/platform-neoforge/`, `scripts/boot-neoforge.sh`, `xena.neoforge-mod`, a plugin's `neoforge/` (or its shared code, when it has one), and what boots every platform. Runtime budgets aren't measured on NeoForge, as on Fabric; jar sizes are (`gradle/jar-budgets.txt`): xSample 356 KiB on every line, xTwin 280 KiB.

## Platform builds go into each plugin's current unreleased version

The lead's decision for M16: no rewrite has shipped yet (every plugin milestone is merged, unreleased, until the release milestone), so a plugin's new platform builds (NeoForge, Forge 1.20.1, Sponge) go into its current unreleased version, in the same CHANGELOG `## <version> (unreleased)` entry, rather than a separate minor. ROADMAP.md's "a platform added later is a minor" holds once a major has been released.
