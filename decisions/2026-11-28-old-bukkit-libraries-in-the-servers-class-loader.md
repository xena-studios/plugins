# On old Bukkit the libraries go into the server's class loader, and nothing is preloaded (2026-11-28)

Spigot 1.8.8 on Java 21 with several rewritten plugins (xBackup, xMoney and xBans, or the whole family) failed to start some of them on most boots:

```
[xBackup] xBackup couldn't start: java.lang.LinkageError: loader org.bukkit.plugin.java.PluginClassLoader @… attempted duplicate class definition for kotlin.text.Regex$Companion
[xBans] xBans couldn't start: java.lang.NoClassDefFoundError: Could not initialize class kotlin.text.Regex
```

**Why.** Bukkit before 1.16.5 shares classes between plugins. A plugin's class loader that can't find a class asks `JavaPluginLoader.getClassByName`, which calls every other plugin's `PluginClassLoader.findClass(name, false)`; that checks its map and, on a miss, defines the class from its own jar or anything added to it. It takes none of that loader's locks, so two threads that want the same class at once, at least one of them through another plugin's loader, both define it: the second gets the `LinkageError`, and a class whose static initializer failed that way is unusable for the whole server (`NoClassDefFoundError: Could not initialize class`). The loader added the libraries (the stdlib, okio, snakeyaml-engine-kmp, urlencoder) to the first plugin's class loader (decisions/2026-11-24-the-cores-library-loader.md: "the first plugin's stdlib is everyone's"), so every other plugin's Kotlin classes were defined there that way. The server enables plugins on one thread, which is why ordinary plugins never meet it. Ours load classes on others: `Startup.preload` on up to two threads per plugin (a Paper startup list or the stdlib's biggest classes), and each plugin's own async work as it enables (opening its database, fetching its JDBC driver). How often two of them meet depends on the machine and the JVM: CI's Java 8 cell on two cores passed, while ten cores and Java 21 failed three boots in four with xBackup in the set. #220, which kept the loader's class names, wasn't the cause: the race is in Bukkit's loader, and jars built just before it failed the same way (`duplicate class definition for kotlin.text.Regex$Companion`, once in 12 boots on two CPUs under load, against once in 5 for #220's).

**What changed**, in core-loader, for Bukkit before 1.16.5 only (`Startup.definesForOthers`: the plugin's class loader declares `findClass(String, boolean)`, as 1.8.8 to 1.16.4 do and 1.16.5's `loadClass0` doesn't):

- **The libraries go into the server's class loader,** the parent of every plugin's, which each plugin's loader asks first, through `loadClass` and its locks, so no plugin's loader defines a library class for another. On Java 8 that's `URLClassLoader.addURL`; on 9 and later the application class loader isn't a URLClassLoader, so it's `appendToClassPathForInstrumentation`, the method the JDK's own `Instrumentation.appendToSystemClassLoaderSearch` calls, through the trusted lookup (reflection with `--add-opens java.base/jdk.internal.loader=ALL-UNNAMED` after it). The next plugin sees the probe classes there and adds nothing. If the server's loader takes no jar, the libraries go into the plugin's own as before, with a warning (which fails a boot test, so CI would see it). `loader: isolated` still means a class loader of the plugin's own.
- **Nothing is preloaded there.** With the libraries in the server's loader, the preload threads would be safe for the libraries, but a plugin's jar can still hold a class another plugin's jar holds too (xMoney shades Vault's API beside Vault itself on these servers), and the old servers have no startup budget to keep.

Paper, Spigot 1.16.5 and later, Folia and the proxies take neither path: one `getDeclaredMethod` that throws `NoSuchMethodException` (a JDK class), no class of ours added at startup, each Bukkit jar about 0.7 KiB bigger (xSample 474.2 → 475.0 KiB).

Everyone on an old server now sees our libraries through the server's class loader, as they already did through the shared class map; a plugin with its own unrelocated Kotlin gets ours first, as it did once one of ours had loaded.

**Checked.** core-loader's tests: `StartupTest` (old Bukkit's loader told from 1.16.5's, nothing preloaded on it) and four in `LibrariesTest` (into the server's URLClassLoader, into a Java 9+ application loader through `appendToClassPathForInstrumentation`, the fallback and its warning, `isolated` unchanged). Boots of xSample beside every rewritten Bukkit plugin (xTwin, xUtilities, zChat, xMoney, xTeleport, xBans, xVanish, xMarket, xVote), none with a class defined twice: Spigot 1.8.8 on Java 8, 11, 17, 21 and 25 (twice each), 1.12.2 on Java 8 and 21 in a Linux container (twice each; on macOS arm64 its bundled SQLite driver has no native library) and on 11 and 17 on macOS (every plugin started; only the databases failed), 1.8.8 on Java 21 on two CPUs under load, twelve times. Paper 26.3 with five of them, unchanged. **Guard:** boot.yml's Spigot 1.8.8 cell runs the family test a second time on Java 21 (`newest-java`), with a real client joining.
