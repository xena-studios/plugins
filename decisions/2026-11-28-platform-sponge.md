# platform-sponge: one jar from API 8 to 21, its own command bridge, and everything inside the jar (2026-11-28)

The core on Sponge (M16, #134), in `core/platform-sponge`, with xSample built on it as a Sponge plugin (`core/core-testing/sample/sponge`) for boot tests, and `xena.sponge-plugin`, the convention every plugin's `sponge/` adapter is packaged with. A plugin's Sponge build goes into its current unreleased version, as the lead decided for every M16 platform ([2026-11-28-neoforge-and-forge.md](2026-11-28-neoforge-and-forge.md)). What wasn't obvious:

- **The versions, from what Sponge publishes** (repo.spongepowered.org, and its download API's `recommended` flag): the floor is **SpongeVanilla 1.16.5-8.2.0**, API 8, the last 1.16.5 release; the newest release is **1.21.10-17.0.0** (API 17, the newest `recommended` build); the newest build is **26.3-21.0.0-RC2827**, API 21, a release candidate for the Minecraft line Paper and Fabric boot as their newest. Pull requests boot the floor and 26.3; the nightly run all three. Sponge's 1.21.11 (API 18) and 26.1/26.2 (19, 20) builds are release candidates too and aren't booted: the jar is the same, and 17 and 21 sit either side of them.
- **Java:** the jar is Java 8 bytecode, as the core is, which every line runs. 1.16.5 runs on Java 8 to 17 (its Mixin can't read Java 21's class files, so it fails to start there); 1.21.10 needs 21 and 26.3 needs 25. CI boots each on the newest Java it starts on.
- **One jar for every API line, compiled against API 8.** SpongeAPI broke little between 8 and 21 in what a plugin of ours calls, but it did break: API 17 moved the player who left from `ServerSideConnectionEvent.Disconnect` to a new `Leave` event (`Disconnect` keeps only a profile, and fires for connections that never joined). So the convention checks each shrunk jar twice with the API floor check (`ApiFloor`, which now knows Sponge's packages): `checkApiFloor` against API 8, where R8 could reach for something newer, and `checkApiNewest` against API 17, the newest release, where a member a later API took away would fail on the server. A call made only after checking goes in `api-floor.txt` or `api-newest.txt` beside the build file: today that's `Disconnect.player()`, which platform-sponge calls only where there's no `Leave` (`SpongeQuits`, which finds `Leave` by name and calls its `player()` through a method handle). `checkApiNewest` found that one before a real client did.
- **Listeners are registered in code, by type token for a generic event.** Sponge reads an annotated listener's generic event type from the class file's local variable table (M0: R8 had to keep parameter names for it), and a listener for a generic event's bare class (`StartingEngineEvent` without `<Server>`) is refused. So platform-sponge registers every listener with `EventListenerRegistration` and a geantyref `TypeToken` where the event is generic (`RegisterCommandEvent<Command.Raw>`, `StartingEngineEvent<Server>`), which common.pro's type-token rules keep. No class of a plugin carries Sponge's annotations, and the main class is plain: Sponge finds it from `META-INF/sponge_plugins.json` and makes it with Guice, which needs only `@Inject` on its constructor.
- **The plugin metadata is the older layout** (`loader` and `license` at the top, everything else per plugin), which plugin-meta reads on API 8 (0.8) and 21 (0.9) alike; the newer `global` block isn't needed. It depends on `spongeapi` `[8.0.0,)`.
- **Commands are our own small bridge, as M0 said** (Cloud has no Sponge 8+ module): one `Command.Raw` per label of each root, which hands the whole line to the core's dispatcher and answers completions with its suggestions, so clients get our suggestions but no argument hints, as on Bukkit. Sponge takes commands in `RegisterCommandEvent`, as the server starts, and has no way to remove one, so a label stays registered for the server's life and the newest dispatcher decides what it does: a root a reload turned off answers as an unknown command and is hidden from players' trees (`canExecute`), and a root a reload turned on is registered through the command manager's registrar then, and players get their new tree. Sponge namespaces every command, so a label another plugin has stays theirs and ours is `/<plugin>:<label>`.
- **Everything is inside each plugin's jar.** Sponge has no library loader, no Kotlin language provider, and loads every plugin in one class loader (as one module layer on the newer lines, which refuses two jars with the same package). So the Kotlin stdlib, the YAML parser (snakeyaml-engine-kmp, okio, urlencoder) and the core are shaded into the jar and relocated to `co.xenastudios.<id>.libs` and `.core`, then shrunk by R8 into the package `<id>` against SpongeAPI alone. xSample's jar is 4,293 KiB shaded and 687 KiB shrunk, about 160 KiB more than its Bukkit jar, which downloads the stdlib and the parser. A plugin's shipped files are read from its own jar (`SpongePlatform.resource`), since a resource found by name through the shared class loader could be another plugin's. JDBC drivers are fetched on demand into `config/xena/libraries/`, as on Fabric.
- **What that costs:** each plugin has its own stdlib, so another plugin's API can't be called with Kotlin's own types across two Sponge jars (a `kotlin.uuid.Uuid` from one isn't the other's). The family's board was built for that already (JDK maps only), and the plugins that call another's API on Sponge take the JDK-typed entry points (`PlayerRefs.of(UUID)`); each plugin's Sponge milestone checks its integrations.
- **The scheduler is core-jvm's `TickScheduler`,** moved there from platform-fabric (it knew no Minecraft already), ticked by a Sponge task that runs every server tick from `StartingEngineEvent<Server>`. Before the server exists, the thread that constructs plugins owns global work, and scheduled work waits for the first tick. It closes after every plugin's own `StoppingEngineEvent` listeners (`Order.POST`), so their last saves run.
- **Permissions through Sponge's permission service,** with Bukkit's rules around it (core-common's `PermissionResolver`): the service's answer first (LuckPerms, or Sponge's own), then declared parents, then the default by operator. Sponge has no API for operators, so a player is one when the service grants vanilla's level-2 `minecraft.command.gamemode`, which is what an operator is to Sponge's own service; the console always is.
- **The family is `config/xena/`, and its board is on the other Xena plugins' main objects** ("The family"): Sponge has no registry for objects plugins share, so each plugin's main class extends `SpongeBootstrap`, a JDK `Supplier` handing out the board, found by its class name in each plugin's relocated core (`JvmFamilyBoard.fromShims`), as on the proxies. The player cache records joins and quits, and compares the online players' languages every 5 seconds (the client-settings event changed shape between API lines).
- **Not yet on Sponge:** the chat bridge (zChat's milestone brings it), chest menus (xMarket's), and the world hooks, which no plugin on Sponge uses (xRewind, xPlots and xLimits aren't planned for Sponge: ROADMAP.md, Platforms per plugin). bStats has a Sponge platform, but each plugin needs a Sponge service of its own on bstats.org, which only the owner can make, so Sponge reports nothing until then. Real clients (`client:` steps) aren't in `scripts/boot-sponge.sh` yet; a mineflayer client joined and left 1.16.5 and 1.21.10 by hand.
- **The boot script** (`scripts/boot-sponge.sh`) is boot-fabric.sh's shape: SpongeVanilla's universal jar from Sponge's repository, checked against its SHA-1, with Minecraft and the libraries it downloads cached in `.cache/sponge/`; plugins in `mods/`. 1.16.5 logs "Not a registry ops" from vanilla's parser for any flat world set in `server.properties`, so it boots the default world; the others a one-layer flat one.
