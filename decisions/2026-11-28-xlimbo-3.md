# xLimbo 3.0: 2.x kept whole on the new core, Paper only, and a limbo world on one server through xTeleport (2026-11-28)

M15 (#133): xLimbo rewritten in place on the rewrite's core, as `xlimbo/api`, `common` and `bukkit`, on Paper 1.21.11 and newer (and Purpur) only, as [xLimbo is Paper only](2026-10-22-xlimbo-is-paper-only.md) decided and ROADMAP.md's table says; a Velocity companion comes later, and `common` (no `java.*`, built for wasmWasi too) is what it will share. Laid out, migrated, documented and boot-tested as xRewind 2.0 was ([xRewind 2.0](2026-11-27-xrewind-2.md)); the Java 2.x plugin is gone from the tree (the `maintenance` branch keeps 2.x). What was decided:

- **Paper only, still, and Folia still not.** Folia can't create worlds and a limbo has nothing to spread across regions (2.x's reasons, unchanged); Spigot has none of the Paper API xLimbo is built on (placing a player before they're in the world, async chunks and teleports, Adventure, plugin chunk tickets). So there's no `plugin.yml`: only `paper-plugin.yml`, `load: STARTUP` (before the worlds, so a world in bukkit.yml can use the generator), `folia-supported: false`, and the release's `PAPER` platform. The whole `bukkit` module is compiled against Paper 1.21.11's API, its floor, and is **Java 21 class files** (1.21.11 needs Java 21; ROADMAP.md's "Paper-only code is Java 21"); the core shaded in stays Java 8. `checkApiFloor` finds one member past the floor, the core's guarded `Player.Spigot.getLocale()` for servers before 1.12.
- **2.x's world rules, byte for byte.** The `xlimbo.dat` marker with 2.x's floor shape (`minecraft:purple_stained_glass@64`), so 3.0 takes over a saved 2.x world as it is and 2.1.0 put back takes over 3.0's; only a marked, unloaded folder is ever deleted; a world xLimbo didn't make is used as it is, or refused; 1.x's unmarked world is adopted only on a carry from config version 1; both folder layouts (beside the main world before 26.1, inside it after). `WorldFolders` and its tests are 2.x's, kept as Java; the generator is Kotlin, made by name through the bootstrap's `getDefaultWorldGenerator`, which reads the floor from `config.yml` read-only, as 2.x's did, since the server can ask before the plugin's enabled.
- **2.x's config paths are 3.0's.** Config version 3; `migrate(1)` is 2.0's carry (1.x's `GLASS` floor and 4000-block spread, the build guard's 0), `migrate(2)` moves the messages to `lang/en.yml` (the owner's edits carried by `CarriedMessages`, each mapped in `Legacy.MOVED` with the texts 1.x, 2.0 and 2.0.1 shipped), the theme into `messages.theme` and `update-checker` into `updates`. Messages edited set `messages.language: en`. The old file is copied aside as `config.yml.bak-v2`. Tested on 1.0.1's file as it shipped and 2.1.0's (from the docs it generated) with an owner's edits (`MigrationTest`), and on a real Paper 1.21.11 server: 2.1.0 with a saved world and a block built in it and an edited welcome, then 3.0 (the block kept, the message in `lang/en.yml`), then 2.1.0 again without renaming anything (it reads 3.0's file as a newer one, keeps every setting, takes over the same world with the block), then with `config.yml.bak-v2` renamed back. Going back is on the upgrade page.
- **Every 2.x feature, command, permission and setting kept:** the void world and its rebuilds on reload, players placed before they're in the world, the spawn area kept loaded with plugin chunk tickets, hide-others, the join, quit, death and advancement messages, creative and flight (kept through game-mode changes), the action bar, `/join` with its aliases, configurable permission and cooldown, auto-join, server-check's Server List Ping (`JvmStatusPing`, off the server thread) with its paced queue and the three-tries-in-five-minutes limit kept across reloads, and the thirteen protections, each its own listener registered only while on. `xlimbo.admin` still grants the admin commands (2.x's reload and info; info is everyone's now, as every Xena plugin's).
- **The family: xTeleport sends players back, xVanish decides who's counted.** New `send-back.via` (`proxy`, 2.x's, the default; or `teleport`): with `teleport` the limbo is a world on a server players play on. `/xlimbo send`, the API's `sendToLimbo` and the `xlimbo` destination xLimbo registers with xTeleport (`registerDestination`) put a player there; every way back (`/join`, auto-join, `/xlimbo back`, the API) is a teleport to `send-back.destination` through xTeleport's API (`previous`, its spawn, `warp:<name>`, or another plugin's named destination), with `TeleportOptions.immediate()` and its safety check; without xTeleport, Paper's own teleport to where they were or the main world's spawn. Both APIs are reached by name through Bukkit's services manager and reflection on their own classes (`XTeleportBridge`, `XVanishBridge`), as xTeleport reaches xMoney: each plugin relocates its own core, so their `PlayerRef` and `Location` aren't xLimbo's, and the provider is a `java.lang.reflect.Proxy` of xTeleport's `DestinationProvider`. `paper-plugin.yml` names both with `load: OMIT`: xLimbo starts before the worlds and they after, so they're found on the first tick and on `PluginEnableEvent`. **A player sent in on a server they play on is put in adventure, not creative** (creative's items would come back with them), and gets their game mode and flight back as they leave; only players in limbo are hidden from each other or have their messages left out. **Vanished players** (xVanish's `isVanished` and `canSee` with its levels; without it the family's player cache and `xvanish.see`) aren't counted in `/xlimbo`, listed by `/xlimbo list` or counted in the queue's place and total for anyone who can't see them; the API's `playersInLimbo` and `queueSize` count everyone, `visibleCount` doesn't. Checked with real clients on Paper 1.21.11 beside xTeleport 2.0 and xVanish 1.0 (`family-checks.txt`): Friend sent to limbo in adventure, the vanished Joiner counted for Joiner and not for Friend, Friend's `/join` landing on xTeleport's spawn in survival again.
- **The API**, `XLimbo.api()` (also in the services manager), by `PlayerRef`: the main server's status, who's in limbo and in line, `sendBack`, `sendToLimbo` (`CompletableFuture<Boolean>`), the add-on hooks (holds keep players in limbo, asked before every way back; priorities reorder the line, stably), and five events, `PreEnterLimboEvent` and `PreReturnEvent` cancellable before, `EnteredLimboEvent`, `ReturnedEvent` and `MainServerStatusEvent` after, each fired only when something listens, on xLimbo's bus and as Bukkit events (`co.xenastudios.xlimbo.api.bukkit`, bridged with the first event). 2.1.0's Java API and its three Bukkit events are replaced; the developer page maps each. ABI dumps in `xlimbo/api/api/`; Maven Central's `xlimbo-api` and `xlimbo-api-bukkit` come from the shipped jar, as every API's.
- **Admin:** `/xlimbo reload`, `debug` and `forget` (what's kept in memory about a player: their tries at going back and their `/join` cooldown), plus `list`, `send` and `back` (`xlimbo.list`, `xlimbo.send`, `xlimbo.back`, operators'). No `import` (no other plugin's data to take) and no `migrate` (no database).
- **Messages** in `lang/en.yml`, and de, es, fr, pt-BR, ru, pl and zh-CN drafted by machine and marked as drafts on the messages page. The welcome is sent a second after the arrival, so it's in the client's language (as xVanish's joined message).
- **Tests can't hang:** the common tests run on the fake platform with virtual time; the status ping's on real local sockets with its 3-second timeouts; every test task has a 5-minute timeout.
- **Size: the jar is 568 KiB, over the 500 KiB target and 2.x's 185, and stays so.** About 400 KiB is the shared core xLimbo reaches (commands, config, messages and translations, the family's cache, the admin commands, the update checker); the rest is xLimbo's own with its API: the world and its generator, the return queue and status ping, the thirteen protections, the commands, the two family bridges and the five Bukkit events, plus the seven translations, bStats and the startup class list. There's nothing to drop that isn't a 2.x feature or the family's. `gradle/jar-budgets.txt`: 620.
- **Startup and memory.** On Paper 26.3 on an M1 Pro, beside other agents' boots (`scripts/budgets/check.sh`, median of 3): startup 77 to 141 ms as the first plugin across runs (150 ms budget; CI's 2-core budgets job is the word), metaspace 1.244 MB of 1.5 MB (402 classes) with the startup list, idle 0.0003 ms a tick. **The heap budget leaves the world aside, as M0's did** (sandbox/m0/budgets/RESULTS.md: "not counting chunks of worlds the plugin creates on purpose"): with its world and the 121 chunks it keeps loaded, the heap over a server without it is about 50 MB, all chunk holders and sections (its own instances are 21 KB). So the budgets job runs xLimbo with `--seed xlimbo/bukkit/budgets-seed`, a config naming a folder it didn't make, which it refuses: every module on and no world, 1.225 MB. `check.sh` learnt `--seed`, and to read a jar with only `paper-plugin.yml`, in their own pull request first.
- **Booted** locally: Paper 1.21.11 and 26.3 from the console (`boot-checks.txt`: the world and its floor, every command, a paused server's reload, debug); Paper 1.21.11 with real clients as a fallback (`client-checks.txt`: Joiner lands on the floor without a teleport, is welcomed and shown the hint in German, doesn't see Friend, `/join` and its cooldown) and as a world on the server with xTeleport and xVanish (`family-checks.txt`, above); the family test on 26.3 with every rewritten plugin. CI: xLimbo alone on every Paper cell from 1.21.11 (other cells skip it), the clients on the `client` cell, and the family test on Paper from 1.21.11.
- **Release:** `xlimbo/bukkit` applies `xena.release` for its one jar (`PAPER`, Minecraft from 1.21.11, Java 21), Modrinth `xlimbo`, Hangar `xLimbo`, voxel.shop 10709, bStats 34867 (2.x's); version 3.0.0, unreleased, its pages at `/xlimbo/next/` and 2.x's at `/xlimbo/v2/` (`versions.json`'s `unreleased`), `modrinth.md` unchanged.
- **Not done:** native review of the seven drafts; the Velocity companion (planned: ROADMAP.md); `previous` and the game mode given back survive a restart only as "spawn" and the server's default game mode (they're in memory, and a restart with players in limbo is rare); real clients on 26.3, which mineflayer can't join yet.
