# xLimbo starts as the first world loads, not as it's enabled (2026-11-28)

Part of M15 (#133). xLimbo 3.0's startup was 124 to 173 ms on CI's two-core budgets job, against the first plugin's 150 ms budget, nearly all of it in its onEnable.

- **The cause: `load: STARTUP` leaves the core's preloader no time.** The core's shim starts loading and verifying the jar's startup classes on a thread of its own at onLoad ([a lighter core](2026-11-25-a-lighter-core.md)); a plugin that loads after the worlds is enabled seconds later, with them all loaded. xLimbo has to be enabled before the worlds (a world in `bukkit.yml` can name its generator, and Paper only asks an enabled plugin), and Paper enables a STARTUP plugin straight after loading it: 10 ms later. A wall-clock profile on Paper 26.3 in a two-core Linux container (async-profiler started with the JVM, five boots) showed the 107 ms of onEnable as the classes loading on the server's thread, racing the preloader for the same ones (about 10 ms waiting on its class-loading locks, another 10 on the JIT's queue): the platform 34 ms, `config.yml` 25 ms (the YAML parser's classes), the modules' listeners 15 ms, the rest small. The translations were already read off the server thread.
- **Chosen: enable, then start on the first `WorldLoadEvent`.** onEnable only registers the plugin's own listener; the start that was onEnable (the platform, `config.yml`, the commands, the modules, the API) runs as the first of the server's worlds loads, by which time the preloader has done its work. That is still before any plugin that loads after the worlds is enabled, before the first tick and so before any player can join: nothing has to be queued, and add-ons enabled after the worlds find the API as before. The limbo world is still made on the first tick (`BukkitLimboServer.loadingWorlds`), once every world is loaded. Enabled once worlds exist (`/reload confirm`, a plugin manager), it starts at once. The generator was already answered by the Java bootstrap without the plugin started.
- **Measured** on Paper 26.3, two cores (`docker run --cpuset-cpus=0,1`, nothing else booting, medians of 5): startup (loader, onLoad and onEnable, what the budget counts) 127.8 → 20.4 ms. The deferred start logs its own time ("started in"): 35 to 58 ms, so the server's thread spends about 55 to 70 ms on xLimbo in all, against about 130 before. Metaspace unchanged (1.256 MB).
- **Not chosen:** reading the platform and config on an async task during the world load (Bukkit's command map and listeners aren't safe to touch from another thread while other plugins enable, and the classes are what cost, which the preloader already loads off the thread); starting the preloader earlier, from Paper's plugin loader (a core change, and the plugin's class loader doesn't exist yet there); dropping `load: STARTUP` (loses generators in `bukkit.yml`).
- **What changes for add-ons:** a plugin with `load: STARTUP` that depends on xLimbo finds its API from the first `WorldLoadEvent` on, not as it enables (developer-api.mdx says so).
