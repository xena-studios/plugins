# xStats 2.0: counted in memory, saved in batches, the network read from the shared database (2026-11-28)

M10 (#129): xStats rewritten in place on the rewrite's core, as `xstats/api`, `common` (Kotlin Multiplatform, no `java.*` in commonMain, built for wasmWasi too), `bukkit`, `fabric` and `velocity`. It runs on Paper, Folia, Spigot and CraftBukkit 1.13+, Fabric 1.20.1, 1.21.11 and 26.3, and Velocity 3.4+. It's laid out, documented and boot-tested as xVote 2.0 was ([xVote 2.0](2026-11-27-xvote-2.md)). Every 1.0.1 command, permission, setting, stat, board, placeholder and web API field keeps its meaning. Today's Java xStats is gone; its `web/` site is the same files, copied into every jar. What was decided:

- **The network's view on the proxy: the shared database and the change feed, not the proxy layer.** Each server already writes its players' rows to the network's MySQL under its own `server-name`, and publishes `saved` on the core's change feed after each save (and `player` on `/stats private` and forget). xStats on Velocity opens the same database read-only (`Engine(readOnly = true)`: it never writes a stat), reads every server's rows as one network, and reads them again when it hears `saved` (checked every `proxy.refresh-seconds` at most). `/networkstats`, `/networkleaderboard` and the website then answer from memory there. The proxy layer was the other way: each server would send its numbers to the proxy. It was turned down because a server without xStats, a server that's down, and a proxy restart would each leave holes, while the database already has everything, and a proxy restart only reads it again. The cost is a read of the network's rows after each save, which servers do anyway in network mode. On SQLite, which servers can't share, the proxy has nothing to read, and the console and `/xstatsproxy status` say so. The proxy's command is `/xstatsproxy` (`/xsp`), and its player commands are named apart from `/stats` and `/leaderboard`, so a player's own server still answers those. `NetworkTest` runs two servers and a proxy on one SQLite file. The network test boots them on MariaDB.
- **Counting is cheap: in memory, in batches.** Minecraft's own stats aren't listened for: they're read from the counters the server keeps, every `collecting.save-every-minutes`, on each player's own thread, `reads-per-tick` players a tick. Other plugins' changes (the API, the family's hooks) and joins go into an in-memory queue (`data/Inbox`) that merges each player's increments to one entry per stat. It's capped at a million entries, with a warning at 100,000. Each save applies the queue and writes what changed in one transaction on the database's own thread. Nothing is written per event. A player the database couldn't read keeps their events, in order, for the next save. Every engine change runs on that thread, so the engine needs no lock but the queue's.
- **1.x's schema, byte for byte, and the downgrade.** The tables (`players`, `stats`, `servers`, `totals`, `daily`, `monthly`, `boards`, `sources`, `meta`) are made with 1.x's own statements at schema 2. 2.0 adds no table and no column, and converts nothing. 1.0.1 opens a database 2.0 has used, and that is the downgrade path. `MigrationTest` loads a 1.0.1 database (`stats-1.0.1.sql`), counts and saves through 2.0, and checks the tables are exactly as 1.x made them, still at schema 2, with a stat 2.0 doesn't define keeping its row. The config goes to version 2: messages move to `lang/` (the boards' words and the period names too), `theme` moves into `messages.theme` and `update-checker` becomes `updates`. The old file is copied aside as `config.yml.bak-v1` first, and every message changed in 1.x is carried into `lang/en.yml` (`Legacy`). The fixtures are `config-1.0.1.yml.txt` and `-edited.yml.txt`, kept as `.txt` because of their blank MySQL password. The steps back are in the docs ([Upgrading](https://plugins.xenastudios.co/xstats/upgrade/)).
- **Stats from other plugins: the add-on API.** `registerStat(owner, id, name, unit, latest, decimals)` gives a `CustomStat` (`increment`, `set`), kept, saved, ranked and shown like xStats' own, with periods. On a network, a `latest` stat is the last value any server set, and a count is every server's added up. `unregisterStats` takes them out of use (Bukkit does it as the owner disables). `registerProfileSection` adds lines to `/stats`, the website and the web API, each asked off-thread with half a second to answer. The events are `StatChangeEvent` and `PrivacyChangeEvent` (cancellable, new in 2.0), and 1.x's `StatsSavedEvent` and `LeaderboardChangeEvent`, also as Bukkit events, bridged with the first listener. ABI dumps are in `xstats/api/api/`.
- **The family's stats, by reflection.** Each Xena plugin relocates its own core, so their types can't be named at build time. `FamilyHooks` finds `co.xenastudios.<id>.api.X<Name>` (zChat's `ZChat`) in that plugin's class loader, calls `getEvents()`, and subscribes by event-class name at MONITOR, with a `java.lang.reflect.Proxy` of that plugin's own listener interface. It reads each event through public getters only. The stats are xVote's `VoteRewardedEvent` → `xvote_votes`; xMoney's `BalanceChangedEvent` → `xmoney_balance` (latest) and `xmoney_earned`; xBans' `PunishedEvent` → `xbans_punishments` (not counted again when another server's arrives); xTeleport's `TeleportEvent`; xRewind's `RollbackFinishedEvent` (blocks applied, for the staff member); xMarket's `ShopBoughtEvent` and `ShopSoldEvent`; zChat's `ChatMessageSentEvent`. Each has a switch under `integrations`. They're registered once the database is open, so saved values are read first, and only on a server with one of them: `XStatsPlugin.FAMILY` is a constant the adapter checks before loading the hooks' code. `FamilyTest` drives xVote's and xMoney's events through stand-in API classes with the real names. Two `api` projects can't share a Gradle classpath, since both are `co.xenastudios:api`. The Boot workflow's family test boots xStats beside the real xVote, xBans, xTeleport, xRewind, xMarket and zChat, and each one's hook must log its stats. `boot.sh --xmoney` does the same with xMoney. Players xVanish hides (the family's player cache) are left out of leaderboards while hidden, and shown as offline on the website.
- **Placeholders.** On Bukkit, PlaceholderAPI's `%xstats_*%` are 1.x's, answered from memory. On Fabric, Text Placeholder API's `%xstats:stat <params>%` takes the same params, plus `%xstats:kd%`. It's reached by reflection, since its 2.x (1.20.1 to 1.21.11) and 3.x (26.1 on) register through different methods and handler types, so the handler is a `Proxy` of whichever the server has. Fabric has no PlaceholderAPI, so `papi:` stats read nothing there.
- **Boards in the world need 1.19.4.** They're text displays, made by a class only servers that have them load (`TextBoards`, in `bukkit/src/modern`, compiled against Paper). Below 1.19.4 `/xstats board add` says why it can't. Fabric has no boards. The Bukkit floor is 1.13, the first version with block data and the flattened stat names. 1.x's table names every stat from 1.13 to 26.x, and a stat a server's Minecraft lacks (`raid_win` before 1.14) reads 0 there, with one note in the console. `api-floor.txt` lists each newer member, every one guarded.
- **The first start's import waits for a world.** On Fabric the world comes after the mods, and the database can open first. The first start's import tries again each second for two minutes, rather than finding no world and never importing.
- **Startup without the slow parts.** Enable reads only `config.yml` on the server thread. The database opens on an async task and every player is read on the database's thread. Code an idle server never runs loads at first use: a save's code (`data/Saving.kt`), the store's writes (`store/Writes.kt`), the API's bodies (`Calls.kt`), a player's reading (`Reading`), the website and the import (`Extras`, made through a factory), boards, the family's hooks, the event queue (with the first event), and leaderboards. While nobody has played there's nothing to rank; boards asked for then are made empty, as a save makes them, and the first player's save works them all out. The repeating save is a plain scheduler task, not a module, and the one-method classes are folded into the classes that load anyway. Each deferred class is pinned in `bukkit/r8/xstats.pro` so R8 doesn't inline it back. The startup list (`bukkit/startup-classes.txt`) keeps only the classes a boot links, not ones loaded just for the verifier. The shim's `getDeclaredConstructors()` links each class it lists, which costs metaspace for a class that would otherwise only be loaded. That trim was made by hand from `-Xlog:class+init` (see Not done).
- **Size: the Bukkit jar is 850 KiB, over the 500 KiB target (and 1.x's 399 KiB), and stays so.** About 425 KiB is the shared core it reaches, the same parts as xVote's: the database layer and change feed, commands, config, messages and the family. About 300 KiB is xStats' own code and its API: the engine and its periods, 1.x's tables and statements, the stat table, leaderboards, boards, the commands, the website's server and JSON API, the import, the family's hooks, PlaceholderAPI and the events. The seven translations add 20 KiB, the website's own files 18 KiB, bStats 8 KiB and the startup list 3 KiB. Velocity's jar is 697 KiB, and Fabric's are 752 to 766 KiB before Loom remaps them. `gradle/jar-budgets.txt` has each size plus 10%.
- **Startup and memory.** Measured on Paper 26.3 on an M1 Pro, beside other work (`scripts/budgets/check.sh`, median of 3), with the startup list: startup 69 to 85 ms (150 ms budget), and **metaspace 1.525 MB** in chunks here (1,569,952 bytes in blocks, 469 classes). On CI that's about 1.48 MB: CI reads 0.04 MB less than this machine, as xVote's 1.464 MB on CI against 1.505 MB here shows. It was 1.685 MB, with 513 classes and a 227 ms startup, before the deferrals and the list. The measure is the loader's chunks, so it moves in steps of up to 20 KB between runs of the same jar. Heap: 3.0 to 4.2 MB over the bare server across local runs, against a 4 MB budget; CI keeps the lowest of three. Velocity 3.4.0 alone starts in 24.6 ms and 4.3.1 in 26.6 ms, both within 150 ms. CI's budgets job measures on two cores and is the final word.
- **Tested on real servers.** The boot checks ran on Paper 26.3 with boards, on Folia 26.3, and on Paper 1.21.11 with a real client in German (`/stats`, jumps a save reads, the leaderboard, `/stats private`). They ran on Spigot 1.13.2, the floor, in a Linux container with a client, and on Fabric 1.20.1, 1.21.11 and 26.3 from the console. They ran on Velocity 3.4.0 and 4.3.1 alone, and in the family test (Paper 26.3, the seven plugins above) and beside xMoney. The network test runs Velocity 4.3.1 in front of two Paper 1.21.11 servers on one MariaDB: a client jumps on lobby, lobby saves, and the proxy's `/networkleaderboard jumps` has them.
- **The core didn't change.** `scripts/budgets/bots/client.js` has the `xstats` and `xstats-network` scenarios, and `core/platform-fabric/settings.gradle.kts` has the `xstats` branch and its substitution. No core class loads more.
- **bStats 35436, 1.x's id, on Bukkit only.** Velocity has no xStats service id. The update checker runs everywhere.
- **Release:** `xstats/bukkit` applies `xena.release` for the Bukkit, Velocity and Fabric jars: Hangar `xStats`, voxel.shop 10716, Modrinth `xstats`. Version 2.0.0, unreleased, with its pages at `/xstats/next/` (`versions.json`'s `unreleased`, which keeps 1.0.1 as the release). The 1.x pages are at `/xstats/v1/`. `modrinth.md` is unchanged until the release.

  - The family's hooks for xBans, xTeleport, xRewind, xMarket and zChat are checked to subscribe in the family test. Only xVote's and xMoney's are checked to count, by `FamilyTest`'s stand-ins. No boot fires the others' events.
  - Fabric has no boards and no PlaceholderAPI stats, and no real client has played on Fabric or Folia with xStats.
  - `scripts/budgets/startup_classes.py` still records every class loaded before "Done". A re-recorded list would grow by the 35 classes trimmed here, about 9 KB of metaspace. Teaching it `-Xlog:class+init` would help every plugin's list, and is left for a pull request of its own.
  - Proxy-side placeholders don't exist.
