The config is `plugins/xBans/config.yml` (`plugins/xbans/` on Velocity, `config/xbans/config.yml` on Fabric), written on first start. Apply changes with `/xbans reload` (`/xbansproxy reload` on the proxy): everything applies, even switching to another database. A bad value falls back to its default with a warning in the console; xBans never stops over config. xBans' messages, the ban screens among them, are in `lang/`: see [Messages](/xbans/messages/).

| Section | What it's for |
| --- | --- |
| `messages` | The language and the theme, `shared` with every Xena plugin unless set here. |
| `screens` | The appeal link the ban screens show. The screens themselves are in `lang/`. |
| `commands` | Each command's switch, aliases and permission. |
| `punishing` | The default reason, and whether punishments are silent unless `-p` is given. |
| `mutes` | Which commands a mute blocks, and signs, books and anvil renames. |
| `warnings` | How long a warning lasts, and what happens at 3 or 5. |
| `templates` | Reasons and escalation ladders, such as `hacking`. |
| `staff-limits` | Weights, and the longest ban and mute per group. |
| `ips` | Whether IPs are recorded, hashed, and checked for banned alts. |
| `scopes` | This server's name, and whether punishments are global or local by default: [Networks](/xbans/networks/). |
| `lists` | How many to a page, and how dates are written. |
| `storage` | Where punishments are: SQLite in the plugin's folder (`punishments.db`), MySQL/MariaDB, or the family's shared database. |
| `network` | Sharing bans between servers and the proxy: [Networks](/xbans/networks/). |
| `updates` | The update checker: [Privacy](/start/privacy/). |

## Templates

```yaml
templates:
  hacking:
    type: "ban"
    reason: "Hacking"
    ladder: ["1w", "30d", "permanent"]
    expire-ladder: "180d"
```

`/ban Steve hacking` gives the first step of the ladder the first time, the second the next time, and the last step every time after. A past punishment counts toward the ladder until `expire-ladder` has passed since it was made; one that was revoked (an appeal, a mistake) doesn't count. `type` is `ban`, `mute` or `warn`, and a template only works with its own kind of command. `ip: true` makes it an IP punishment, and `silent: true` a silent one.

Each template needs its own permission, `xbans.template.<name>` unless `permission` names another. Operators have it; give it to the staff who should use the template. A template's durations are held to the sender's [staff limits](#staff-limits) like typed ones, so a helper capped at a day can't get to a permanent ban by repeating `/ban Steve hacking`: past their cap, it's refused. Staff with `xbans.limit.bypass-templates` may use a template's own durations past their cap (not ones they type).

## Warnings

```yaml
warnings:
  default-duration: "30d"
  actions:
    3:
      commands: ["tempmute <player> 1h -s Reached 3 warnings"]
```

When a player reaches a number of active warnings, the console runs that number's commands. Any command works, including other plugins'.

## Mutes

`mutes.blocked-commands` lists the commands a muted player can't use. A command's aliases and namespaced forms are blocked too: blocking `msg` blocks `/tell`, `/essentials:msg` and EssentialsX's `/emsg`. Muted players also can't write on signs (`block-signs`) or in books (`block-books`), or rename items on an anvil (`block-anvils`, from 1.11). On Fabric, Minecraft has no event before a command runs, so a mute blocks Minecraft's `/me` and `/say` and [zChat](/zchat/)'s `/msg` and `/reply` there, and signs, books and anvils not at all.

## Staff limits

```yaml
staff-limits:
  weights: true
  groups:
    helper:
      permission: "xbans.limit.helper"
      ban: "1d"
      mute: "1d"
```

A staff member with a group's permission can't ban or mute for longer than its limits; with several groups, the longest applies. `permanent` means no limit. See [Commands](/xbans/commands/#staff-limits) for weights.

## Storage

`type: sqlite` needs nothing set up. Use `type: mysql` (it works with MariaDB too) for a network, or point several servers at one database; `shared` keeps xBans' tables in the database every Xena plugin can share, set in `plugins/Xena/config.yml`. `table-prefix` goes in front of every table's name. The tables are 1.x's, unchanged, so the [1.x jar](/xbans/upgrade/#going-back-to-101) reads them too.

The database is opened in the background, and every ban and mute in force is read into memory before it's used. Until then, players trying to join wait up to 10 seconds, then see the `screens.not-ready` message; that's only in the first moments after a start. If the database can't be opened at startup, xBans tries again every 15 seconds, and nobody can join until it opens: a ban plugin that lets everyone in when its database is down would let banned players in too. Changing `storage` on a reload switches to the new database once its bans are loaded; a reload that can't open the new one keeps using the old one. Punishments aren't copied between databases.

## Make it look like your server

`messages.theme` sets the look of every message xBans sends: a prefix, the text colour, and three styles. Each is `shared` until you set it, which takes the value every Xena plugin shares, in `plugins/Xena/config.yml`. `messages.language` is `auto` by default (through `shared`): each player reads xBans' messages, ban screens included, in their client's language, and the console in `default-language`. A config carried forward from 1.x with messages you'd edited is set to `en`, so your words are what everyone sees, as before.
